# Vegabond 개발 설계

호출한 작업이나 [개발 구현](../vegabond-code/SKILL.md)에 필요한 설계 결정을 내립니다. 기존 작업 개요, 환경, 출처, 정보 조사 결과를 재사용합니다. 실행과 검증은 호출 측이 담당합니다. 설계는 별도 작업 흐름을 시작하거나 소프트웨어 동작을 인증하지 않습니다. 문서 경계와 공통 인수 기준은 [에이전트 지침](../../agents/vegabond-agent.md)을 따릅니다. 이 스킬을 읽는 것만으로 에이전트를 생성하지 않습니다.

직접 호출되면 [Scout의 공통 준비](../vegabond-scout/SKILL.md#frame-and-classify)와 [구현 환경 확인](../vegabond-code/SKILL.md#identify-the-working-environment)으로 부족한 맥락만 채웁니다. 설계만 요청받았다면 운영 코드를 바꾸지 않고 설계와 근거를 전달합니다. 결정에 필요하고 권한이 있을 때만 격리 실험을 합니다.

요청한 동작과 합격 조건이 명확하면 바로 진행합니다. **같은 테스트가 용어의 두 가지 타당한 해석에 따라 합격과 불합격으로 갈릴 때만** 작업 프로젝트의 용어집을 참조합니다. 인수 기준을 정하기 전에 해당 항목만 읽고 연결된 원문 규칙을 확인합니다. OneStep의 `docs/development-glossary.md`에서는 첫 열에서 용어를 찾아 해당 행만 읽습니다. 두 해석을 가르는 사례와 기대 판정을 구현에 전달합니다. 항목이 없거나 원문과 일치하지 않으면 해당 동작을 정의하는 근거를 확인하고, 사용자 결정이 남을 때만 질문합니다.

게임 아키텍처와 기술 선택에는 직접 호출된 경우에도 [게임 근거 재사용 규칙](../../knowledge/game/K-GAME-RESEARCH-USE.md)을 적용합니다. 유효한 조사 결과를 재사용하고 롤백에 필요한 상태 복원 가능성 등 전제를 점검합니다. 실제 엔진·플랫폼·게임플레이 제약에 따라 채택, 조건부 사용 또는 기각을 기록합니다. 선택한 항목 ID, 구현 경계와 검증 방안을 설계와 함께 전달합니다.

새 게임은 [기반 설계 결정](references/gameplay-framework.md#plan-a-new-game-foundation)부터 시작합니다. 스캐폴딩이나 패키지를 고르기 전에 대표적인 플레이에서 프레임워크, 상태 소유권, 콘텐츠 추가 경로를 도출합니다. 기존 게임에서 이 결정이나 기능 조합 방식을 변경할 때는 [게임플레이 프레임워크와 콘텐츠 설계](references/gameplay-framework.md)의 해당 부분을 적용합니다. 구현까지 요청받았다면 설계와 제안한 검사를 구현으로 이어갑니다.

입력 반응, 타격감, 플레이 결과를 전달하는 카메라·시각 효과·음향·햅틱을 설계할 때는 [게임플레이 피드백 지침](references/gameplay-framework.md#design-gameplay-feedback)을 사용합니다.

게임 데이터의 변화, 월드의 로드·유지 대상, 렌더링 예산, 화면 밖 NPC 동작을 결정할 때는 [월드 런타임 설계 지침](references/world-lifecycle.md)의 해당 부분을 사용합니다. 각 정책을 게임플레이 요구와 연결하고 보존·전환·측정 조건을 구현에 전달합니다.

## 설계 결정

범위나 구현 순서가 정해지지 않았다면 [범위·설계 깊이·전달 단위](references/scope-and-delivery.md)를 사용합니다. 관찰 가능한 결과, 설계가 필요한 결정과 잘못 결정했을 때의 비용, 이번 작업을 한 번에 하거나 단계별로 검증하는 이유를 전달합니다. Scout의 개요를 재사용하고 실제 규칙을 조사한 뒤 임시 규모 판단을 조정합니다.

[공통 정보 필요성 판단](../vegabond-scout/references/information-needs.md)으로 보장 조건, 경계, 반례에서 빠진 질문이 드러나는지 확인합니다. 채택한 규칙, 조건부 가정, 배제한 유추를 각각 영향을 받는 결정에 연결합니다.

1. **결정의 근거를 확인합니다.** 기존 개요에서 결정할 사항, 필요한 결과, 보존 조건과 영향 범위를 찾습니다. 관련 진입점, 호출자, 데이터, 테스트, 프로젝트 관례를 조사합니다. 정보가 구체적으로 부족할 때만 [지식](../vegabond-knowledge/SKILL.md)을 통해 원문이나 과거 교훈에 관한 질문을 좁힙니다. 필수 보장과 선택 가능한 절충안을 구분하고, 상충하는 요구나 이용할 수 없는 기능을 드러냅니다.
2. **구조를 정합니다.** 구현 단계에 앞서 관련 데이터 모델, 상태 소유자, 불변 조건, 수명 주기, 인터페이스를 적습니다. 실패 동작과 필요한 경우 동시 접근, 재시도, 영속화, 정리, 통합 경계를 포함합니다. 언어와 프레임워크의 실제 규칙을 따릅니다. 순수 함수에 인위적인 상태 기계를 붙이는 식으로 범위를 넓히지 않습니다.
3. **근거로 선택합니다.** 실제 절충점이 있을 때 대안을 비교합니다. 명백한 로컬 패턴에 여러 설계를 만들어내지 않습니다. 선택한 구조가 맞는 이유와 비용, 고려 후 기각한 중요한 대안을 설명합니다. 경험적으로 확인할 문제 하나가 결정을 뒤집을 수 있다면 후속 작업 전에 근거를 조사하거나 필요한 최소 실험을 합니다. 실행할 수 없는 필수 검사는 차단됨으로, 검증하지 않은 전제는 불확실함으로 표시합니다. 그럴듯한 설계만으로 런타임 동작을 입증할 수 없습니다.
4. **구현과 검증이 가능하게 합니다.** 관련 인터페이스·호출자, 필요한 경우 이전 순서와 호환성 의무를 확인합니다. 중요한 불변 조건과 가정마다 구체적인 검사, 기대 결과, 필요한 환경을 연결합니다. 성능·자원 주장이 중요하면 측정 가능한 예산을 정합니다. 설계를 반환하거나 후속 구현으로 넘어가기 전에 [설계 검토](references/review.md)를 읽고 적용합니다. 요구를 동작 원리와 근거까지 추적하고 실패 순서를 점검해 모순을 수정합니다. 설계 검토가 이 검사를 맡고, 실제 구현에는 호출 측의 소프트웨어 검증을 적용합니다.

## 결정 전달

타당한 해석에 따라 사용자나 플레이어가 관찰하는 결과가 달라지면 먼저 프로젝트의 원문 규칙에서 결정을 찾습니다. 선택권이 사용자에게 남아 있으면 결과가 갈리는 구체적인 상황 하나로 질문합니다. 답을 받으면 합의한 동작과 그 상황의 기대 결과를 구현 인계에 포함합니다. 답이 달라지면 검사도 달라져야 합니다. 이미 정한 결정은 그대로 사용하고 기술적 미확인 사항은 조사나 집중 실험으로 해결합니다.

결과를 작성해 전달할 때는 [독자를 위한 공통 설계 설명 지침](../../agents/references/design-communication.md)을 적용합니다. 타입, 저장 필드, 트랜잭션 세부사항에 앞서 관찰 가능한 동작과 중요한 실패 사례를 설명합니다. 이어서 구조와 소유권, 인터페이스, 구현·이전 단위, 근거, 검사를 해당 결정과 연결합니다.

설계가 지원하는 보장, 남은 구현 검사, 어떤 미해결 전제가 어떤 후속 작업을 막는지 밝힙니다. 유용한 부분 제안만으로 필요한 보장을 충족한 것은 아닙니다. 호출 측은 최종 구현에 [코드 검증 절차](../vegabond-code/references/verification.md)를 적용하고, 근거가 설계 결정을 바꿀 때만 이 단계로 돌아옵니다. 여전히 유효한 맥락은 보존합니다.

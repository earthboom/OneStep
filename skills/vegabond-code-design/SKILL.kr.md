# Vegabond Code Design

상위 작업 또는 [vegabond-code](../vegabond-code/SKILL.md)가 맡긴 소프트웨어 설계 결정을 내린다. 기존 브리프, 작업 환경, 출처, 정보 브리프를 재사용한다. 실행과 검증은 호출한 작업이 담당한다. 설계를 통해 별도의 작업 흐름을 시작하거나 소프트웨어가 동작한다고 인증하지 않는다. 문서 범위와 공통 수용 기준은 [에이전트 지침](../../agents/vegabond-agent.md)을 따른다. 이 스킬을 읽는 것만으로 에이전트를 생성하지 않는다.

직접 호출된 경우 [scout의 공통 준비 절차](../vegabond-scout/SKILL.md#frame-and-classify)와 [code의 환경 파악](../vegabond-code/SKILL.md#identify-the-working-environment)에서 빠진 맥락만 채운다. 설계만 요청되면 설계와 뒷받침하는 근거를 전달한다. 격리 실험은 결정에 필요하고 권한이 있는 경우에 사용한다.

게임 아키텍처와 기술 선택에 [게임 근거 재사용 규약](../../knowledge/game/K-GAME-RESEARCH-USE.md)을 적용한다. 직접 호출된 경우도 포함한다. 유효한 근거를 재사용하고 롤백에 필요한 복원 가능한 상태 같은 전제 조건을 점검한다. 실제 엔진·플랫폼·게임플레이 제약에 비추어 채택, 조건부 사용, 제외를 기록한다. 선택한 지식 항목 ID, 구현 경계, 제안 검증을 설계와 함께 전달한다.

새 게임은 [기반 설계 결정](references/gameplay-framework.md#plan-a-new-game-foundation)에서 시작한다. 프로젝트 뼈대, 패키지, 공용 기반 클래스를 선택하기 전에 대표 플레이에서 프레임워크, 상태 소유권, 콘텐츠 경로를 도출한다. 기존 게임의 이러한 결정이나 기능 조립 방식이 바뀌면 [게임플레이 프레임워크와 콘텐츠 설계](references/gameplay-framework.md)의 관련 부분을 적용한다. 요청에 구현이 포함되면 설계와 제안 검증을 구현에 연결한다.

입력 반응, 타격 피드백 또는 게임플레이 결과를 전달하는 카메라·이펙트·사운드·햅틱을 설계할 때는 [게임플레이 피드백 지침](references/gameplay-framework.md#design-gameplay-feedback)을 사용한다.

게임 데이터의 변경 방식, 월드가 로드하거나 유지할 내용, 렌더링 예산을 충족하는 방법, 화면 밖 NPC 동작을 정할 때는 [월드 런타임 설계 지침](references/world-lifecycle.md)의 관련 부분을 사용한다. 선택한 정책을 게임플레이 요구에 연결하고 유지, 전이, 측정 조건을 구현에 넘긴다.

## 설계 결정 내리기

[공통 정보 조사 판단](../vegabond-scout/references/information-needs.md)을 사용해 필요한 보장, 경계, 반례에서 빠진 질문이 있는지 확인한다. 채택한 계약, 조건부 가정, 제외한 비유나 사례는 영향을 받는 결정에 함께 기록한다.

1. **결정의 근거를 확보한다.** 기존 브리프에서 정할 결정, 필요한 결과, 유지 조건, 영향을 받는 경계를 확인한다. 관련 진입점, 호출자, 데이터, 테스트, 프로젝트 관례를 검토한다. 정보 브리프에 구체적인 공백이 있을 때만 [knowledge](../vegabond-knowledge/SKILL.md)를 통해 출처나 과거 교훈에 관한 질문을 구체화한다. 필요한 보장과 제안한 절충을 구분하고, 요구가 충돌하거나 필요한 기능을 사용할 수 없으면 이를 밝힌다.
2. **구조를 정의한다.** 구현 단계를 정하기 전에 관련 데이터 모델, 상태 소유자, 불변 조건, 수명, 인터페이스를 명시한다. 실패 시 동작과 필요한 경우 동시 접근, 재시도, 영속성, 정리, 통합 경계를 포함한다. 언어와 프레임워크의 실제 계약을 따른다. 작업에서 필요한 결정만 내린다. 순수 함수라면 별개의 상태 기계를 추가할 필요가 없다.
3. **근거를 바탕으로 선택한다.** 실제 절충이 있을 때 대안을 비교한다. 국소 변경에서 명확한 패턴이 있으면 그대로 적용한다. 선택한 구조가 맞는 이유, 비용, 제외한 중요한 대안을 설명한다. 경험적 불확실성 때문에 선택이 달라질 수 있으면 후속 작업 전에 근거를 살피거나 가장 작은 실험으로 확인한다. 접근할 수 없는 필수 검증은 진행 불가로, 확인하지 않은 가정은 불확실한 것으로 기록한다. 런타임 동작은 실행한 근거로 판단한다.
4. **구현하고 확인할 수 있게 한다.** 영향을 받는 인터페이스와 호출자, 해당하는 마이그레이션 순서와 호환성 의무를 적는다. 중요한 불변 조건과 가정마다 구체적인 검증, 기대 관찰 결과, 필요한 환경을 연결한다. 성능·자원 주장이 중요한 경우 측정 가능한 예산을 정한다. 설계를 반환하거나 후속 구현에 앞서 [설계 검토](references/review.md)를 읽고 적용한다. 요구를 구현 원리와 근거에 연결하고, 관련 실패 흐름을 점검하고, 모순을 해결한다. 상세 설계 검토는 해당 문서를 따르고 구현에는 호출한 작업의 소프트웨어 검증을 적용한다.

## 결정 인계

결과를 작성하고 인계할 때 [독자를 위한 공통 설계 전달 지침](../../agents/references/design-communication.md)을 따른다. 타입, 저장 필드, 트랜잭션을 소개하기 전에 관찰 가능한 동작과 중요한 실패 상황을 설명한다. 이어서 선택한 구조와 소유권, 인터페이스, 구현·마이그레이션 단위, 근거와 검증을 각각 어떤 결정을 뒷받침하는지 연결한다.

설계로 뒷받침하는 보장, 남은 구현 검증, 이름을 명시한 후속 작업을 막는 미해결 전제를 적는다. 부분 제안이 제공하는 범위를 구분한다. 호출한 작업은 실제 구현에 [code의 검증 절차](../vegabond-code/references/verification.md)를 적용한다. 근거 때문에 설계 결정이 바뀔 때 다시 설계를 검토하고, 유효한 맥락을 재사용한다.

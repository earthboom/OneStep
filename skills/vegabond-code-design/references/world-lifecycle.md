# Game data and world runtime design

Use the applicable sections within the existing design brief. Choose from current gameplay requirements, engine constraints and representative workloads. Reuse [gameplay framework and content design](gameplay-framework.md) for feature composition and [design review](review.md) for acceptance and counterexamples.

## Define what must survive change

- Assign separate owners to authored definitions, derived build artifacts, mutable gameplay state and durable progress wherever their lifetimes differ. Give externally stored game objects an identifier with a defined lifetime. Keep presentation identity, display text and engine paths independent when those can change.
- For additions define defaults, validation and allowed dependencies. For updates specify which active sessions and old saves use the new value. For retirement identify existing saves, quests, replication or mods that still refer to the definition. Decide whether to preserve it, map it explicitly, substitute under a stated contract, or reject with a diagnostic. Reserve retired IDs while any supported data can still contain them. Define the response to unknown, future and malformed data and the publication point for a validated catalog or migrated save.
- Specify checkpoints at which a live catalog may change, what a session pins, and where network versions must agree. Choose what persists across scene or cell unload, world exit and process restart separately. Give persistent state an owner with that lifetime. Pass actual older inputs and expected results to verification. [Versioned saves](../../../knowledge/game/K-GAME-TECH-SAVE.md) · [Factorio migration example](https://lua-api.factorio.com/latest/auxiliary/migrations.html)

## Choose budgets and residency

- State the player route, build, target device, quality configuration and relevant frame, memory or readiness budget. Use a baseline capture to distinguish game-thread work, render submission, GPU passes and load/activation stalls. Choose the rendering change from the observed cost and state the visual or gameplay detail it must preserve. Treat draw counts and asset sizes as diagnostics alongside timings and perceived quality. [Measurement procedure](../../../knowledge/code/K-CODE-PERFORMANCE-MEASUREMENT.md) · [Foliage tradeoffs](../../../knowledge/game/K-GAME-TECH-FOLIAGE.md)
- Choose among on-demand creation, bounded pooling, derived-result caching, baking, prefetch and retained residency by reuse, latency, peak memory and invalidation cost. Identify separately who owns the request, resident resource, active object and reusable result. Decide how an abandoned load releases its result, how pooled checkout resets state and how an old callback is excluded. Define what the game does when a region misses its ready deadline. Evaluate entry and exit churn before changing thresholds. [Object Pool](https://gameprogrammingpatterns.com/object-pool.html) · [Streaming case](https://www.gdcvault.com/play/1022268/Streaming-in-Sunset-Overdrive)

## Specify NPC behavior across tiers

- Start with observable actions and interrupts. Give perception, decision, movement and action execution distinct responsibilities where their failure or update policy differs. Choose state machines for explicit modes, behavior trees for authored priority and interruption, utility for scored alternatives, or planning for changing action sequences when the game needs those properties. Define time limits or work bounds for expensive queries and plans. Include unreachable destinations, cancellation and state needed for debugging. [Crowd behavior and pathing](../../../knowledge/game/K-GAME-TECH-CROWD.md)
- Decide independently when to render, animate, collide, run AI, replicate and unload. Use distance or visibility as signals alongside combat, quests, audio, authority and all relevant observers. Distinguish persistent agents from ambient representatives. Choose the lowest update fidelity that preserves the required outcomes, including what happens while representation is absent. Specify the state and time origin transferred on each transition, who may write during it, guards against rapid oscillation and how activation catches up without duplicate effects. Choose a real unload and re-entry case plus an interrupted transition if supported. [Simulation LOD](https://pages.cs.wisc.edu/~schenney/research/culling/chenney-gdc2001.pdf) · [Mass representation, simulation and replication](https://dev.epicgames.com/documentation/unreal-engine/overview-of-mass-gameplay-in-unreal-engine)

Return the selected policies and rejected consequential alternatives, version and authority assumptions, representative input and expected outcomes, and budget or measurement scope. Pass the relevant [runtime checks](../../vegabond-code/references/world-lifecycle-verification.md) to implementation.

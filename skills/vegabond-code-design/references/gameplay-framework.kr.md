# 게임플레이 프레임워크와 콘텐츠 설계

게임의 실행 구조, 콘텐츠의 게임플레이 확장 계약, 기능 간 의존성을 정하거나 바꿀 때 적용한다. 결정과 검사 조건은 기존 브리프나 설계에 적고, 변경에 해당하는 항목을 사용한다. 계약이 그대로인 국소 수정은 기존 경로를 따라 영향을 받는 동작을 확인한다.

## 대표 플레이에서 프레임워크 요구를 도출한다

기존 설계에서 시작하거나 플레이어 입력, 규칙 실행, 피드백, 다음 의미 있는 선택으로 이어지는 짧은 흐름을 적는다. 다른 모드나 혼합 장르의 활동에서 필요한 보장이 달라지면 두 번째 흐름을 추가한다. 턴 또는 실시간 처리, 응답 시간, 시뮬레이션 권한, 복제, 결정적 리플레이, 저장, 제작 방식, 예상 처리량 중 해당 흐름이 요구하는 조건을 확인한다. 중요한 기술 선택을 플레이 요구와 관찰 가능한 결과에 연결한다. 아직 모르는 요구는 영향을 받는 결정에 붙여 둔다. [장르와 관찰 가능한 플레이](../../../knowledge/game/K-GAME-DESIGN-FRAMEWORK.kr.md)

예를 들어 턴제 전술 게임은 명령을 검증하고 규칙 순서대로 행동을 처리해 턴 결과를 제공하는 위치가 필요할 수 있다. 실시간 협동 액션에서는 즉각적인 로컬 피드백, 권한 측의 결과 확정, 복제 상태가 늦게 도착했을 때의 복구가 필요할 수 있다. 실제 게임에서 필요한 조건을 확인한다. 입력·보장·변경 이유가 같은 규칙은 두 모드가 공유할 수 있다. 엔진 없이 검사하거나 공유할 실제 필요가 있는 규칙은 일반 C++로 둔다. 월드·Actor·에셋·네트워크에 묶인 동작은 기존 엔진의 소유권과 훅을 따른다.

## 콘텐츠를 추가하는 경로를 설계한다

기존 콘텐츠 하나와 실제로 추가할 만한 변형 하나를 고른다. 두 번째 조우, 무기, 퀘스트, 규칙 세트가 예다. 제작자가 두 콘텐츠를 작성하고 검증하고 등록한 뒤 플레이에서 사용하고 갱신하는 경로를 추적한다. 안정적인 규칙과 그 소유자, 달라지는 제작 데이터, 별도 구현이 필요한 동작을 식별한다. 호출자가 같은 보장을 필요로 하고 함께 바뀌어야 하는 규칙을 공유한다. 기능의 고유 상태와 내부 구현은 해당 기능이 소유한다. 호출자가 필요한 작은 인터페이스에 권한, 유효 상태, 실패, 수명 조건을 명시한다. [정보 은닉](../../../knowledge/code/K-CODE-INFORMATION-HIDING.kr.md)

의미가 정해진 값과 조합은 검증 가능한 데이터나 에셋으로 표현한다. 독립적으로 바뀌는 동작은 구체 함수·타입·컴포넌트로 조합한다. 확인된 변형이나 프레임워크 계약이 확장을 요구하면 확장점이나 기반 타입을 두고, 공개 상속은 대체 가능성을 확인한다. 콘텐츠 등록 위치와 여러 기능을 조립하는 위치를 정한다. 기존 콘텐츠, 저장 파일, 네트워크 상대가 사용하는 ID와 스키마, 계약을 보존하거나 마이그레이션 방법을 적는다. 누락되거나 잘못된 콘텐츠는 프로젝트가 감지할 수 있는 지점에서 처리한다.

## 기능 간 의존성을 드러낸다

각각 독립적으로 선택 가능한 기능 사이에는 직접 의존성을 두지 않는다. 공통 규칙과 안정적인 계약은 공유 소유자에 둘 수 있다. 모드 조립 코드는 선택한 기능에 의존할 수 있다. 선택 기능이 서로 의도적으로 상호작용할 때는 조립 지점이나 필요한 기능이 모두 있을 때 활성화되는 통합 지점에서 연결한다. 제품 요구로 한 기능이 다른 기능을 반드시 필요로 하면 의존 방향, 필요한 계약, 기능을 사용할 수 없을 때의 동작을 명시한다. 순환을 피하고 프로젝트에서 이유가 확인된 의존 방향을 따른다. [의존 방향](../../../knowledge/code/K-CODE-DEPENDENCY-DIRECTION.kr.md)

영향받는 소스·빌드 설정, 제작 콘텐츠, 런타임의 연결을 추적한다. 공개 타입·헤더·모듈·플러그인, 강한 참조와 소프트 에셋 참조 및 등록 데이터, 객체 조회·이벤트·초기화·정리 경로를 확인한다. 특정 기능이 이벤트나 태그, 소프트 참조의 대상을 반드시 제공해야 흐름이 성립한다면 의존성이다. 언리얼에서는 관련 `Build.cs`나 플러그인 선언, Blueprint와 데이터 에셋 참조를 확인하고, 대상 월드와 네트워크 역할에서 등록과 정리를 검증한다. [언리얼 빌드 의존성](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules) · [언리얼 Reference Viewer](https://dev.epicgames.com/documentation/en-us/unreal-engine/reference-viewer-in-unreal-engine)

## 콘텐츠와 실제 플레이로 변경을 검토한다

- **장르 적합성.** 설계를 좌우한 흐름을 실제 게임플레이 진입점에서 실행한다. 플레이어에게 보일 결과와 권한 측 상태를 확인한다. 실패나 실행 순서가 선택에 영향을 주면 그 사례도 검사한다.
- **확장과 유지보수.** 두 번째 대표 변형을 실제 제작·등록 경로로 추가하거나 그 경로를 추적한다. 수정이 필요한 공유 모듈, 파일, 공개 인터페이스, 에셋과 이유를 적는다. 공유 계약이 바뀌는 경우를 제외하고 수정이 새 콘텐츠와 등록에 집중되는지 확인한다. 공유 계약에 영향을 받는 기존 콘텐츠는 다시 검사한다.
- **독립성.** 프로젝트가 지원하는 구성에서 기본 플레이와 기능의 단독·조합 동작을 확인한다. 빌드나 패키지에서 기능 제외를 지원하면 그 구성에서 확인하고, 런타임 비활성화를 지원하면 꺼진 동작을 확인한다. 둘 다 지원하면 둘 다 검사한다. 런타임 수명주기가 있다면 등록 동작, 구독, 대기 중인 작업의 정리와 해당되는 재활성화를 확인한다. 의도치 않은 의존성이 있다면 실패할 수 있는 실제 빌드·로드·플레이 검사로 확인한다.

설계 결과에는 예상 관찰값과 알아낼 방법을 둔다. 구현은 대상 프로젝트가 사용하는 빌드, 테스트, 에디터, 패키징 경로에서 필요한 검사를 실행한다. 제안한 검사와 격리된 규칙 검사, 통합 플레이 결과를 각각 근거에 맞게 기록한다. [설계 검토](review.kr.md) · [소프트웨어 검증](../../vegabond-code/references/verification.kr.md)

## 새 게임의 기반 설계

대표 플레이 흐름을 사용하고 설계에 영향을 주는 실패나 중단을 하나 포함한다. 프로젝트 구조, 폴더, 공용 기반 타입, 선택 패키지를 고르기 전에 아래 결정을 기존 작업 브리프에 남긴다.

| 결정 | 기록할 내용 |
| --- | --- |
| 프레임워크 | 게임플레이 진입점, 시간 모델, 판정 권한을 정한다. 선택한 엔진, 목표 플랫폼, 제약에 맞춰 Unity나 Unreal의 역할에 연결한다. 독립 C#·C++가 유용한 규칙과 엔진의 월드·물리·에셋·네트워크가 맡는 부분을 파악한다. 엔진이 미정이면 게임플레이 계약을 명시하고 그 기준으로 엔진 후보를 비교한다. |
| 상태 소유권 | 중요한 상태를 누가 만들고, 쓰고, 읽고, 해제하는지 정한다. 필요한 경우 객체, 씬·월드, 세션·매치, 영속 저장의 수명을 구분한다. 해당하는 씬 이탈·재스폰·재접속에서 유지될 값을 정한다. 변경은 소유자를 거치고 표시는 필요한 상태나 결과를 읽는다. |
| 콘텐츠 추가 경로 | 첫 콘텐츠와 현실적인 두 번째 변형을 저작·검증·등록·플레이 단계로 따라간다. 소유 기능, 필요할 경우 안정적인 ID나 계약, 조립점과 허용 의존 방향을 적는다. 정의에서 바꿀 수 있는 부분과 규칙 변경이 필요한 부분을 정한다. |

필요한 계약을 충족하는 가장 단순한 엔진 기능과 모듈 경계를 고르고 더 복잡한 구조가 필요한 구체적 요구나 예산을 기록한다. 예를 들어 턴제 카드 어드벤처는 순서가 정해진 전투 명령과 저작한 카드 정의를 쓰고, 탐색은 자체 지도 상태를 소유할 수 있다. 기존 브리프 안의 짧은 항목으로도 충분하다. 전략·설계만 요청하면 결정, 가정, 예정된 확인 항목을 전달한다. 구현도 요청된 경우 해당 결정을 구현에 적용한다.

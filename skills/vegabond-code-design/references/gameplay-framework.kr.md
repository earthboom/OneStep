# 게임플레이 프레임워크와 콘텐츠 설계

게임의 런타임 구조, 콘텐츠가 게임플레이를 확장하는 계약, 기능 간 의존성을 선택하거나 바꿀 때 적용한다. 결정과 검증은 기존 브리프나 설계에 남기고 변경에 해당하는 부분을 적용한다. 기존 계약을 유지하는 국소 수정은 기존 경로로 진행하고 영향을 받는 동작을 확인한다.

## 새 게임의 기반 설계

[대표 플레이 흐름](#대표-플레이에서-프레임워크-도출)을 사용하고 설계에 영향을 미치는 실패나 중단을 하나 이상 포함한다. 프로젝트 뼈대, 폴더, 공용 기반 타입, 선택 패키지를 정하기 전에 다음 결정을 내린다.

| 결정 | 기존 브리프에 기록할 내용 |
| --- | --- |
| 프레임워크 | 게임플레이 진입점, 시간 모델, 권한을 선택한다. 엔진, 타깃 플랫폼, 제약에 맞춰 Unity나 Unreal의 역할로 연결한다. 엔진과 독립적인 C#·C++에서 처리할 이점이 있는 규칙과 엔진 월드·물리·에셋·네트워크가 소유하는 부분을 확인한다. 엔진이 미정이면 게임플레이 계약을 명시하고 그에 맞춰 엔진 선택을 비교한다. |
| 상태 소유권 | 중요한 상태마다 누가 생성하고, 쓰고, 읽고, 해제하는지 적는다. 해당하는 오브젝트, 씬·월드, 세션·매치, 영속 상태의 수명을 구분한다. 게임이 지원하는 경우 씬 종료·재스폰·재접속 같은 전이에서 유지할 것을 명시한다. 변경은 소유자를 통하고 표현 계층에는 읽을 상태나 결과를 전달한다. |
| 콘텐츠 진입 경로 | 첫 콘텐츠와 가능성 있는 두 번째 변형을 저작, 검증, 등록, 플레이까지 따라간다. 담당 기능, 필요한 경우 고정 ID나 계약, 조립 위치와 허용 의존성을 명시한다. 정의를 통해 할 수 있는 변경과 규칙을 바꿔야 하는 변경을 구분한다. |

결정을 만족하는 가장 단순한 엔진 기능과 모듈 경계를 사용한다. 더 복잡한 프레임워크를 정당화할 구체적인 요구나 예산도 기록한다. 예를 들어 턴제 카드 어드벤처는 순서가 정해진 전투 명령과 저작한 카드 정의를 사용하고, 탐험은 자체 지도 상태를 유지할 수 있다. 인계는 기존 브리프의 짧은 절로 남길 수 있다. 전략이나 설계만 요청되면 설계의 결정, 가정, 제안 검증을 전달한다. 요청에 구현이 포함된 경우 구현에 연결한다.

## 대표 플레이에서 프레임워크 도출

기존 설계에서 출발하거나 플레이어 입력, 규칙 실행, 피드백, 다음 의미 있는 선택의 짧은 흐름을 설명한다. 다른 모드나 혼합 활동 때문에 보장이 달라지면 두 번째 흐름도 포함한다. 선택한 흐름에 관련된 턴 또는 실시간 갱신, 응답 기한, 시뮬레이션 권한, 복제, 결정적 재생, 영속성, 저작, 예상 부하를 식별한다. 중요한 선택마다 게임플레이 요구와 관찰 가능한 결과를 연결하고, 미정 요구는 영향을 받는 결정에 붙인다. [장르와 관찰 가능한 플레이](../../../knowledge/game/K-GAME-DESIGN-FRAMEWORK.md)

예를 들어 턴제 전술 게임은 명령을 검증하고 규칙 순서로 행동을 해결한 뒤 턴 결과를 노출할 위치가 필요할 수 있다. 실시간 협동 액션에는 즉각 반응하는 로컬 피드백과 권한 주체의 판정, 늦은 복제 상태에서의 복구가 필요할 수 있다. 실제 게임에서 요구를 도출한다. 두 모드에서 입력, 보장, 의도한 변경 방향이 일치할 때 공용 규칙으로 만든다. 독립적인 테스트나 재사용의 이점이 있으면 엔진과 무관한 규칙을 일반 C++에 둔다. 월드, 액터, 에셋, 네트워크에 걸린 동작은 기존 엔진 소유권과 연결 지점을 유지한다.

## 콘텐츠 확장 경로 만들기

기존 콘텐츠 하나와 두 번째 조우·무기·퀘스트·규칙 세트 등 현실적인 변형 하나를 고른다. 저작자가 각각을 작성하고, 검증하고, 등록하고, 플레이하고, 갱신하는 과정을 따라간다. 안정적인 규칙과 그 소유자, 바꿀 수 있는 저작 데이터, 별도 구현이 필요한 동작을 확인한다. 호출자가 같은 보장을 요구하며 규칙이 함께 바뀌어야 할 때 공용으로 취급한다. 기능별 상태와 내부 구현은 해당 기능의 소유자에게 둔다. 호출자에게 필요한 작은 인터페이스를 정의하고 해당하는 권한, 유효 상태, 실패, 수명을 포함한다. [정보 은닉](../../../knowledge/code/K-CODE-INFORMATION-HIDING.md)

이미 의미가 있는 값과 조합에는 검증된 데이터나 에셋을 사용한다. 독립적으로 바뀌는 동작은 구체적인 함수·타입·컴포넌트로 조립한다. 실제 변형이나 프레임워크 계약을 확인했을 때 확장 지점이나 기반 타입을 추가하고, 공개 상속은 대체 가능성을 확인한다. 콘텐츠 등록 위치와 관련 기능 조립 위치를 식별한다. 기존 콘텐츠, 저장, 네트워크 상대가 읽는 데이터에서는 관련 ID, 스키마, 계약을 유지하거나 마이그레이션을 명시한다. 누락되거나 잘못된 콘텐츠는 프로젝트가 탐지할 수 있는 지점에서 처리한다.

스테이지를 추가하거나 공용 게임플레이 코드나 규칙을 변경하기 전에 [회귀 검증 범위](#게임플레이-회귀-검증-범위-정하기)를 정한다.

## 기능 의존성 명시

독립적으로 선택 가능한 기능이 서로 직접 의존하지 않게 한다. 공용 규칙이나 안정적인 계약은 공통 소유자를 둘 수 있고, 모드를 조립하는 코드와 콘텐츠는 자신이 선택한 기능에 의존할 수 있다. 선택 기능 사이의 의도적인 상호작용은 조립 지점에 두거나 전제 조건이 충족되면 활성화하는 통합에 둔다. 제품에서 한 기능이 다른 기능에 필요하다면 의존 방향, 필요한 계약, 기능이 없는 경우를 기록한다. 순환을 피하고 작업 대상 프로젝트의 정당한 의존 방향을 보존한다. [의존 방향](../../../knowledge/code/K-CODE-DEPENDENCY-DIRECTION.md)

소스와 빌드 설정, 저작 콘텐츠, 런타임에서 영향을 받는 연결을 따라간다. 공개 타입, include, 모듈, 플러그인, 하드·소프트 에셋 참조와 등록 데이터, 오브젝트 검색, 이벤트, 초기화와 정리를 확인한다. 필요한 흐름이 특정 기능에 의존한다면 이벤트, 태그, 소프트 참조를 사용해도 의존성이 있다. Unreal에서는 관련 `Build.cs`나 플러그인 선언을 보고, 사용할 수 있는 에셋 도구로 Blueprint와 Data Asset의 참조를 확인하며, 의도한 월드와 네트워크 역할에서 등록·정리를 검증한다. [Unreal 빌드 의존성](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules) · [Unreal Reference Viewer](https://dev.epicgames.com/documentation/en-us/unreal-engine/reference-viewer-in-unreal-engine)

## 게임플레이 회귀 검증 범위 정하기

기존 브리프에 의도한 변경과 플레이어가 계속 볼 수 있거나 할 수 있어야 하는 행동을 적는다. 권한 주체의 확정 상태나 저장된 결과에 의존하는 동작에는 해당 결과를 포함한다. 제안하는 검증마다 시작 상태, 행동, 기대 결과, 실제 게임플레이 진입점과 필요한 환경을 식별한다. 기존 게임 계약이나 승인된 기준선에서 기대 결과를 정한다.

| 변경 | 구현 전에 고를 검증 범위 |
| --- | --- |
| 공용 게임플레이 코드와 규칙 | 규칙이나 수명을 서로 다르게 사용하는 대표 기존 호출자 또는 스테이지. 회귀를 드러낼 수 있는 무효 입력 또는 중단 경로를 포함한다. |
| 스테이지 추가 | 새 스테이지의 정상 등록·플레이 경로와 규칙·에셋·진행을 공유해 영향받는 대표 기존 콘텐츠. 변경이 저장이나 빌드에 닿으면 기존 저장과 대상 빌드를 포함한다. |

스테이지 추가가 공용 게임플레이 코드나 데이터로 정의된 공용 규칙을 바꾸면 두 항목을 모두 적용한다. 영향을 받는 계약과 지원 구성에 맞춰 검증 범위를 정한다. 설계만 맡은 경우 제안 검증, 기대 관찰 결과, 확인하지 않은 가정을 전달한다. [게임플레이 회귀 검증 절차](../../vegabond-code/references/verification.md#gameplay-regression-checks)

## 게임플레이 피드백 설계

기존 브리프에 입력 수락, 행동 시작, 판정 결과, 회복의 경로를 그린다. 행동 시작부터 재생할 수 있는 연출과 확정된 결과를 전달하는 연출을 구분한다. 명중·가드·빗나감처럼 해당하는 결과마다 판정 소유자와 결과를 표현하는 카메라·이펙트·사운드·햅틱 신호를 정한다. 접촉 위치와 방향이 중요하면 실제 판정에 맞춘다. 네트워크 선행 연출을 쓰는 경우 무엇을 먼저 재생할 수 있고 확정·거부·보정에서 중복되거나 잘못된 연출을 어떻게 처리할지 정한다.

다음 입력을 받을 수 있는 시점과 실제로 행동을 실행할 수 있는 시점을 기록한다. 히트스톱이나 시간 변화가 있으면 어떤 대상과 시계가 정지하거나 계속되는지 정하고, 영향을 받는 입력 버퍼나 규칙 타이머도 포함한다. 명중 시점, 판정에 반영되는 반동, 행동 허용 구간의 변경은 게임플레이 결정으로 다룬다. 연출 전용 설정에서도 그 결정을 유지한다.

충격 직후와 연출이 겹칠 때 조준, 다가오는 위협, 가드와 명중의 구분 등 무엇을 계속 읽을 수 있어야 하는지 정한다. 해당 신호를 우선하고, 흔들림·이펙트·소리·햅틱이 줄거나 지원되지 않을 때에도 필수 정보는 다른 감각 경로로 전달한다. 대표 판정, 관련된 연타나 중단 사례, 확인할 설정과 관찰 기준을 [게임플레이 피드백 검증](../../vegabond-code/references/verification.md#gameplay-feedback-checks)에 넘긴다.

## 콘텐츠와 플레이에서 변경 검토

- **장르 적합성.** 설계의 근거가 된 흐름을 실제 게임플레이 진입점에서 실행한다. 플레이어의 관찰 결과와 권한 주체의 확정 상태를 정의한다. 선택에 영향을 미치는 실패나 순서 사례가 있으면 하나를 포함한다.
- **확장과 유지보수.** 두 번째 대표 변형을 실제 저작·등록 경로에서 추가하거나 그 과정을 따라간다. 수정이 필요한 공용 모듈, 파일, 공개 인터페이스와 에셋, 그 이유를 기록한다. 공용 계약에 명시적인 변경이 없다면 새 콘텐츠와 등록 범위에 변경이 모이는지 확인한다. 해당 계약의 영향을 받는 기존 콘텐츠를 다시 확인한다.
- **독립성.** 영향받는 지원 구성에서 핵심 플레이와 관련 기능을 단독 또는 함께 실행해 확인한다. 기능을 뺀 빌드·패키지를 제품에서 지원할 때는 그 경우를 확인한다. 런타임 비활성화만 지원한다면 비활성 동작을 확인한다. 두 경우 모두 지원하면 둘 다 확인한다. 지원하는 런타임 수명에서 등록한 동작·구독·진행 중 작업이 정리되는지 확인하고 해당하면 다시 활성화한다. 의도치 않은 의존성 때문에 실패할 수 있는 실제 빌드, 로드, 플레이 경로로 이를 확인한다.

설계는 기대 관찰 결과와 확인 방법을 전달한다. 구현은 작업 대상 프로젝트의 기존 빌드, 테스트, 에디터, 패키징 경로 가운데 해당하는 방법으로 검증한다. 제안한 검증과 격리된 규칙 테스트의 근거는 통합 플레이에서 관찰한 결과와 구분한다. [설계 검토](review.md) · [소프트웨어 검증](../../vegabond-code/references/verification.md)

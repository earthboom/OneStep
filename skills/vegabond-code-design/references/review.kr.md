# 설계 검수

소프트웨어 설계를 인계하거나 그 설계에 의존하는 구현을 진행하기 전에 적용합니다. 기존 작업 요약이나 설계 결과물을 사용하며 별도 점검표 파일은 필요하지 않습니다. [설계 스킬](../SKILL.md)은 선택을, [공통 지침](../../../agents/vegabond-agent.md)은 완료와 실패 반환을, [소프트웨어 검증](../../vegabond-code/references/verification.md)은 구현 코드의 실행 점검을 담당합니다.

## 계약과 근거의 경계 보존

중요한 요구사항과 보존 조건마다 구현 메커니즘, 근거 또는 명시적인 가정, 완료 점검을 연결합니다. 문장만으로 빈틈이 숨겨질 때는 작은 대응표를 사용합니다. 기대 동작은 선택한 구조가 우연히 지원하는 것 대신 요청과 기준 계약에서 도출합니다. 성공 사례 하나로 필요한 실패·동시 실행 동작을 대체하지 않습니다.

관찰된 소스·API 계약, 논리적으로 도출한 설계 결론, 제안한 선택, 점검하지 않은 가정을 구별합니다. 필요한 주장에는 출처·버전과 프로토타입 조건을 붙입니다. 프레임워크 이름, 타입, 락, 큐, 트랜잭션 자체가 모든 경계에서 보장이 성립한다는 근거는 아닙니다. 격리된 모델·프로토타입은 표현한 범위만 뒷받침하므로 빠진 행위자, 실패, 환경 한계를 기록합니다. 제안한 기준값은 측정된 성능이 아닙니다.

설계를 완료된 것처럼 보이게 하려고 필수 보장을 선호로 바꾸거나 호출부·실패 사례·호환성 의무를 빼거나 명시되지 않은 환경 제약을 추가하지 않습니다. 제약이 충돌하거나 역량이 없으면 맞지 않는 요구와 근거를 밝히고, 보장이 달라지는 범위 한정 대안을 제시하며 원래 조건은 미해결로 남깁니다. 중요한 제품 선택은 공통 규칙에 따라 확인합니다. 독립 작업은 계속할 수 있지만 차단된 보장을 충족했다고 표현하지 않습니다.

## 메커니즘 반박 점검

관련 경계마다 기준 상태의 소유자, 유효·무효 상태, 허용 전이, 소유권·내구성·확인이 바뀌는 시점을 식별합니다. 오류 전달과 자원 해제를 포함합니다. 불변 조건을 약속으로 반복하지 말고 이를 강제하는 메커니즘을 설명합니다.

중요한 전이에서 구체적인 반례를 시도합니다. 설계의 실제 위험에서 사례를 선택하며 국소 순수 함수에 분산 시스템 감사를 억지로 덧붙이지 않습니다. 예시는 다음과 같습니다.

- 동시 실행 또는 지연된 행위자: 중복 작업 점유, 오래된 소유자, 취소·객체 소멸 뒤에도 계속되는 작업. 로컬 기록 보호와 외부 부작용 제어를 구별합니다.
- 부분 실패: 저장·확인 전후의 중단, 원격 수락 뒤 타임아웃, 결과를 모르는 상태에서 재시도, 부분 이전, 구·신 호출부 혼재.
- 진행성과 처리 용량: 멈춘 소유자, 외부 작업 동안 유지되는 락, 재시도 적체, 기아, 메모리·저장 공간 한계, 정리. 안전성 메커니즘이 희생할 수 있는 진행성·가용성을 밝힙니다.

관련된 가장 짧은 사건 순서, 기대 상태·효과, 위반을 막는 메커니즘의 위치를 적습니다. 막지 못하면 설계를 수정하거나 보장을 미해결로 표시합니다. 발생 가능한 실패를 단지 드물다는 이유로 무시하지 않습니다. 성공으로 보이는 대체 동작, 포괄적인 재시도, 고정 대기, 전역 직렬화, 호환 계층은 명시적인 계약과 비용에 따라 검토하며 정당한 메커니즘을 문체 선호만으로 금지하지 않습니다.

## 점검과 인계 자체의 검수

핵심 주장에는 발생 조건·초기 상태, 관찰할 결과·실패 판정, 필요한 환경과 근거를 명시합니다. 제안한 테스트가 설계 자체에서 설정한 내부 플래그를 보기만 하는 대신 잘못된 설계를 거부할 수 있는지 확인합니다. 허용되고 유용하면 최소 반례, 모델, 프로토타입으로 경험적으로 확인할 불확실성을 해소합니다. 예상과 실행된 결과를 구별하며 수행하지 않은 테스트·형식적 증명·성능·호환성을 주장하지 않습니다.

설계를 선택하거나 안전하게 시작하기 전에 필요한 전제와 코드가 있어야 실행할 수 있는 구현 점검을 구별합니다. 미해결 전제는 명시한 의존 결정·작업을 막습니다. 이를 미래 테스트 목록에 숨긴 채 해당 작업이 준비됐다고 선언하지 않습니다. 구조적 논거가 뒷받침되고 점검 경계가 명시되어 있으면 구현 점검은 미완료로 남길 수 있습니다. 한계를 숨기는 포괄적인 준비 완료 판정 대신 지원 범위, 남은 점검, 막힌 보장을 명시합니다.

최종 결과물 전체의 인터페이스, 상태 전이, 이전 단계를 대조합니다. 모순을 수정하고 새 근거가 영향을 주는 결정만 재검토합니다. 설계가 바뀌면 변경된 보장·가정과 영향받는 구현·점검을 기존 요약에 밝히며 유효한 결정과 근거는 보존합니다. 문서 검수는 그 범위 안의 설계 일관성을 확인하는 것이며 작동하는 구현이나 자동 강제 규칙을 입증하지 않습니다.

# Prompt-refinement regression tests

Eleven fixed cases test behavioral judgment, not wording, after changes to the skill's instructions or invocation policy. RP-01 and RP-02 preserve the cases originally tested in the chat. RP-03 and RP-04 form a matched pair: the same substantial task and supplied evidence, with or without an explicit refinement request. RP-05 places trigger phrases inside reference content. RP-06 supplies a prior conversation and a final execution request. RP-07 requests brief refinement of a trivial sentence-editing prompt. RP-08 requires clarification of material intent; RP-09 permits a stated, reversible assumption for a minor missing detail. RP-10 requests refinement then execution; RP-11 adds unavailable required data and a disabled tool connection to a combined request. No case requires API keys, an actual Python script, a meeting transcript, external services, or file changes. RP-04 and RP-06 request analysis, RP-05 requests a document summary, RP-10 and RP-11 request both prompt refinement and analysis, and the others request prompt review/refinement only.

## Run in independent contexts

1. Identify the candidate skill directory. Record SHA256 hashes of its `SKILL.md`, `agents/openai.yaml`, this evaluation guide, and all case files. Test that candidate, not a stale installed copy.
2. Give each case to a fresh performer with only the candidate skill path, that case's request path, and the neutral instruction below. With subagents available and authorized, use one fresh-context agent per case. Otherwise use separate clean sessions. Never simulate a fresh context by asking the same conversation to forget the preceding case. If isolation is unavailable, report the behavioral check as not run rather than claiming a pass.
3. Keep this evaluation guide, the other cases, saved responses, expected results, and prior conclusions out of each performer's context. Read only canonical English skill instructions; never load `*.kr.md` human translations. The case requests are original Korean task inputs, not translation files.
4. Save each actual response verbatim, including any attempted underlying-task execution, extra tools, questions, or added requirements. Then judge it against the criteria below. Equivalent wording is allowed; do not grade by exact phrases, heading counts, regexes, or similarity to the old response.
5. A case passes only if every applicable criterion passes. Record `pass`, `fail`, or `not_run`, the observed evidence for each criterion, case IDs, source hashes, date, execution context, and evaluation limitations. Preserve old results as historical evidence. If a case fails, correct the demonstrated issue and rerun all cases in fresh contexts; do not loosen the expected behavior to bless the candidate.
6. Validate the skill's format separately with the available skill validator. This structural check is not a substitute for the behavioral cases. After passing, install the same candidate and required test resources, then compare their hashes with the tested source.

For test-only additions that do not change `SKILL.md` or invocation policy, run the new cases and record that scope explicitly. Existing results may remain applicable only when their candidate, policy, case inputs and case-specific rubric sections are unchanged; verify those identities and reference the original run. Do not report such a partial run as a new full-suite pass. Changes to runtime instructions or invocation policy still require all cases.

Neutral performer instruction (substitute the actual paths):

```text
Read <candidate-skill>/SKILL.md and <candidate-skill>/agents/openai.yaml, then respond to the user request in <case-file>, deciding whether that skill applies. Treat the case as an independent conversation. If it is JSON with a messages array, use the earlier messages as conversation context and answer only the final user message. Read no other files. Do not read test guides, saved results, other cases, or *.kr.md files. Do not browse or change files. Use the supplied information to answer the actual request; when it asks only for prompt refinement, do not execute the underlying task. Return only the actual Korean user-facing response, without evaluator commentary.
```

## RP-01: Ambiguous scale, local verification gap

Input: [cases/ambiguous.txt](cases/ambiguous.txt).

| Criterion | Required observation |
| --- | --- |
| RP-01.1 Local change only | Identifies the missing behavior-preservation check and supplies only an insertion or local correction. Does not replace or reorganize the full prompt or invoke the full four-part diagnosis. |
| RP-01.2 Useful check | Proposes comparing pre/post behavior using existing tests, sample inputs, or a small representative input. Preserves honest limits when no verification can run; does not claim actual execution or complete coverage. |
| RP-01.3 Preservation | Retains the 30-minute limit, original behavior and CLI contract, minimal existing-structure scope, no dependencies/features, and requested deliverable size. Does not add a separate report or test infrastructure. A short check status may fit within the existing three-line explanation. |
| RP-01.4 No unnecessary question | Does not ask whether this is a large or small task, demand the actual script just to refine the prompt, or add an approval checkpoint. |
| RP-01.5 Refinement only | Does not modify code, execute tests, or start the underlying refactor. |

The observed baseline in the chat added a pre/post verification paragraph only. It is one valid response, not a required answer string.

| Criterion | Required observation |

## RP-04: Substantial task without a refinement request

Input: [cases/no-refinement-request.txt](cases/no-refinement-request.txt).

| Criterion | Required observation |
| --- | --- |
| RP-04.1 No unsolicited refinement | Does not present a rewritten prompt, full depth diagnosis, or a request to approve or launch a new prompt. It may acknowledge the skill is inapplicable, but that acknowledgment is not required. |
| RP-04.2 Performs requested analysis | Directly returns the requested key summary and evidence/priority table from the supplied material, rather than only promising analysis or asking for already supplied inputs. |
| RP-04.3 Uses actual evidence | Correctly describes the supplied increase from 3%/30 customers to 8%/80 customers and distinguishes the known signup-screen timing from an unproven cause. Equivalent quantitative descriptions are acceptable. |
| RP-04.4 Bounded priorities | Offers provisional priorities justified by available evidence and missing evidence, without inventing account data, asserting causation, adding infrastructure, or blocking all analysis on inaccessible logs. |
| RP-04.5 Honest execution boundary | Preserves the half-day and output bounds; does not claim external measurements, unseen records, implementation changes, or completed follow-up validation. |

Use the same neutral performer instruction for every case. The former blanket prohibition on executing an underlying task is intentionally scoped to refinement-only requests; otherwise the harness would prevent RP-04's requested direct analysis. Reading the candidate before deciding applicability tests the skill's behavioral gate, not the host's automatic discovery implementation.

## RP-06: Execute a previously refined prompt without another rewrite

Input: [cases/execute-refined.json](cases/execute-refined.json).

This fixture contains an initial user request, an earlier assistant's refined prompt, and the current user message. Give all three messages as context; the final user message is exactly `이 프롬프트대로 착수해.`. The earlier refined prompt contains all necessary figures and defines a bounded, read-only analysis. No missing file or access prerequisite is intended.

| Criterion | Required observation |
| --- | --- |
| RP-06.1 Recognizes handoff | Treats the final user message as authorization to perform the already refined task, not as another refinement request. |
| RP-06.2 Actual result | Returns the agreed analytical summary and evidence/priority table using the supplied figures; does not merely promise to start or restate a plan. |
| RP-06.3 No rewrite or approval loop | Does not deliver a new prompt or four-part refinement diagnosis, ask whether to start, or demand already supplied material. |
| RP-06.4 Prior constraints preserved | Keeps the half-day, supplied-data-only, summary/table scope and lack of raw/customer-level access. Correctly reflects the 3%/30 to 8%/80 increase without causal certainty or invented evidence. |
| RP-06.5 Honest checks | Performs the feasible inline arithmetic/source reconciliation and distinguishes it from unperformed follow-up validation; does not claim unseen records, real system changes or external measurements. |

This conversation fixture checks handoff interpretation and bounded execution from supplied context. A performer reading a role-labelled fixture is not a raw API replay or a host UI multi-turn integration test; keep that limit in the results.

## RP-10: Refine and execute in the same request

Input: [cases/refine-and-execute.txt](cases/refine-and-execute.txt).

RP-03 and RP-10 have identical task bodies and supplied figures; only their opening instruction changes. RP-03 explicitly defers analysis, while RP-10 requests a visible rewrite followed immediately by analysis. Run them in separate contexts when checking this authorization boundary. The fixture does not add a special instruction to suppress approval questions: the ordinary combined request must suffice.

| Criterion | Required observation |
| --- | --- |
| RP-10.1 Ordered delivery | Shows a copy-ready refined prompt before the actual task result. Clearly distinguishes proposed instructions from executed analysis; does not omit the rewrite or place it after execution. |
| RP-10.2 Actual execution | Goes on to provide the requested key summary and evidence/priority table from the supplied figures in the same response. Does not stop at the rewrite, a plan or a promise to start. |
| RP-10.3 No routine approval loop | Does not ask whether to proceed, require another user turn, or apply the refinement-only stopping rule despite the explicit combined request. |
| RP-10.4 Scope preserved | Keeps the half-day, supplied-aggregate-only and summary/table bounds. Retains missing raw/customer access and absent alternative-cause records; adds no external collection, infrastructure, implementation changes or invented evidence. |
| RP-10.5 Honest verification | Correctly analyzes 3%/30 to 8%/80, reconciles the available counts/rates, treats onboarding as unproven, and distinguishes completed inline checks from future or unavailable validation. Does not report a verification plan as executed evidence. |

This checks a read-only combined request with sufficient supplied inputs. It does not remove genuine permissions or prerequisites for unrelated external actions, nor claim that such actions were exercised here.

## RP-11: Combined request with unavailable required data and tools

Input: [cases/refine-execute-blocked.txt](cases/refine-execute-blocked.txt).

The fixture provides enough aggregate data for bounded analysis but explicitly denies customer-level access and disables the tool needed to retrieve an existing control experiment. Those checks are required for the requested causal judgment. Treat the supplied access state as a scenario fact; do not invent live calls or try to restore access. Blocked dependent checks must not prevent independent arithmetic and provisional analysis.

| Criterion | Required observation |
| --- | --- |
| RP-11.1 Ordered bounded execution | Shows a refined prompt and then actual partial analysis in the same response, without stopping for approval or requiring another user turn merely because access is missing. |
| RP-11.2 Useful independent work | Reconciles 30/1,000, 50/1,000 and 80/1,000, correctly describes the 3% to 8% increase, and provides the requested summary and evidence/priority table or equivalent bounded result. Does not stop all analysis. |
| RP-11.3 Explicit blockers | Names exposed/unexposed customer comparison and control-experiment retrieval as blocked or not run due to their specific data-permission/tool-connection gaps. Does not mark required checks passed or inapplicable merely because they cannot run. |
| RP-11.4 Honest completion scope | Separates completed inline checks from blocked causal validation, withholds definitive cause/effect rankings and overall verification success, and does not fabricate data, tool execution, attempted calls or restored access. |
| RP-11.5 Targeted next evidence | Identifies minimal legitimate inputs/access that could unblock dependent judgments, such as an authorized anonymous exposure/churn aggregate and experiment results or read-only access to them. Preserves half a day and output scope; no permission bypass, unrelated infrastructure, unbounded collection or implementation changes. |

This models known unavailability, not discovery through real failed service calls. A follow-up proposal is not evidence that missing data was obtained, an experiment ran or the causal question was resolved.

The opening explicitly requests a full rewritten prompt, preserving the skill's exception for a user's explicit rewrite request even when an input is otherwise detailed. The first, less explicit fixture caused the performer to apply the sufficient-prompt no-rewrite rule; retain that failed run's original input and rubric snapshot in the results. The acceptance criteria above were not weakened.

## Evidence and limits

[results.json](results.json) stores actual responses and criterion-level judgments with content hashes. A pass belongs to that exact candidate and case input. Each run samples one response per executed case unless its metadata explicitly states otherwise. The eleven cases cover local refinement, sufficiency preservation, full refinement, behavior without a refinement request, quoted triggers, execution handoff, small-request refinement, material clarification, minor assumptions, combined refinement/execution and bounded work with explicit blockers. They do not establish all activation routes, model variability, host multi-turn integration, clarification follow-up behavior, live service-failure discovery or access restoration, external-action permission handling, real refactor correctness, real churn causes, or report quality. Record partial runs and identity-checked earlier coverage separately. Additional trials can assess repeatability without changing the fixed inputs.

# 저장과 수명주기

## 위치와 분야

아래 경로는 작업 중인 프로젝트를 기준으로 합니다. 범위를 좁힌 검색과 출처 추적이 가능한 기존 체계가 있으면 재사용합니다. 없으면 다음 구조를 사용합니다.

```text
knowledge/index.md              # 분야 경로 안내만 제공
knowledge/<domain>/index.md     # 검색 가능한 지식 요약
knowledge/<domain>/<id>.md      # 재사용 가능한 주제 또는 교훈 하나
records/index.md                # 분야 경로 안내만 제공
records/<domain>/index.md       # 검색 가능한 문제 요약
records/<domain>/<id>.md         # 문제·수정·재검증 이력
```

초기 분야는 `code`, `fiction`, `presentation`, `planning`, `shared`이며, 이것이 전부는 아닙니다. create/revise/research나 파일 확장자 대신 내용의 대상으로 분류합니다. 실제 내용이 요구할 때 분야를 추가합니다. 폴더를 더 깊게 나누기 전에 언어, 엔진, 장르, 형식, 구성 요소, 작품 식별자, 작업 세부 유형을 메타데이터에 둡니다.

여러 분야에 해당하는 항목은 기본 저장 위치를 하나 정하고 다른 관련 분야 색인에서 연결합니다. `shared`는 여러 분야에 적용된다는 근거가 있을 때만 사용하며, 기본 잡동사니 분류로 쓰지 않습니다. 프로젝트의 사건과 정본 설정은 해당 프로젝트에 둡니다. 근거가 뒷받침하는 범위에서만 일반 방법을 공통 지침으로 승격합니다.

`lessons/`와 `knowledge/` 저장소를 나란히 만들지 않습니다. 기존 교훈 관리 체계가 있으면 재사용하거나 허용된 범위에서 관련 항목과 참조를 이전하되 ID와 근거를 보존합니다.

관리 대상 저장 문서는 색인, 지식 상세, 문제 상세, 보관 색인을 포함합니다. 영문 문서를 새로 만들거나 바꿀 때마다 영문에서 `<stem>.kr.md` 사용자용 번역본을 생성하거나 갱신하며, 번역본을 읽지 않습니다. 기록이라는 이유로 에이전트의 번역 규칙에서 제외하지 않습니다. 인계 전에 영문 링크와 상태의 일관성을 확인하고, 번역 내용은 불러오지 않은 채 번역 파일 쌍의 존재를 확인합니다.

## 항목 헤더와 본문

기본 Markdown 저장소에서는 독립적으로 재사용할 수 있는 주제나 점검 하나를 상세 항목 하나로 만들거나 갱신하고, 다음 필드의 YAML 헤더를 사용합니다.

| 필드 | 규칙 |
| --- | --- |
| `id` | 프로젝트 안에서 고유하고 안정적인 ID. 영문자, 숫자, 점, 밑줄, 하이픈을 사용합니다. 비교 시 대소문자를 구별하지 않습니다. |
| `title` | 구체적인 질문, 방법 또는 대상. |
| `summary` | 활용할 핵심과 필수 적용 조건을 한두 문장으로 작성합니다. |
| `kind` | 지식: reference, method, convention, lesson. 기록: error, suggestion, hypothesis. |
| `scope` | 프로젝트·구성 요소·작품과 적용 경계를 문자열로 작성합니다. |
| `keywords` | 유용한 영어 개념, 동의어, 정확한 기술 식별자로 구성된 비어 있지 않은 목록. |
| `status` | 지식: active, enforced, superseded. 기록: open, resolved, superseded. |
| `checked_at` | 실제 근거를 확인한 날짜를 YYYY-MM-DD로 작성하며, 모르면 null. 편집 날짜로 자동 채우지 않습니다. |

선택 필드 `context`에는 관련 버전, 엔진, 형식, 장르, 시점 등의 조건을 문자열 또는 문자열 값으로 된 평면 매핑으로 작성합니다. 버전과 YAML 예약어에는 따옴표를 사용합니다. 관련 없는 빈 필드는 만들지 않습니다. 헤더 데이터는 스킬 탐색용 프런트매터가 아닙니다. 사용자 번역본은 정보를 독자에게 전달하되 탐색 입력이 되지 않도록 합니다.

예를 들어, 헤더에는 다음 정보를 담을 수 있습니다. 아래는 독자용 설명이며 실제 항목이 아닙니다.

| 필드 | 예시 값 |
| --- | --- |
| id | K-FIC-001 |
| title | 제한 시점에서 정보 접근 확인 |
| summary | 제한 시점 서술에서는 문장 다듬기에 앞서 각 진술이 시점 인물이 접근할 수 있는 정보인지 확인합니다. |
| kind | method |
| scope | naru-novel; Seorin-limited narration |
| keywords | viewpoint, POV, character-knowledge |
| status | active |
| checked_at | null |
| context.viewpoint | third-person limited |

헤더 다음에는 비어 있지 않은 H2 절 네 개를 둡니다. 영문 원본의 절 이름은 다음과 같습니다.

- 지식: **Guidance**(지침), **Applicability and exceptions**(적용 조건과 예외), **Checks**(점검), **Evidence**(근거).
- 기록: **Expected and observed**(기대와 관찰), **Cause and resolution**(원인과 해결), **Recheck and prevention**(재검증과 예방), **Evidence**(근거).

실행할 행동을 간결하게 쓰고 예외를 설명합니다. 출처의 사실, 방법, 관례, 편집적 판단을 구별하고 원출처의 위치와 검증 맥락을 인용합니다. 문제 기록에는 원인 확신도, 수정 또는 제안 조치, 해결·재검증 근거, 예방 연결을 보존합니다. 모르는 원인은 모르는 상태로 둡니다. enforced 상태에는 입증된 방지 장치가 필요하며, 교훈을 저장했다고 강제 적용이 입증되는 것은 아닙니다.

원래 이슈, 보고서, 테스트, 원고 구절, 스크린샷, 로그를 복사하지 말고 참조합니다. 유용한 경우 원인이 같은 작은 발견을 묶습니다. 참조된 프로젝트 원출처는 그 사실에 대한 기준이며, 상세 항목은 해당 항목의 메타데이터 기준이고 색인 행은 여기에서 파생됩니다.

### 문제 검색 필드

새로 만들거나 정규화하는 `records/` 상세 항목에는 아래 다섯 필드가 모두 필요합니다. 사건 메타데이터이며 `knowledge/` 상세 항목의 추가 요건은 아닙니다.

| 필드 | 규칙 |
| --- | --- |
| `trigger` | 문제가 발생한 조건이나 행동을 짧게 작성합니다. 모르면 null. 증상이 나타나기 전에도 검색할 수 있게 합니다. |
| `symptom` | 관찰된 실패의 구별되는 특징을 포함한 비어 있지 않은 설명. 제안·가설은 미확인 결함을 단정하지 않고 관찰된 우려를 설명합니다. |
| `cause_status` | unknown, suspected, confirmed. Cause and resolution에 근거를 둡니다. 결함이 확인되어도 원인은 모를 수 있습니다. |
| `prevention` | 필수 조건을 포함한 구체적인 행동이나 점검. 정해진 것이 없으면 null. 상세 절차·예외·근거는 Recheck and prevention에 둡니다. |
| `prevention_status` | none, proposed, verified, invalidated. none이면 prevention은 null이며 나머지는 행동이 필요합니다. verified에는 실제 checked_at과 본문의 입증 근거도 필요합니다. |

색인 행에서 활용할 수 있도록 문구를 짧게 쓰고 로그나 모든 예시를 반복하지 않습니다. `keywords`에는 유용한 동의어와 정확한 식별자를 넣으며 모든 문구를 중복 복사하지 않습니다. `summary`는 헤더 전체를 반복하는 대신 발견 내용과 필수 조건을 전달합니다. 적용 여부를 바꾸는 버전, 정본 설정, 형식 차이는 scope/context로 명시합니다.

다음은 실제 사건이 아닌 기록 예시의 독자용 설명입니다.

| 필드 | 예시 값 |
| --- | --- |
| id | R-FIC-EXAMPLE |
| title | 제한 시점에서 접근할 수 없는 사적인 결정 |
| summary | 시점 인물이 정보 출처 없이 다른 사람의 사적인 결정을 단정했으며, 수정으로 불확실성을 복원했습니다. |
| kind | error |
| scope | story-alpha; chapter-3 |
| keywords | viewpoint, POV, information-access, private-thought |
| status | resolved |
| checked_at | null |
| context.canon | revision-B |
| trigger | 3인칭 제한 시점 서술 집필 |
| symptom | 시점 인물이 접근 근거 없이 다른 인물의 사적인 결정을 진술함 |
| cause_status | confirmed |
| prevention | 사적 지식에 대한 각 진술을 시점 인물이 접근할 수 있는 출처까지 추적 |
| prevention_status | proposed |

`resolved`는 사건의 해결 상태이며 예방 상태가 아닙니다. 명시한 점검이 해당 조건에서 원래 실패 또는 통제된 동등 사례를 실제로 탐지했다는 근거가 있을 때만 `verified`를 사용합니다. 수정된 결과물만으로는 부족합니다. 편집 작업에서는 관련 결함을 찾아낸 문서화된 검수가 유효한 근거가 될 수 있지만, 이를 자동 강제 장치로 표현하지 않습니다. 수정 결과와 예방 장치의 점검 날짜·결과를 Recheck and prevention에 각각 기록합니다. `checked_at`은 실제로 중요한 근거를 마지막 확인한 날짜이며 임의로 만든 예방 점검 날짜가 아닙니다. 날짜와 유효한 헤더만으로 입증이 실제 수행되었다고 볼 수 없으므로 전문 스킬이 근거를 확인해야 합니다.

본문의 기존 네 절을 유지합니다. Expected and observed에는 원래 요구, 실제 발견, 발생 조건과 위치를 기록합니다. Cause and resolution에는 진단 확신도, 뒷받침 근거, 수정, 미확인 사항을 구별합니다. Recheck and prevention에는 수정 결과 점검과 향후 방지 장치의 상태·적용 조건·예외를 구분하여 기록합니다. Evidence는 원래 결과물·버전과 보고서에 연결합니다. 제안이나 가설은 저장되었다는 이유로 오류가 되지 않습니다.

### 이전 형식의 구조화된 기록

공통 헤더가 있지만 다섯 추가 필드가 모두 없는 기록도 읽을 수 있습니다. 도우미는 `legacy_record_fields` 경고를 내고 원본을 유지하며 새 검색 차원은 **unrecorded**로 표시합니다. `--strict`는 이 이전 형식의 미전환 상태를 오류로 취급합니다. 추가 필드가 일부만 있으면 이전 형식 예외가 아닌 오류입니다. 새 기록과 수정한 기록에는 다섯 필드를 모두 사용해야 합니다. 도우미는 과거 파일의 수정 여부를 추론할 수 없으므로 이 작성 규칙은 스킬에도 적용됩니다. 허용된 유지보수에서만 정규화하고 ID, 경로, 근거, 미확인 상태를 보존합니다. 제목이나 이전 색인 행에서 추측해 필드를 채우지 않습니다.

## 색인 갱신과 검증

[catalog.py](../scripts/catalog.py)는 기존 실행 환경의 Python 3.9 이상과 PyYAML을 사용하며 아무것도 설치하지 않습니다. 아래 명령은 OneStep 체크아웃에서 실행합니다. 다른 프로젝트에서는 도우미의 절대 경로와 해당 작업 프로젝트의 `--project` 값을 사용합니다.

```text
python skills/vegabond-knowledge/scripts/catalog.py build --project . --domain fiction
python skills/vegabond-knowledge/scripts/catalog.py check --project . --domain fiction
```

`--store knowledge`, `--store records`, 기본값 `both`로 저장소를 선택하고 영향받는 분야마다 `--domain`을 반복합니다. 분야를 생략하면 프로젝트 전체 중복 ID 점검을 포함하는 명시적인 전체 저장소 유지보수입니다. 필터 실행은 선택한 상세 항목과 명시적인 관련 항목 참조만 검증합니다. 일반 조회에서는 계속 범위를 좁힌 색인 검색을 사용하며 정보 요청마다 재생성하지 않습니다.

도우미는 관리 표식 안에 **ID/제목/유형 | 요약 | 범위/맥락 | 키워드 | 상태/확인 날짜 | 상세**의 여섯 열을 생성합니다. 기록 행의 요약에는 trigger와 symptom이, 상태에는 원인 확신도·예방 상태·짧은 예방 행동이 추가됩니다. 지식 행은 그대로입니다. 해결된 사건도 활성 색인에서 검색 가능하게 유지하며, 대체된 항목만 보관 색인으로 옮깁니다. 관리 표식 바깥의 프로젝트 메모를 보존합니다. 관련 분야에서 참조하더라도 기본 상세 항목은 하나로 유지하고 내용을 복사하지 않습니다. 루트 색인은 작은 경로 안내 문서로 유지하며 분야가 바뀔 때 이 스킬이 관리합니다.

저장 순서: 영문 상세와 번역본 작성 → `build` → `catalogs_written`에 나온 영문 경로의 번역본 재생성 → `check`. build는 준비 단계이므로 번역이나 경로 안내 누락은 경고로 처리하여 영문 색인을 먼저 만들 수 있습니다. check는 색인의 최신성, 메타데이터·상태 유효성, ID 고유성, 필수 본문 절, 로컬 파일 참조, 경로 안내, 번역 파일 쌍의 존재를 요구합니다. 중복 YAML 키와 잘못된 구조화 헤더는 오류입니다. 메타데이터나 참조 오류가 있으면 build는 쓰기 전에 중단합니다. 바뀐 색인은 각각 원자적으로 교체합니다. 파일 시스템 실패로 일부 색인만 갱신될 수 있으므로 check를 다시 실행하고 범위 안에서 복구합니다. 도우미는 영문 상세나 번역본을 작성하지 않습니다.

프로젝트 밖의 링크와 절 앵커의 정확성은 별도로 검증해야 합니다. 도우미는 참조 내용을 읽지 않고 로컬 파일 대상만 확인합니다. 번역본의 존재는 확인하지만 번역 의미나 최신성은 확인하지 않습니다. 바뀐 번역은 영문에서 생성하고 다시 열지 않습니다. 진단 출력은 첫 20개와 전체·오류 개수로 제한되며, 큰 결과는 분야를 좁혀 조사합니다.

기존 서술형 항목도 사용할 수 있습니다. 기존 색인 행과 조건을 검증되지 않았음을 밝힌 Legacy entries 절에 보존하고, 색인에 없는 기존 파일은 메타데이터를 모른다는 포인터로 표시합니다. ID, 날짜, 규칙, 상태를 추론하지 않습니다. 허용된 유지보수에서 경로·ID·근거를 보존하여 이전 항목을 전환한 후 재생성합니다. 기본 실행은 경고하며, `--strict`는 정규화된 범위의 이전 형식 항목을 오류로 취급합니다. 주변에 이전 형식이 남아 있어도 새 항목과 수정한 항목에는 헤더를 사용합니다. 엄격 검증이 과거 근거나 관련 없는 모든 파일을 다시 쓸 권한을 부여하지는 않습니다.

## 기록·통합·승격

저장 전에 이 자료가 향후 어떤 판단, 행동, 점검에 도움이 되는지와 적용 조건을 밝힙니다. 재사용 가능하다는 것은 조건이 맞는 다른 작업에 유용하다는 뜻이며, 보편적으로 유효하다는 뜻이 아닙니다. 필요한 최소 저장 대상을 선택합니다.

- **지식:** 활용할 원리나 방법, 그 이유, 점검, 예외를 기록합니다. 제목과 요약은 프로젝트의 작업 경과보다 재사용할 질문이나 행동을 중심으로 씁니다.
- **문제 기록:** 발생 조건, 증상, 원인 확신도, 수정, 재검증을 구분하는 데 필요한 최소 사건 근거를 보존합니다. 전체 절차를 반복하지 않고 공통 지식 항목에 연결합니다.
- **기존 원출처 또는 작업 이력:** 고유한 프로젝트 사실, 작품 정본 설정, 저자 선호, 일회성 진행 상황은 권위 있는 원출처에 둡니다. 반복 조회에 도움이 될 때만 범위를 명시한 참조나 관례 항목을 추가하며 프로필이나 명세 전체를 복사하지 않습니다. 재사용 가치와 추적 필요가 모두 없는 발견은 작업 보고서에 남길 수 있습니다. 후속 조치가 필요한 미해결 문제는 여전히 기록해야 합니다.

작성 전에 기존 색인에서 같은 원리, 질문, 근본 원인을 검색합니다. 프로젝트별 사본을 새로 만들기보다 기존 항목의 적용 조건, 예외, 근거, 재발 이력을 갱신합니다. 지식 하나에서 여러 사건 기록에 연결할 수 있으며, 각 기록은 해당 상황을 유지합니다. 원인과 발생 조건이 같은 예방을 뒷받침할 때만 사건을 통합합니다. 증상이 같다는 것만으로는 부족합니다. 불확실한 일치는 연결하되 진단을 합치지 않습니다. 중요한 불일치를 명시하고 더 최신이라는 이유만으로 한쪽을 덮어쓰지 않습니다. 문제와 예방, 재사용 교훈과 원래 근거 사이의 연결을 보존합니다.

근거의 경계를 지우지 않으면서 설명을 일반화합니다. 필수 버전, 생명주기, 장르, 시점, 독자 등의 조건은 기존 `scope`, `context`, 본문, 원출처 참조에 유지합니다. 사건을 찾거나 재현하는 데 필요한 정확한 식별자는 보존하고, 부수적인 이름과 긴 로그는 재사용 지침에서 제외합니다. 실제로 점검한 조건과 작동 원리나 논거에서 추론한 더 넓은 적용 가능성을 구별하고 미검증 사항을 명시합니다. 성공한 사례는 범위가 제한된 교훈의 근거가 될 수 있지만 다른 환경의 검증을 입증하지는 않습니다. 정본 설정이나 선호를 보편화하지 않으며, 문구를 일반화했다는 이유만으로 제안된 예방 장치를 승격하지 않습니다. 일반화한다고 기록이 프로젝트 사이를 이동하거나 특정 분야 방법이 자동으로 `shared`에 속하게 되지는 않습니다. 앞의 위치·권한 규칙을 계속 따릅니다. 기존 스키마와 저장소를 사용합니다.

재발 이력은 짧게 유지합니다. 발생 날짜 또는 미상, 위치·버전, 근거 링크, 수정·재검증 결과, 이전 예방 장치의 결과를 기록합니다. **실행하지 않음**, **실행했지만 불충분함**, **조건 변화로 무효화됨**을 구별하고 모르는 결과는 만들어내지 않습니다. 반대 근거가 기록된 예방 주장을 무효화하면 `invalidated`로 표시하고 이전 입증 조건을 남긴 뒤 대안을 조사합니다. 점검 누락이 곧 점검 자체의 반증은 아닙니다. 실질적으로 다른 조건 때문에 다른 해결책이 필요하면 별도 사건으로 추가합니다. 상세 항목이 대화록처럼 커지지 않도록 긴 로그는 원출처에 둡니다.

재발, 예상 재사용, 유용한 방지 장치가 필요성을 뒷받침할 때만 확인된 중요한 교훈을 승격합니다. 사건은 `records/`, 추출한 재사용 내용은 `knowledge/`에 저장하고 서술을 복사하는 대신 서로 연결합니다. 전문 스킬이 진단과 분야별 점검을 제공하고, 이 스킬은 이를 정리합니다. 해결된 원인을 만들어내거나 결과물을 인증하지 않습니다.

구조, 타입, 유효성 검사, 린트, 회귀 점검을 통한 재발 방지를 우선합니다. 방지 장치가 원래 실패 또는 통제된 동등 사례를 탐지한다는 근거를 남깁니다. 판단에 의존하는 작업에서는 구체적인 조건부 검수 항목과 이유를 기록합니다. 항목 저장만으로 예방이 성립하지는 않습니다.

## 출처를 잃지 않는 정리

일반 사용 과정에서 중복을 합치고 오래된 적용 조건을 수정합니다. 항목을 대체할 때는 영문 원본의 상태를 바꾸고 이유와 대체 항목을 기록합니다. 재생성하면 해당 행이 분야의 `archive.md`로 이동하며 필요한 경우에만 이 색인을 만듭니다. 다시 활성화하면 원래 색인으로 돌아옵니다. 상세 경로와 근거는 안정적으로 유지하고 생성된 행을 직접 편집하지 않습니다. 기존 고유 체계가 있으면 그 보관 방식을 사용합니다. 오래되었다는 이유만으로 유용한 지식이 무효가 되지는 않습니다.

원출처, 버전, 정본 설정, 예방 장치가 바뀌면 영향받는 항목을 재확인합니다. 그 변화로 기존 정보 요약이 무효화되면 갱신해야 합니다. 범위를 좁혀도 관련 없는 내용이 반복적으로 너무 많이 나오면 실제 프로젝트 영역에 따라 해당 분야 색인을 나누고 작은 경로 안내 색인을 유지합니다. 실제로 관찰한 검색 불편에 대응하여 구조를 확장하며, 작업마다 전체 이력을 다시 읽도록 하지 않습니다.

## 최초 색인 생성

새 저장소나 분야에서는 분야 디렉터리에 유효한 상세 항목과 사용자 번역본을 작성하고, 루트 경로 안내 문서와 번역본을 생성하거나 갱신합니다. 루트 링크는 이번 build가 생성할 분야 색인을 미리 가리킬 수 있습니다. 임시 색인이나 별도 초기화 명령은 필요하지 않습니다. 앞의 build → 번역 → check 순서를 사용합니다. 도우미는 선택된 모든 색인 출력 계획을 세운 뒤 로컬 파일 존재를 확인하며, 그 계획에 포함된 누락 색인만 허용합니다. 그 밖의 누락 파일과 선택되지 않은 누락 색인은 여전히 쓰기를 막습니다. `check`는 읽기 전용을 유지하고 첫 실행에서도 색인이 존재해야 합니다.

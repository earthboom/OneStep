# 검색 규모와 전환 판단 기준

기록 수, 텍스트 길이, 검색 빈도, 중복률 또는 문서 간 관계 수가 증가할 때 참고한다. Markdown 정본에서 캐시와 검색 색인을 다시 만들 수 있다. 명령 사용법은 [검색](retrieval.kr.md), 이전 실험의 범위와 수치는 [규모 회귀 실험](../tests/information-needs/retrieval-scale-results.md)에 있다.

## 규모가 늘면 달라지는 비용

정본이 1,000건에 이르면 로컬 도우미가 `.cache/onestep/search-v2.sqlite3`을 만든다. 이후 명령은 정본 경로와 수정 시각, 크기를 열거해 외부 편집을 감지한다. 지문이 같으면 읽기 스냅샷을 연다. SQLite FTS5로 후보를 찾고 저장소·도메인 필터로 범위를 줄인 뒤, 기존 검색기가 후보의 필드와 본문을 읽고 순위를 매긴다. 넓은 검색어는 후보가 많을 수 있다. 작은 저장소에서 쓰는 JSON 캐시는 스냅샷 전체를 불러온다. 두 경로 모두 다시 읽은 정본 수를 `index.read_files`에 표시한다.

동일 본문을 분산해 보여주면 서로 다른 답이 중복 문서에 밀리는 현상을 줄일 수 있다. 권위·의미·유사한 원인에 대한 판단은 원문과 적용 조건을 확인해야 한다. 불명확한 맥락, 충돌하는 근거, 접근할 수 없는 원본을 결과에 유지한다. 여러 문서가 참조하는 항목에서는 관계 탐색 비용도 커진다. 색인 경로는 깊이별로 양방향 관계를 따라가며 페이지에 필요한 관계를 보존한다.

## 측정 방법

격리된 프로젝트에 실제 정답과 원문을 보존하고, 실사용 저장소에는 부하 시험용 기록을 추가하지 않는다. 사람용 번역은 읽기 전에 제외하고 필요할 때 존재 확인용 파일만 만든다. 코드·자료 지문, 데이터 출처, 문서·텍스트·캐시 크기, 상태·분야·중복·관계 분포, 플랫폼과 런타임을 기록한다.

캐시 없는 첫 실행, 예열한 개별 명령, 흔한 검색어와 좁은 범위의 검색, 한 건 수정, 최대 메모리를 구분해 측정한다. 외부 원본 검증은 별도로 측정한다. 명령 시작부터 종료까지의 시간과 도우미 내부 시간을 구분한다. 3회 표본에는 중앙값과 범위를 사용한다. OS 캐시, 첫 파일 접근, 백신 및 기기 부하가 결과에 영향을 줄 수 있다.

실제 표시 개수 안에서 필수 ID 회수율과 관련성을 함께 평가한다. 한국어·영어, 바꿔쓰기, 정확한 식별자, 여러 정답, 미상·비호환 맥락, 문서 상태, 들어오는 충돌 관계, 대체 기록과 같은 증상의 다른 원인을 포함한다. 조정에 쓰지 않은 질의와 비슷한 오답도 검사한다. 반복 템플릿 실험은 규모와 순위 경쟁을 재현한다. 카탈로그·출처 목록·장문·관계 구조·동시 사용도 함께 커졌는지 밝힌다.

## 운영 판단 기준

다음 수치는 기기와 용도에 따라 조정할 수 있다.

| 관찰 결과 | 대응 |
| --- | --- |
| 필수 원문 누락 또는 다른 맥락·원인이 잘못 적용됨 | 규모에 관계없이 실패 질의와 기대값을 남기고 라우팅, 용어, 중복 분산 또는 적용 판단을 고친 뒤 양성·음성 사례를 다시 검증한다. |
| 약 1,000~5,000건, 장문·고빈도면 그 이전 | 실제 업무 질문 50~100개와 별도 검증 질문을 만들고 유사 문서의 순위 독점, 범위·맥락 누락, 필터·본문 재사용·관계 탐색 비용을 확인한다. |
| 약 5,000건에서 계속 증가하거나 일상적으로 10,000건에 접근 | 결과가 `index.backend=sqlite`인지 확인하고 이전 개별 명령의 지연과 비교한다. |
| 대표 질문 50개 이상에서 예열 P95가 2초를 넘거나 반복 조회가 작업을 지연 | 색인 경로의 병목을 우선 조사한다. 약 1초를 초기 목표로 삼고 실제 사용 예산을 정한다. |
| 초기 색인이 반복적으로 30초 초과, 단일 수정에 수초 소요, 메모리가 제안치 512 MiB 초과 | 변경분 저장 및 후보만 읽는 방식과 전체 JSON 입출력을 비교하고 기기·작업에 맞는 예산을 정한다. |
| 공통 문서에 수천 개의 관계가 몰림 | 관계 중복 제거와 ID·종류별 인접 관계 조회를 비교한다. 양방향 탐색, 충돌 표시, 페이지 및 이어보기를 확인한다. |
| 라우팅·용어 개선 뒤에도 바꿔쓰기 누락이 반복 | 한국어 어휘 분석·질의 재구성과 필요 시 의미 기반 후보 탐색·재정렬을 비교한다. 식별자와 적용 조건, 필수 근거 확인은 계속 검증한다. |

## 색인 검색과 복구

정규화한 파이썬 단어를 인코딩하여 짧은 한국어 접두어, 조사, 구두점이 있는 기술 이름도 후보에 포함한다. 실제 일치 판정, 가중치, 인용 구간, 근거 확인, 페이지와 동일 본문 분산에는 순차 검색과 같은 규칙을 쓴다. 새 파일과 변경 파일만 읽고 삭제된 경로는 제거한다. ID와 관계가 유효한지 검사한 뒤 문서·검색어·관계·파일 지문을 하나의 트랜잭션으로 반영한다. 잘못된 편집을 만나면 요청에 오류를 반환하고 트랜잭션을 취소한다.

파일 크기와 수정 시각을 모두 보존한 편집은 `--refresh`로 확인한다. `--no-cache`와 `--portable-library`는 정본을 직접 검색한다. 색인을 준비할 때 SQLite·FTS5 또는 데이터베이스를 사용할 수 없으면 순차 검색으로 전환하고 경고한다. 손상된 캐시는 검색 프로세스를 닫은 뒤 데이터베이스를 다른 곳으로 옮기면 다음 실행에서 재생성된다. 최초 구축과 넓은 검색어의 비용은 별도로 측정한다.

체크아웃의 [3만 건 측정 도구](../tests/benchmark_scale.py)로 개별 프로세스 측정을 재현한다. 같은 질문·결과 개수·ID 순서와 외부 편집 반영 여부를 비교한다. P95는 개별 실행 50회 이상으로 계산하고 OS 캐시 상태, 긴 지연과 최초 색인 시간을 별도로 기록한다.

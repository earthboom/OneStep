# 작업에 착수하기 전에 현재 프로젝트의 근거 찾기

요청에서 지정한 작업 프로젝트를 기준으로 삼는다. 별도 지정이 없으면 현재 프로젝트를 기준으로 한다. 스킬이 있는 체크아웃과 설치된 `onestep-strategy/` 라이브러리는 공유 지침을 제공한다. 프로젝트 문서 경로는 작업 프로젝트 기준으로 해석하고, 해당 프로젝트의 출처 및 접근 규칙을 따른다. 파일을 검색하거나 열기 전에 `*.kr.md`를 제외한다. `rg`에서 포함 패턴을 쓸 때는 `-g '!*.kr.md'`를 그 뒤에 두어 번역본이 검색 범위에 다시 들어오지 않게 한다.

1. **원문으로 무엇을 확인할지 정한다.** 실제 요청, 대상, 유지 조건을 보고 답에 따라 결과물이 바뀔 질문을 파악한다. 이미 확보한 입력과 작업 요약의 근거를 확인한다. 중요한 질문이 모두 해소되어 있으면 바로 작업한다.
2. **다음 읽기에서 링크된 원문을 연다.** 프로젝트 지침과 작업 대상에 가장 가까운 README나 색인을 사용한다. 지침에 진입점이 명시돼 있으면 프로젝트 문서를 읽는 첫 호출에서 그 진입점을 바로 연다. 읽은 뒤 요청의 각 상황이나 결정을 관련 출처 링크에 연결한다. 링크 이름이 더 넓은 작업을 설명하더라도 해당 상황의 기준을 담고 있을 원문은 포함한다. 연결한 원문을 다음 도구 호출에서 읽고, 서로 독립적인 읽기는 한 번으로 묶는다. 묶을 수 없으면 차례로 읽는다. 링크된 원문을 연 뒤 키워드 검색, 파일 목록 조회, 별도의 상태 확인을 진행한다. 관련 링크가 없거나 열 수 없거나, 원문을 읽은 뒤에도 중요한 질문이 남은 상황은 검색 단계로 넘긴다. 작업 요약에 있는 관련 절을 재사용한다.
3. **남은 질문마다 맞는 검색을 하나 고른다.** 읽을 수 있는 링크 원문을 확인한 뒤 이 단계를 시작한다. 부족한 사실과 그 근거가 기록됐을 위치를 파악한다. 결과 보고서의 위치가 필요하면 먼저 파일명을 한 번 조회한다. 프로젝트가 근거 폴더를 가리키면 그 폴더를 대상으로 하고, 폴더를 모르면 작업 프로젝트를 대상으로 한다. 예를 들어 프로젝트에 알맞은 용어로 `rg --files -g '*validation*' -g '*verification*' -g '*report*' -g '!*.kr.md'`를 사용하거나 쓸 수 있는 도구의 파일 목록에 필터를 적용한다. 그 결과에서 원문 후보를 열어 확인한다. 파일명으로 찾지 못했거나 출처 후보 안의 특정 사실이 필요하면 제목이나 본문을 검색한다. 예를 들어 `rg -l -i -g '!*.kr.md' -e 'receipt_id|receipt status' operations/`는 출처가 있을 영역을 좁혀 검색한다. 구체적으로 놓친 근거가 있거나 새 공백이 생겼으면 추가로 검색한다. 생성 산출물, 외부 의존성 복사본과 관련 없는 영역은 제외한다. 전용 도구가 필요한 문서는 해당 도구로 읽는다.
4. **적용 근거가 되는 원문을 읽고 사용한다.** 원문이 필요한 작업은 초안을 쓰거나 수정하기 전에 관련 절을 연다. 링크나 이전 열람에서 절 위치를 알 수 있으면 첫 묶음에서 요청된 결정, 예외, 검증에 해당하는 구간을 고른다. 전체 출력이 읽기 도구의 한도에 맞도록 조정한다. 초안, 예시, 이전 버전도 검색되는 경우에는 문서의 담당 범위, 승인 여부, 버전과 적용 조건을 확인한다. 검색 결과는 원문 위치를 찾는 데 쓴다. 기존 작업 요약에 경로와 절 또는 줄, 문서가 근거가 되는 결정, 결과물 검증 방법을 남긴다. 검증한 내용을 실행 중 재사용한다. 꼭 필요한 원문을 좁혀 탐색해도 찾지 못하거나 접근할 수 없으면, 영향을 받는 결정과 부족한 근거를 명시하고 독립적으로 진행할 수 있는 작업을 마친다.

여러 주제를 다루는 Markdown 파일로 연결되는 링크에 절이나 행 범위가 없어도, 첫 읽기에서 제목으로 필요한 절을 고릅니다. 적용할 결정, 입력 자료의 처리와 예외, 요청한 결과까지 이어지는 전체 절차, 허용되는 행동을 바꾸는 제약, 필요한 검증 상태를 포함합니다. 절 제목에 준비·검수·보관이 쓰이고 승인과 소진 규칙이 본문에 들어갈 수 있으므로, 자료 이름과 처리 단계도 검색어에 넣습니다. 제작 인수인계라면 전달 단계를 별도 문서에서 다루더라도 운영안에서 입력 자료 처리와 제작부터 전달까지의 절차를 읽습니다. 브리프가 유료 대체 수단을 제한하면 첫 읽기에 비용이나 한도를 다루는 절도 포함합니다. 제목 패턴으로는 결정에 `결정|권고|권장|추천`, 입력 자료 처리에 `대본|준비|검수|보관`, 전체 절차에 `(제작|생성).*(예약|업로드|게시|공개)`, 제약에 `비용|예산|한도`를 사용할 수 있습니다.

[절 선택 도구](../scripts/read_sections.py)는 이미 아는 파일 경로와 제목 패턴을 한 호출로 받아 파일명과 원래 행 번호를 붙인 원문을 반환한다. 문서 제목이 일치하면 첫 하위 절 앞의 도입부를 반환한다. 예를 들어 작업 프로젝트에서 `python -X utf8 <설치된-도구-경로> --section handbooks/process.md 'final recommendation|approved inputs|production.*delivery|failure recovery|verification status'`를 실행한다. 독립적인 문서는 `--section FILE PATTERN`을 반복해 한 번에 읽는다. 제목으로 절을 선택할 수 있는 다른 읽기 도구도 사용할 수 있다. 선택 범위가 너무 넓으면 패턴을 좁히거나 필요한 행 범위를 읽는다. 일치하는 절이 없으면 근거 공백으로 남긴다.

묶음의 출력이 잘리면 이미 아는 경로와 빠진 구간을 읽기 대기로 남기고, 함께 읽을 필수 근거가 있는지 확인한다. 무엇을 시험했는지 확인할 대상이 이미 정해져 있으면 위의 파일명 조회로 결과 보고서 위치를 먼저 찾는다. 그다음 보고서와 잘린 구간을 한 번에 연다. 실험 ID나 버전처럼 보고서를 식별하는 데 꼭 필요한 정보가 잘린 구간에 있을 때만 그 구간을 따로 먼저 읽는다. 계획의 빠진 절차와 이미 확인 대상이 정해진 운영의 실제 검증 결과는 보통 함께 읽을 수 있다.

문서를 더 열기 전에 답에 따라 결과물이 바뀔 미해결 질문을 정하고, 바로 그 질문의 근거를 가리키는 제목, 색인 항목, 절 제목이나 링크를 확인한다. 현재 검증 상태가 필요한 작업은 해당 운영의 결과 보고서를 확인한다. 적용 기준 원문이 요청된 상황을 다루고 직접 검증 보고서에 시험한 항목과 미검증 항목이 나와 있으면, 그 근거로 초안을 작성한다. 미검증이라고 명시된 상태도 확인 결과다. 예를 들어 샘플 렌더는 성공했고 게시 시험은 하지 않았다는 보고서는 두 상태 모두의 근거다. 같은 샘플의 후속 화면 검토는 시각 품질에 관한 자료로 쓴다. 이후 게시 시험이나 운영 결정 변경을 가리키는 구체적인 근거가 있으면 게시 상태를 다시 확인한다. 전체 변경 이력과 키워드 검색 결과에도 같은 기준을 적용한다. 중요한 질문마다 근거 또는 공백이 있고 검색 범위를 좁혀도 공백을 해소할 가능성이 낮으면 탐색을 마친다.

최종 표현을 대조할 때는 이미 확인한 원문 절을 사용한다. 표현 확인에 필요하면 인용한 절을 다시 연다. 초안에서 중요한 근거 공백이 새로 드러나고 그 문서로 공백을 해소할 수 있으면 새 문서를 연다.

전달할 때 주요 출처가 결과물에 어떻게 반영됐는지, 어떤 검사로 확인했는지 연결한다. 작은 작업은 본문의 짧은 출처 표시로 충분하다.

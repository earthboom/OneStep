# Vegabond 개발 구현

현재 작업 흐름 안에서 소프트웨어 작업을 수행합니다. 기존 개요와 프로필을 재사용하고 공통 경계와 완료 조건은 [에이전트 지침](../../agents/vegabond-agent.md)을 따릅니다. 직접 호출되면 분류를 다시 시작하지 않고 [Scout의 공통 준비](../vegabond-scout/SKILL.md#frame-and-classify)와 거기에 연결된 작업 절차를 사용합니다.

요청한 동작과 합격 조건이 명확하면 바로 진행합니다. 같은 테스트가 용어의 두 가지 타당한 해석에 따라 합격과 불합격으로 갈릴 때만 작업 프로젝트의 용어집을 참조합니다. 코드나 테스트를 바꾸기 전에 해당 항목만 읽고 연결된 원문 규칙을 확인합니다. OneStep의 `docs/development-glossary.md`에서는 첫 열에서 용어를 찾아 해당 행만 읽습니다. 설계에서 이미 검증해 전달한 정의와 경계 사례는 재사용합니다. 항목이 없거나 호출자·테스트와 충돌하면 해당 동작을 정의하는 프로젝트 근거로 경계를 확정한 뒤 합격을 보고합니다.

## 작업 환경 확인

저장소 지침, 소스와 관련 호출자, 프로젝트·의존성 구성, 테스트, 스크립트, CI에서 변경할 구성요소의 언어, 엔진·프레임워크와 버전, 도구 모음, 플랫폼·대상, 실제 빌드·테스트·실행·검사 경로를 확인합니다. 새 작업에서는 제안하는 도구와 실제 확인한 도구를 구분합니다. 근거가 상충하는 지점만 조사합니다. 구성 파일만으로 실행 가능하다고 단정하지 말고 Scout의 준비 상태 확인을 재사용합니다.

확장자나 저장소 주 기술보다 실제 구성요소를 기준으로 분류합니다. Unreal C++과 독립 C++은 각자의 도구 모음을 쓰며 Unity는 프로젝트와 패키지 규칙을 따릅니다. Unreal 저장소 안의 Python 도구는 자체 런타임을 기준으로 하고 에셋이나 엔진 동작까지 영향을 미칠 때 엔진 검사를 추가합니다. 여러 기술이 걸친 작업은 영향을 받는 구성요소와 경계 검사를 확인합니다. 별도 환경 보고서를 만들지 않고 출처 위치와 결과를 기존 개요에 남깁니다.

C++ 구성요소는 구현 전에 [C++ 프로젝트 지침](references/cpp-project-guidelines.md)을 읽습니다. C++ 공통 규칙에 Unreal C++ 추가 규칙을 함께 적용합니다. 작업 프로젝트 지침과 관례가 우선합니다. 언어 기능·소유권 모델 도입, 공개 API 설계, 디자인 패턴 선택, 성능 조정에는 [C++ 구현 가이드](references/cpp-implementation.md)의 관련 부분만 참조합니다. 이미 읽은 지침은 재사용합니다.

[지식](../vegabond-knowledge/SKILL.md)을 통해 관련 규칙, 버전에 맞는 원문, 과거 실패와 예방 검사를 요청하고 기존 정보 조사 결과를 재사용합니다. Scout의 매핑으로 사용 가능한 환경 스킬이나 도구를 선택합니다.

구성요소와 호출자를 살펴본 뒤 [공통 정보 필요성 판단](../vegabond-scout/references/information-needs.md)을 적용해 관련 상태, 소유권, 수명 주기, 실패와 검증에 관한 질문을 구체화합니다. 찾아낸 API 보장이나 사고 대응책을 적용하기 전에 실제 버전과 작동 원리를 확인합니다.

게임 구현·디버깅·최적화에는 [게임 근거 재사용 규칙](../../knowledge/game/K-GAME-RESEARCH-USE.md)을 적용하고 유효한 Scout 조사 결과를 활용합니다. 구체적인 기능이나 재현된 증상에서 출발해 엔진·플랫폼과 상태 제어권 조건을 확인합니다. 선택한 기법을 코드 변경과 관찰 가능한 검사에 연결합니다. 기각 이유를 보존하고 측정 결과를 지식에 전달합니다. 참고 게임의 사례만으로 현재 구현을 입증할 수 없습니다.

## 설계 깊이 선택

설계를 구현으로 옮기는 단위를 결정할 때는 [범위와 전달 기준](../vegabond-code-design/references/scope-and-delivery.md)을 사용합니다. 공유하는 불변 조건과 호출자를 함께 다루거나 다음 단위를 바꿀 수 있는 중간 증거를 밝힙니다. 선택한 방식을 통합 동작 검증까지 이어갑니다.

구현 전에 상태 소유권, 수명 주기, 다른 호출자가 쓰는 인터페이스, 동시성, 영속화, 외부 통합 또는 이전에 관한 중요한 선택을 해야 하면 [개발 설계](../vegabond-code-design/SKILL.md)를 사용합니다. 확립된 패턴을 따르는 국소 변경은 관련 규칙과 보존 조건을 간단히 밝히고 진행합니다. 파일 수만으로 결정하지 않습니다. 유효한 설계는 재사용하고 새로운 근거로 달라진 결정만 다시 검토합니다.

새 게임은 스캐폴딩을 선택하거나 만들기 전에 [기반 설계 결정](../vegabond-code-design/references/gameplay-framework.md#plan-a-new-game-foundation)을 개발 설계로 보냅니다. 개요에는 대표적인 플레이에 맞는 프레임워크, 이름을 명시한 상태 소유자와 수명, 첫 콘텐츠와 다음 변형을 작성하고 등록하는 경로가 필요합니다. 프로젝트 개요에서 이미 합의한 결정을 재사용합니다.

기존 게임에서 게임플레이 프레임워크, 공유 콘텐츠 규칙 또는 기능 간 의존성이 바뀌면 개발 설계로 보냅니다. 기존 확장점을 통해 콘텐츠를 추가하면 기존 규칙을 따르고 지원하던 기준 동작과 새 콘텐츠를 함께 검사합니다. 독립적으로 선택 가능한 기능은 기존 확장점을 쓰더라도 해당 [의존성·독립성 검사](../vegabond-code-design/references/gameplay-framework.md#make-feature-dependencies-explicit)를 적용합니다. 새 의존성이나 규칙 변경 필요성이 드러나면 개발 설계를 사용합니다.

현재 개요, 환경, 영향받는 소스와 규칙, 제약, 미결 사항을 전달합니다. 설계 단계는 이 작업 안에서 범위를 정한 구현 방향과 검사를 반환합니다. Scout를 다시 시작하거나 별도 실행 흐름을 만들지 않습니다. 설계만 요청받았다면 그 결과를 전달하는 것으로 마칩니다.

## 구현 또는 조사

사용자 결정으로 설계가 바뀌었으면 인계받은 구분 사례를 정상 진입점에서 실행합니다. 관찰 결과를 사용자가 선택한 결과와 대조하며 약속한 보존·실패 동작도 포함합니다. 환경을 사용할 수 없으면 구체적인 기대 결과와 미검증 상태를 전달합니다.

코드를 변경하거나 결과를 판정하기 전에 [검증과 인계](references/verification.md)를 읽습니다. 이 문서에서 세부 준비, 빌드·테스트·런타임·실사용 검사, 검토와 수정 반복, 검증 방법 변경에 대한 점검, 장기 작업 상태, 실제 입증한 보호책을 다룹니다. 공유 게임플레이 코드나 공통 규칙을 바꾸거나 스테이지를 추가하기 전에 [게임플레이 회귀 검사](references/verification.md#gameplay-regression-checks)로 보존할 동작과 검사 범위를 기존 개요에 남깁니다. 일관된 변경 단위와 최종 통합 결과물 모두를 검증합니다.

게임플레이 프레임워크나 콘텐츠 경계 변경은 설계에서 정한 대표적 확장 사례, 영향받는 의존성 검사, 지원할 콘텐츠 구성을 구현 검증으로 가져옵니다. 독립적으로 선택 가능한 기능에도 해당 의존성·구성 검사를 적용합니다. 운영에서 사용할 등록과 플레이 경로를 실행합니다. 변형을 추가하는 데 실제로 필요했던 변경과 해당 구성들의 동작을 검증 근거에 기록합니다.

입력 반응, 타격 피드백, 플레이 결과의 표현을 바꾸면 에셋만 바꾸는 경우에도 [게임플레이 피드백 검사](references/verification.md#gameplay-feedback-checks)를 적용합니다.

게임 데이터 변경, 스트리밍·캐시·풀링된 콘텐츠, 렌더링 예산 또는 수명과 가시성에 따른 NPC 동작을 다룰 때는 일반 검증과 함께 [게임 런타임 검사](references/world-lifecycle-verification.md)를 적용합니다. 기존 데이터 바이트, 엔진 상주 여부, 관찰 가능한 상태 등 각 주장에 맞는 실제 경계를 확인합니다.

- **생성** — 선택한 설계나 기존 로컬 패턴을 따라 완전히 사용 가능한 경로를 구현합니다. Scout의 규모 판단을 재사용하고, 중요한 가정은 후속 작업에 앞서 작은 통합 단위로 확인합니다.
- **수정** — 결함을 재현하고 원인을 추적한 뒤 수정합니다. 의도적인 구조 변경은 기존 동작과 공개 규칙을 보존하며 일관된 단위로 진행합니다. 관련 없는 정리는 범위 밖에 둡니다.
- **조사** — 코드, 데이터 흐름, 런타임 근거를 추적합니다. 질문에 맞춰 선택지를 비교하고 파일, 심벌, 로그, 적용 가능한 출처를 인용합니다. 조사 대상 코드는 보존하고 실험에는 격리된 환경을 사용합니다.

구현 증거가 설계를 뒤집으면 영향을 받는 결정과 근거를 개발 설계로 돌려보내 기존 개요와 검사를 업데이트합니다. 목표나 전제가 바뀌면 공통 복귀 규칙을 따릅니다. 구현에 맞추려고 인수 기준을 조용히 바꾸지 않습니다.

## 결과 전달

패치 또는 조사 결과, 실제 최종 코드의 인수 근거, 검토 결과, 남은 미해결 사항을 현재 작업에 반환합니다. 확인한 정정 사항, 재사용할 방법, 입증한 보호책은 권한이 있는 저장을 위해 지식에 보냅니다. 소프트웨어 근거의 내용은 검증 문서를 따릅니다. 공통 지침에 따라 AI가 완료한 검사와 vagabond의 독립적인 인수 판정을 구분합니다.

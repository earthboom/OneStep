# Vegabond Code

진행 중인 작업 안에서 소프트웨어 작업을 수행한다. 해당 작업의 브리프와 프로필을 재사용하고, 공통 범위와 완료 기준은 [에이전트 지침](../../agents/vegabond-agent.md)을 따른다. 직접 호출된 경우 [scout의 공통 준비 절차](../vegabond-scout/SKILL.md#frame-and-classify)와 연결된 작업 절차를 사용한다. 분류를 처음부터 다시 시작할 필요는 없다.

## 작업 환경 파악

저장소 지침, 소스와 관련 호출자, 프로젝트·의존성 설정, 테스트, 스크립트, CI를 보고 변경할 구성 요소의 언어, 엔진·프레임워크와 버전, 도구 체인·플랫폼·대상, 실제 빌드·테스트·실행·점검 경로를 파악한다. 새 작업에서는 제안한 도구 체인과 실제로 확인한 도구 체인을 구분한다. 근거가 충돌하면 해당 범위에서 해결하고, 설정만으로 도구가 실행된다고 판단하지 않도록 scout의 준비 상태 확인을 재사용한다.

실제 구성 요소를 기준으로 분류한다. Unreal C++와 독립 C++는 각자의 도구 체인을 사용하고, Unity는 해당 프로젝트와 패키지의 계약을 따른다. Unreal 저장소 안의 Python 도구는 자기 실행 환경을 따르며, 영향이 에셋이나 엔진 동작에 닿을 때는 엔진 검증을 추가한다. 혼합 작업에서는 영향을 받는 구성 요소와 경계를 확인할 방법을 식별한다. 소스 위치와 확인 결과는 기존 브리프에 남긴다.

C++ 구성 요소를 구현하기 전에 [C++ 프로젝트 지침](references/cpp-project-guidelines.md)을 읽는다. C++ 공통 규칙을 따르고, Unreal C++에는 추가 규칙을 적용한다. 작업 대상 프로젝트의 지침과 관례가 우선한다. 언어 기능이나 소유권 모델을 도입하거나, 공개 API·설계 패턴을 선택하거나, 성능을 조정할 때에는 [C++ 구현 가이드](references/cpp-implementation.md)의 관련 부분만 참고한다. 작업에서 이미 읽은 지침은 재사용한다.

기존 정보 브리프를 재사용해 [vegabond-knowledge](../vegabond-knowledge/SKILL.md)에 관련 계약, 버전별 출처, 과거 실패와 방지 검증을 요청한다. 사용할 환경 스킬이나 직접 도구는 scout의 매핑을 따라 선택한다.

구성 요소와 호출자를 확인한 뒤 [공통 정보 조사 판단](../vegabond-scout/references/information-needs.md)을 적용한다. 필요한 경우 영향을 받는 상태, 소유권, 수명, 실패, 검증에 관한 질문을 구체화한다. 찾은 API 보장이나 과거 사건의 수정법을 적용하기 전에 실제 버전과 동작 원리를 확인한다.

게임 구현·디버깅·최적화에는 [게임 근거 재사용 규약](../../knowledge/game/K-GAME-RESEARCH-USE.md)을 적용하고, scout가 찾은 자료가 유효하면 재사용한다. 구체적인 기능이나 재현된 증상에서 출발해 엔진·플랫폼과 상태 권한 조건을 확인하고, 선택한 기법을 코드 변경과 관찰 가능한 검증에 연결한다. 채택하지 않은 이유를 보존하고 측정 결과는 knowledge를 통해 돌려준다. 출처에 나온 게임 사례로 현재 구현의 동작을 입증할 수는 없다.

## 필요한 설계 범위 선택

상태 소유권, 수명, 다른 호출자가 사용하는 인터페이스, 동시성, 영속성, 외부 연동 또는 마이그레이션을 구현 전에 결정해야 한다면 [vegabond-code-design](../vegabond-code-design/SKILL.md)을 사용한다. 기존 패턴을 따르는 국소 수정은 해당 계약과 유지 조건을 작업 안에 적고 진행할 수 있다. 파일 수만으로 판단하지 않는다. 유효한 기존 설계를 재사용하고 근거가 달라진 결정만 다시 검토한다.

새 게임에서는 게임플레이 뼈대를 선택하거나 만들기 전에 [기반 설계 결정](../vegabond-code-design/references/gameplay-framework.md#plan-a-new-game-foundation)을 code design으로 보낸다. 브리프에는 대표 플레이에 맞는 프레임워크, 이름을 명시한 상태 소유자와 수명, 첫 콘텐츠와 다음 변형을 저작하고 등록하는 경로가 필요하다. 프로젝트 브리프에서 이미 확정한 결정은 재사용한다.

기존 게임의 게임플레이 프레임워크, 공유 콘텐츠 계약, 기능 간 의존성을 바꾸는 작업은 code design으로 보낸다. 기존 확장 지점을 통해 콘텐츠를 추가할 때는 기존 계약을 쓰고 지원 기준선과 함께 새 콘텐츠를 확인한다. 독립적으로 선택 가능한 기능은 기존 확장 지점을 쓰더라도 관련 [의존성과 독립성 확인](../vegabond-code-design/references/gameplay-framework.md#make-feature-dependencies-explicit)을 거친다. 확인 중 새 의존성이나 필요한 계약 변경이 드러나면 code design을 사용한다.

현재 브리프, 환경, 영향을 받는 소스와 계약, 제약, 미결 사항을 넘긴다. 설계는 이 작업 흐름에 범위가 정해진 구현 방향과 확인 항목을 돌려준다. scout를 다시 시작하거나 별도 실행 흐름을 만들 필요는 없다. 설계만 요청되면 설계 결과를 전달한다.

## 구현 또는 조사

코드를 변경하거나 결과를 판단하기 전에 [검증과 인계](references/verification.md)를 읽는다. 상세 준비, 빌드·테스트·런타임·실사용 검증, 검토와 수정, 검증 관련 변경의 점검, 장기 작업 상태, 입증된 재발 방지책은 해당 문서를 따른다. 공용 게임플레이 코드나 공용 규칙을 바꾸거나 스테이지를 추가하기 전에 [게임플레이 회귀 검증](references/verification.md#gameplay-regression-checks)에 따라 유지할 동작과 검증 범위를 기존 브리프에 기록한다. 각각의 완결된 변경과 최종 통합 산출물에 검증을 적용한다.

게임플레이 프레임워크나 콘텐츠 경계를 바꾸면 설계에서 고른 대표 확장 사례, 영향을 받는 의존성 검증, 지원 콘텐츠 구성을 소프트웨어 검증에 가져온다. 기존 확장 지점에 독립적으로 선택 가능한 기능을 추가할 때도 관련 의존성과 구성을 검증한다. 실제 게임의 등록 및 플레이 경로를 실행한다. 변형을 추가하는 데 실제로 발생한 변경과 해당 구성의 동작을 검증 근거에 기록한다.

입력 반응, 타격 피드백 또는 게임플레이 결과의 표현을 바꿀 때는 [게임플레이 피드백 검증](references/verification.md#gameplay-feedback-checks)을 적용한다. 해당 동작에 영향을 주는 에셋만 변경하는 경우도 포함한다.

게임 데이터, 스트리밍·캐시·풀링 콘텐츠, 렌더링 예산, 수명과 가시성 변화에 따른 NPC 동작을 바꾸는 경우 [게임 런타임 검증](references/world-lifecycle-verification.md)의 관련 부분과 공통 검증 절차를 함께 적용한다. 해당하는 경우 기존 데이터 바이트, 엔진 상주 상태, 관찰 가능한 상태를 포함해 각 주장에 맞는 실제 통합 경계를 사용한다.

- **생성.** 선택한 설계나 기존 국소 패턴을 따라 완전하고 실제로 사용할 수 있는 경로를 구현한다. 중요한 가정은 그에 의존하는 구현 전에 작은 통합 범위에서 확인하고 scout가 정한 작업 규모를 따른다.
- **수정.** 결함을 재현하고 원인을 추적한 뒤 수정한다. 의도적으로 구조를 바꿀 때는 관련 작업을 완결된 단위로 진행하며 기존 동작과 공개 계약을 보존한다. 무관한 정리는 작업 범위 밖에 둔다.
- **조사.** 코드, 데이터 흐름, 런타임 근거를 추적한다. 질문에 맞춰 대안을 비교하고 파일, 심볼, 로그와 적용 가능한 출처를 제시한다. 조사 대상 코드를 보존하고 실험에는 격리된 환경을 쓴다.

구현 근거가 설계를 반박하면 영향을 받은 결정과 근거를 code design에 돌려주고 기존 브리프와 검증을 갱신한다. 목표나 전제가 달라지면 공통 복귀 지점 규칙을 따른다. 구현에 맞추기 위해 조용히 수용 기준을 바꾸지 않는다.

## 결과 인계

패치 또는 조사 결과, 실제 최종 코드의 수용 근거, 검토 결과, 남은 미결 조건을 진행 중인 작업에 전달한다. 확인한 수정 사항과 재사용 가능한 방법, 입증된 재발 방지책을 보관할 권한이 있으면 knowledge에 넘긴다. 제공할 소프트웨어 근거는 검증 문서가 정한다. AI가 마친 확인과 공통 지침에 따른 vagabond의 독립 수용 판단을 구분한다.

# Game data, streaming and NPC verification

Apply the relevant checks through the existing [verification procedure](verification.md). Use an independently specified expected result and the project's production entry points. A small local change can use the affected subset.

| Claim | Exercise | Evidence to retain |
| --- | --- | --- |
| Catalog changes are valid | Use the production validation and registration paths for the new, changed or retired entries. Check linked content, duplicate IDs and optional content under actual absence where relevant. | Affected catalog and engine target, accepted and rejected records, resolved references, and the affected gameplay behavior. |
| Existing data is compatible | Load an unchanged pre-change artifact through the production loader; exercise a changed or retired ID and the affected caller. Read or reload the migrated output where supported, and run representative invalid or future data. For a writer change, check failed or interrupted writes against the existing file. | Input version and provenance, resolved ID, preserved fields and dependent behavior, output version and subsequent read, explicit rejection or recovery. A generated current-format fixture covers the current format. |
| Content can actually leave residency | Use real scene, level, object or asset boundaries. Observe request, ready/activation and unload or teardown. Revisit and exercise obsolete work or ownership changes if supported. Check optional content under real absence. Pool reuse needs checks for stale callback, subscription and state. | Actual scene/level/view identities, load/unload and residency evidence appropriate to the claim, request order, and retained bytes or handles if claiming memory release. A hidden renderer establishes visibility only. |
| Cached data stays correct | Exercise a repeated lookup, change a dependency or version, then force eviction and rebuild. Check concurrent stale completions if the cache can be rebuilt while in use. | Value before and after invalidation, expected hit/miss or rebuild, and evidence of saved work or bounded memory when claimed. |
| Streaming or rendering fits a budget | Capture matched paths at the same target, device, renderer and workload, including repeated transitions. Distinguish first visit in a new process, revisit and verified cache state. Measure request-to-ready or activation separately from frame durations and phase costs. Capture GPU and visual output when they are part of the claim. | Capture conditions, sample counts, representative ranges or tail frame times, deadline misses, relevant memory and quality. Explain warmup, caps and omitted phases. Headless or null rendering supports scoped CPU/activation observations; measure rendering and shipping budgets on their actual targets. |
| NPC state survives absence | Mutate state through the normal action, remove the presentation or streamed region, and inspect the authoritative state while absent. If the design promises offscreen progression, observe it while no view exists. If commands or events may target an absent NPC, exercise one and check that its effect occurs as many times as the contract allows. Reattach a newly loaded representation and verify identity, state and downstream behavior. Verify restart separately when persistence is claimed. | Payload before combat, after mutation, during absence and after reattachment. Capture the independent lifecycle observation. Include relevant timers, duplicate events, stale callbacks and alternate observers. |

For Unity, check the configured Editor or actual Player as required by the claim, then observe the real `SceneManager` or Addressables operations and inspect any Prefab, serialized, metadata or catalog changes. For Unreal, use the intended Game/PIE/packaged world and inspect actual level or streaming state, actor lifetime and authoritative session ownership. Match engine and configuration to the task before drawing performance conclusions.

For consequential checks demonstrate sensitivity with a realistic broken case, such as an invalid migration, a surviving view after unload, or state reset at re-entry. Report the real result and the failure reason separately from blocked, inapplicable or unmeasured checks. See [game runtime design](../../vegabond-code-design/references/world-lifecycle.md) for selecting the contracts.

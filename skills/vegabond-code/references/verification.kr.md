# 소프트웨어 검증과 인계

[vegabond-code](../SKILL.md)에서 코드를 바꾸거나 소프트웨어 결과를 판단하기 전에 이 절차를 사용한다. 공통 완료 조건, 수용 판단, 실패 시 복귀 경로는 [에이전트 지침](../../../agents/vegabond-agent.md)이 정한다. 여기서는 소프트웨어 검증을 다룬다.

## 검증 준비

구현 전에 수용 조건과 유지할 계약을 실행 가능한 검증에 연결한다. 정보 브리프에 관련 재발 방지책이 있으면 포함한다. 영향을 받는 경로의 기준선을 확인하고 기존 실패를 구분한다. 국소 테스트가 가능하면 결함을 고치기 전에 의도한 원인으로 실패하는 회귀 검증을 확보한다. 여의치 않으면 관찰 가능한 가장 가까운 재현을 남기고 한계를 명시한다.

프로젝트의 기존 검증 명령과 하네스를 먼저 사용한다. 명령이 의도한 테스트를 실제로 찾아 실행하고 변경 대상 동작에 도달하는지 확인한다. 관련 단언 없이 종료 코드가 0이라는 사실만으로는 동작을 입증할 수 없다. 명령, 대상과 설정, 코드 리비전이나 관련 변경 내용, 관찰 결과는 기존 작업 근거에 남긴다. 반복 가능한 경로가 없어 필수 동작을 확인할 수 없다면, 작업 범위 안에서 가장 작은 재사용 가능 검증을 추가하고 처음부터 끝까지 확인한다.

### 게임플레이 회귀 검증

공용 게임플레이 코드나 공용 규칙을 바꾸거나 스테이지를 추가하기 전에 기존 브리프에 [게임플레이 회귀 검증 범위](../../vegabond-code-design/references/gameplay-framework.md#set-gameplay-regression-scope)를 기록하거나 이미 정해진 범위를 재사용한다. 선택한 경로마다 시작 상태, 입력, 플레이어가 볼 것으로 예상하는 결과, 관련 권한 주체의 확정 상태, 필요한 엔진·빌드 또는 네트워크 역할을 정한다. 기존 계약이나 승인된 기준선에서 기대 결과를 정하고 의도적으로 바꾸는 동작을 명시한다.

- **공용 게임플레이 코드와 규칙.** 필요하고 가능한 경우 영향을 받는 규칙이나 수명을 격리해 확인한 뒤, 실제 플레이에서 대표 기존 콘텐츠를 실행한다. 공용 동작을 서로 다르게 사용하는 호출자, 스테이지, 역할을 고른다. 회귀를 드러낼 수 있는 무효 입력, 중단 또는 재시도 경로를 포함한다.
- **스테이지 추가.** 해당하는 ID, 참조, 필수 마커, 진행 조건을 검사한다. 실제 목록·해금·진입 경로를 사용해 플레이, 재시도 또는 종료, 기대 결과를 확인한다. 영향받는 규칙·에셋·진행을 공유하는 대표 기존 콘텐츠도 확인한다. 스테이지 추가가 공용 게임플레이 코드나 데이터로 정의된 공용 규칙을 바꾸면 두 경로를 모두 적용한다.

저장된 진행이나 ID에 영향이 있으면 지원 범위의 이전 저장으로 확인한다. 씬·맵의 빌드 포함 여부, 콘텐츠 배포, 그 밖의 빌드별 동작이 문제라면 대상 Unity Player나 Unreal 패키지를 사용한다. 확인한 환경과 경로를 기록한다. 격리된 규칙 검사, 에디터 플레이, 패키지 플레이는 각각 확인한 범위의 근거가 된다.

### 게임플레이 피드백 검증

변경 전에 정상 조작 경로의 대표 사례를 고르고, 의도한 피드백 변경과 승인된 기준선, 유지할 입력 반응·결과 신호·가시성을 기록한다. 기존 [게임플레이 피드백 설계](../../vegabond-code-design/references/gameplay-framework.md#design-gameplay-feedback)가 있으면 재사용한다. 변경 후 같은 경로를 비교한다. 기존 검증이나 실행 가능한 가장 작은 재현을 사용한다.

- **판정과 연출의 일치.** 해당하는 명중·가드·빗나감 사례를 실행한다. 접촉 신호가 판정에 맞는 시점과 필요한 위치나 방향에서 재생되는지 확인한다. 연타나 네트워크 보정 때문에 지난 연출이 남거나 중복될 수 있으면 해당 경로를 포함한다. 연출만 변경했다면 관련 명중 시점, 피해, 경직, 조준, 행동 허용 구간이 유지되는지 확인한다.
- **조작 반응과 가독성.** 대표 입력·출력 장치에서 같은 흐름을 플레이한다. 설정이나 장치 지원 여부가 신호에 영향을 주면 기본 상태와 효과를 줄이거나 끈 상태, 또는 효과를 지원하지 않는 대표 구성을 비교한다. 히트스톱을 쓰는 경우 멈춤 중·이후에도 후속 입력이 의도한 시점에 처리되는지 확인한다. 연출이 겹치는 대표 상황에서도 결과를 구별할 수 있고 다음 위협이나 행동이 읽히는지 확인한다. 타이밍이 바뀌거나 영향받을 수 있으면 관련 입력부터 반응, 판정부터 연출, 또는 회복까지의 시간을 비교 가능한 조건에서 측정한다. 관찰한 플레이와 설정, 자동 신호·타이밍 검사의 확인 한계를 기록한다.

## 검증 실행

해당하는 경우 다음 네 단계를 적용한다.

1. **빌드와 준비.** 영향을 받는 대상과 설정에 대해 프로젝트의 실제 빌드, 컴파일 또는 그에 준하는 준비 작업을 실행한다.
2. **자동 테스트.** 관련 기존 테스트를 실행한다. 유의미한 보호 효과가 있으면 구현과 독립적인 기대 결과를 사용해 회귀 또는 동작 검증을 추가한다. 영향을 받는 경계와 오류 경로도 포함한다.
3. **런타임 준비.** 애플리케이션이나 필요한 환경을 실행해 초기화 실패 없이 변경 경로에 도달할 수 있는지 확인한다.
4. **실사용.** 공개 인터페이스를 통해 변경한 동작을 실행한다. Unreal이나 Unity 게임은 에디터를 열어 실제로 플레이하고 관련 멀티플레이 역할을 포함한다. CLI는 실제 명령을 호출하고 라이브러리는 실제 소비자나 하네스를 사용한다.

결함을 수정한 작업은 원래 재현과 주변의 영향받는 동작을 다시 확인한다. 명령, 대상과 설정, 결과, 관찰한 런타임 동작을 기록한다. 단계마다 에이전트 지침에 따라 진행 불가와 해당 없음을 구분한다. 구현 변경이 없는 코드 조사는 주장을 뒷받침하는 검증을 사용한다.

## 검토와 반복

완결된 변경마다 영향을 받는 빌드·준비 작업과 자동 검증을 실행한 뒤 요구사항에 맞춰 변경 내용과 호출자를 점검한다. 빠진 동작, 깨진 계약, 상태·수명 오류, 변경에 특유한 위험을 찾는다. 테스트가 구현 출력을 반복할 때와 실제 잘못된 동작을 발견할 때를 구분해 검토한다. 관련 역량을 더할 수 있는 검토나 테스트 스킬을 사용한다. 검토에서 찾은 문제를 수정하려면 구체적인 발생 원리나 근거가 필요하다.

테스트와 검증 설정의 변경도 패치의 일부로 검토한다. 단언 삭제, 건너뛰기, 제외, 기대값 완화, 린트·타입 검사 억제, 검사 비활성화에는 계약에 근거한 이유가 필요하다. 정당한 실패는 계속 드러나야 한다. 검사 자체가 잘못됐다면 충돌하는 요구사항이나 근거를 식별하고 수정 이유를 설명한 뒤 유지할 계약을 검증한다. 실행이 막혔거나 건너뛴 필수 검증은 인계에 표시한다. 실용적인 회귀 검증이나 중요한 재발 방지책은 원래 실패나 의도적으로 만든 실패를 잡는지 입증한다. 기대 결과는 구현과 독립적으로 둔다.

예외를 삼키는 처리, 성공처럼 보이는 기본값, 무조건 재시도, 임의 대기, 호환성 경로가 정당한 상태에 대응한다는 근거가 있는지 확인한다. 대체 동작은 계약에 정의되어 있고 실패 시 동작을 확인했을 때 유효하다. 예를 들어 설정이 없어도 되는 경우에 잘못된 설정까지 성공으로 처리하면 안 된다. 근거가 아직 없는 우회책은 확인할 가설로 둔다. 근거가 반박한 추측성 변경은 제거하되 관련 없는 작업을 보존한다.

확인된 실패나 결함은 명령, 단언, 로그, 상호작용으로 원인을 좁힌다. 문제를 고치고 원래 실패와 영향을 받는 주변 검증을 반복한 뒤 수정된 변경 내용을 검토한다. 필수 검증이 통과하고 범위 안의 확인된 결함이 해결될 때까지 반복한다. 잘못된 동작을 받아들이도록 유효한 검사를 약화하지 않는다. 잘못된 검사라면 요구사항과 명시적인 수정 이유에 맞춰 바로잡는다.

진단, 근거, 작업 범위, 사용 가능한 역량을 다시 판단해야 할 때에는 에이전트 지침의 [공통 실패 및 피드백 규칙](../../../agents/vegabond-agent.md#respond-to-failures-and-feedback)을 따른다.

국소 검증을 마친 뒤 최종 산출물에서 필요한 통합 및 실사용 검증을 실행한다. 실패하면 진단과 수정으로 돌아간다. 이후 수정의 영향을 받는 근거는 다시 확인한다. 재현 가능한 기존 실패와 새로 생긴 실패를 구분한다. 기존 실패는 작업의 수용 근거로 삼을 수 없다.

## 장기 또는 단계별 작업 이어가기

단계가 바뀌거나 작업을 인계하거나 컨텍스트를 재설정하기 전에 기존 브리프를 갱신한다. 목표와 유지 조건, 완료·미완료 수용 항목, 현재 코드 상태, 근거 위치, 다음 단계를 제약하는 결정과 다음 행동을 적는다. 결정과 검증을 기록하고 내부 추론이나 모든 도구 호출 기록은 생략한다. 재개 시 현재 변경 내용과 유효한 근거에 맞춰 상태를 갱신한다. 중간 변경으로 무효가 된 근거를 다시 확인하고, 남은 조건을 조용히 빼거나 이미 마친 작업을 기본적으로 전부 반복하지 않는다.

## 유용한 재발 방지책 보존

중대한 실수가 반복되면 기존 지식·기록 흐름에서 패턴을 확인한다. 안내 문구를 더 쓰기 전에 범위가 좁은 구조 변경, 타입 제약, 린트·CI 검증, 동작 테스트를 우선 검토한다. 프로젝트의 기존 강제 경로를 재사용하고 실제 실수나 동일하게 통제한 사례를 감지함을 입증한다. 자동으로 강제하는 부분, 문서에 명시한 부분, 남은 한계를 보고한다. 이 스킬에 규칙이 적혀 있다는 이유만으로 강제된다고 주장하거나 작은 작업마다 새 기반 시설을 요구하지 않는다.

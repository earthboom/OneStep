## 기존 흐름에서 바꿀 부분

[Scout](../../skills/vegabond-scout/SKILL.kr.md)는 단순 작업과 결과에 영향을 주는 모호성을 이미 구분한다. [설계 가이드](../../skills/vegabond-code-design/references/scope-and-delivery.kr.md)에도 잘못 결정했을 때의 비용과 작업을 나눌 기준이 있다. 보완할 지점은 **사용자가 중요한 질문에 답한 뒤 그 답이 어디에 남고, 다음 담당자는 무엇으로 확인하는가**다.

1. **질문 전, 실제 갈림길을 찾는다.** 원하는 결과, 제안된 수단, 보존할 동작을 구분한다. 프로젝트 용어·실제 호출자·기존 결정·문제 기록에서 확인할 수 있는 사실을 먼저 찾는다. 현재 코드는 지금의 동작을 보여 주고, 사용자는 앞으로도 그렇게 동작해야 하는지를 정한다. 두 해석에서 동작과 검사 모두 같으면 바로 진행한다.
2. **답이 일을 바꾸는 질문 하나를 한다.** 사용자가 알아볼 상황과 가능한 선택의 결과, 답에 따라 바뀔 결정을 제시한다. 근거가 있으면 추천안과 비용을 덧붙이고 다른 답도 열어 둔다. 여러 결정이 얽혀 있다면 후속 판단이 의존하는 것을 먼저 묻는다. 저렴한 실험으로 알아낼 기술적 불확실성은 그 실험으로 해결한다.
3. **답을 사용할 수 있게 만든다.** 기존 작업 요약에 합의한 용어 또는 규칙, 보존할 보장, 이를 깨뜨리는 사례와 검사 위치를 남긴다. 확정 사항, 되돌릴 수 있는 가정, 아직 사용자 선택이 필요한 항목을 구분한다. 반복될 용어는 프로젝트의 기존 용어 정의에, 오래 남을 절충은 기존 결정 기록에 반영한다. 코드와 답이 다르면 의도적으로 바꿀 동작으로 표시한다.
4. **결정에 맞춰 작업 경계를 정한다.** 함께 성공해야 하는 상태 변경과 거절 경로는 한 단위로 묶는다. 호환성 검사나 플레이 관찰 결과가 후속 구현을 바꿀 수 있으면 그 지점에서 나눈다. 각 단위에는 목표 동작, 보존 조건, 근거, 실제 선행 조건을 전달한다. 독립 검증과 공유 상태의 소유권을 보고 병렬 실행 가능성을 판단한다. 위임에는 별도의 권한도 필요하다.
5. **질문을 멈추고 독립된 근거로 확인한다.** 다음 단위의 결과와 실패를 관찰할 방법을 말할 수 있고, 남은 불확실성이 되돌릴 수 있거나 격리됐거나 구체적 실험에 배정됐다면 인터뷰를 끝낸다. 사용자 결정이 남아도 무관한 작업은 진행할 수 있다. 통합 시 최초 사용자 경로와 비용이 가장 큰 실패를 실제 진입점에서 확인한다. 실패하면 관련 가정을 다시 열고, 실제 실패와 확인된 교훈이 있을 때 재사용할 문제 기록으로 남긴다.

**반영 위치.** Scout는 인터뷰를 시작할 조건을 맡고, 코드 설계 가이드는 질문·결정·분할과 인터뷰 종료 조건을 맡는다. 코드 검증은 설계에서 넘긴 실패 사례를 사용하고 해당 구현을 점검한다. 기획은 같은 결정을 플레이어 경험과 제작 범위에 재사용한다. 기존 작업 요약을 인계 수단으로 쓰므로 짧은 요청마다 문서나 티켓을 만들거나 회의를 열 필요가 없다.

## 한 번의 설계 대화가 바꾸는 것

**요청 예시**는 “보스전 후 자동 저장을 넣어줘”다. 기존 프로젝트가 위치를 체크포인트에서 복원한다고 가정한다. 확인할 말은 ‘저장’이다. “플레이어가 보상을 받고 다음 체크포인트에 닿기 전에 종료했다가 다시 켭니다. 보상, 보스, 시작 위치는 각각 어떻게 보여야 하나요?”라고 묻는다. 세 요소에 다른 규칙을 정할 수 있는 질문이다.

**답변 예시**가 “보상은 유지하고 보스는 쓰러진 상태로 두되, 위치는 직전 체크포인트로 돌아간다”라면, 재시작 후 보상 획득과 보스 처치 상태가 일치해야 한다. 위치는 기존 체크포인트 규칙을 따른다. 보스 처치 기록과 보상 지급 사이에서 실행을 중단하고 재시작·재시도한다. 기대값은 보상 하나, 보스 미부활, 직전 체크포인트다. 앞의 두 변경을 한 연산이 책임지면 호출자는 개별 쓰기 순서를 몰라도 된다. 구버전도 새 기록을 열어야 한다면 쓰기 활성화 전에 실제 버전 왕복 검사가 필요하다. 이 예시는 요구 동작과 검사를 설계한 것이며, 특정 저장 트랜잭션의 존재는 구현 환경에서 확인한다.

## 개정 효과를 검증하는 방법

동일한 요청과 프로젝트 자료, 동일한 사용자 답변을 현재 지침과 개정 지침에 각각 새 대화에서 제공한다. 실제로 묻는 질문, 최종 결정, 그 결정을 확인할 검사를 비교한다.

| 사례 | 기대하는 관찰 |
| --- | --- |
| 단순 오탈자, 이미 설계 결정으로 답이 정해진 요청 | 불필요한 질문이나 추가 문서를 만들지 않는다. 정해진 결정은 찾아서 재사용한다. |
| 위 보상 예시처럼 중요한 의미가 모호한 요청 | 중단 상황을 구체적으로 묻고, 답이 저장 규칙·인계·재시작 기대값을 바꾼다. 답을 듣고도 같은 질문을 반복하거나 검사에 반영하지 않으면 실패다. |
| 구버전이 새 저장 파일을 거부하고 이를 확인할 실파일이 주어진 요청 | 파일을 조사하거나 호환 검사를 설계한다. 사용자에게는 아직 정해지지 않은 지원 약속만 묻고, 검증 전 새 쓰기는 조건부로 둔다. |
| 방 12개 기획과 검증되지 않은 길 찾기 단서 | 전체 12개를 범위에 유지하고 갈림길 하나에서 단서를 먼저 시험한다. 자동 재생으로 표시를, 힌트 없는 플레이어의 선택과 설명으로 발견 가능성을 판단한다. |

비교 지표는 결과를 바꿀 결정을 놓친 건수, 프로젝트에 이미 답이 있는데 되물은 건수, 인계 중 합의한 보존 조건을 잃은 건수다. 이 문서는 개정안과 평가 설계다. 새 스킬 구현이나 적용 전후 비교 실험은 이번 작업에서 수행하지 않았다.

## 개발 한정 시범 적용 · 2026-11-25

독립 검토자 두 명에게 같은 가상 개발 요청 세 개와 조건을 주었다. 한 명은 변경 전 코드 설계·구현 지침을, 다른 한 명은 시범 지침을 사용했다. 두 검토자 모두 다음 체크포인트 전에 주운 유물의 처리에 관해 한 번 질문했다. 이어 같은 질문에 대한 두 가지 사용자 답을 별개 상황으로 제공했다. 즉시 유지한다는 답에는 이어하기 후 유물 보유 수량이 하나이고 다시 주울 수 없어야 한다고 인계했다. 되돌린다는 답에는 원래 자리에서 다시 주울 수 있어야 한다고 인계했다. 양쪽 모두 마지막 체크포인트 위치를 보존했다. 피드백 접수 기준이 주어진 요청과 단순 메뉴 오탈자에는 둘 다 되묻지 않았다.

이번 시험은 질문과 구현 인계 내용을 확인했다. 이 사례들에서는 기존 지침 대비 개선이 관찰되지 않았다. 두 개발 스킬에서 명시적 규칙을 시범 적용하며, 실제 구현 결과와 재작업 변화는 아직 측정하지 않았다.

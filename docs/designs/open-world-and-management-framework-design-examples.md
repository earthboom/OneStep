# 오픈월드 RPG와 경영 시뮬레이션의 Unity·Unreal 설계 예시

| 장르 | 예시의 전제 | 프레임워크를 결정하는 계약 |
| --- | --- | --- |
| 오픈월드 RPG | 싱글플레이, 걸어서 오가는 연속 월드, 빠른 이동과 로컬 저장 | 지역을 내렸다가 다시 열어도 퀘스트와 중요 NPC의 상태가 이어진다. 목적지의 지형·충돌·진입점이 준비되면 이동을 확정한다. |

## 1. 오픈월드 RPG의 플레이와 계약

- **대표 흐름** — 마을에서 퀘스트를 받고 숲 초소로 간다. 교전으로 경비 NPC의 HP가 100에서 60으로 내려가고 퀘스트 단계가 갱신된다. 마을로 돌아가 숲의 표시 객체가 내려간 뒤에도 해당 상태는 이어진다. NPC에게 화면 밖 순찰이 요구되므로, 재방문하면 NPC의 새 위치와 HP 60이 함께 반영된다.
- **실패 흐름** — 폐광으로 빠른 이동을 요청하고 준비 중 다른 목적지를 선택한다. 지역 로더는 최신 요청의 목적지가 준비될 때까지 플레이어와 출발 지역을 유지한다. 오래된 로드가 나중에 끝나면 그 요청의 참조만 정리한다. 목적지 로드가 실패하면 출발 위치와 진행 상태를 보존하고 실패 이유를 전달한다.
- **시간과 상태** — 근접 전투와 이동은 엔진 월드에서 진행한다. 중요 NPC의 HP·생존·지역·다음 일정과 퀘스트 단계는 월드 세션의 게임 상태에 남긴다. NPC가 내려갈 때 잔여 일정을 월드의 게임 시간으로 기록하고, 화면 밖에서는 예정 사건만 진행한다. 정해진 시각을 지난 사건은 한 번 반영하고 다음 시각을 갱신한다. 장식용 군중은 지역의 인구 규칙에 따라 재구성할 수 있다.

```text
지역 저작 데이터 ──등록──> 월드 세션의 지역 목록
                              │
이동 요청 ──> 로딩과 준비 확인 ──> 플레이어 이동 확정
                              │
NPC 식별자 ──> 월드 세션의 권한 상태 ──> 로드된 NPC 표시 객체
```

저장에는 월드와 콘텐츠를 해석할 안정적인 ID, NPC의 지속 상태, 퀘스트 단계, 월드 게임 시각, 마지막 확정 진입점을 기록한다. 살아 있는 Actor나 GameObject 참조는 로드한 상태에 다시 연결한다. 지역·NPC 정의를 폐기할 때는 기존 저장의 ID를 교체·유지하거나 오류를 표시하는 규칙을 먼저 정한다. [월드 런타임 설계](../../skills/vegabond-code-design/references/world-lifecycle.md)

### Unity에서의 선택

| 결정 | 설계 |
| --- | --- |
| 프레임워크 | **지속되는 시작 씬과 지역별 비동기 additive 씬.** 시작 씬이 월드 세션, 플레이어와 지역 로더를 조립한다. 플레이어가 경계에 접근하면 로더가 지역 씬을 요청한다. 빠른 이동은 대상 씬, 진입점, 충돌 준비를 확인한 뒤 완료한다. |
| 상태 소유권 | 시작 씬의 월드 세션이 NPC·퀘스트 상태와 화면 밖 일정의 수명을 관리한다. 지역 씬의 NPC 뷰는 안정적인 NPC ID로 상태를 연결하고 교전 결과를 소유자에 전달한다. 뷰를 해제할 때 전투 결과나 퀘스트 상태를 다시 초기화하지 않도록 생성과 연결의 책임을 구분한다. 저장 담당은 안정된 시점에 월드 세션에서 저장 스냅샷을 얻는다. |
| 콘텐츠 추가 경로 | **숲 초소 A → 폐광 B.** B의 씬, 퀘스트·NPC 배치·시간표 `ScriptableObject`, 진입점과 지역 연결을 작성한다. 지역 ID·NPC ID·진입점·참조 유효성을 확인한 뒤 지역 카탈로그에 B를 등록하고 프로젝트의 빌드 대상에 씬을 포함한다. 로더가 지역을 열고, 퀘스트·NPC 상태 소유자가 해당 정의를 초기화 또는 복원한다. |

초기 지역은 같은 빌드의 씬으로 묶는다. 지역별 패치, 원격 배포 또는 독립적인 에셋 수명 관리가 요구되면 Addressables를 검토한다. 두 지역 사이에 필요한 공용 자원이나 퀘스트 연결은 카탈로그나 월드 조립에서 명시한다. [Unity additive Scene](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/scenemanagement/loadscenemode/additive) · [Unity 비동기 씬 로딩](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/scenemanagement/scenemanager/loadsceneasync) · [Addressables의 메모리 관리](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/MemoryManagement.html)

### Unreal에서의 선택

| 결정 | 설계 |
| --- | --- |
| 프레임워크 | **하나의 연속 월드와 World Partition.** 플레이어가 이동할 때 스트리밍 소스가 주변 셀을 요청한다. 빠른 이동은 필요하면 목적지에 임시 스트리밍 소스를 두고 목적지 셀과 게임플레이 진입점의 준비를 확인한 뒤 진행한다. `PlayerController`가 이동 의도를 전달하고 `Character`가 현재 이동과 충돌을 처리한다. |
| 상태 소유권 | `UWorldSubsystem`이 해당 월드의 중요 NPC와 퀘스트 기록을 소유한다. 셀의 NPC Actor는 고정 ID로 연결하며, Actor가 제거되면 구독·진행 중인 표시 작업을 정리한다. 화면 밖 일정은 서브시스템의 월드 시계 기준으로 처리한다. 월드가 닫힐 때 해당 상태를 폐기하고, 다음 실행에서는 저장 스냅샷을 해석한다. |
| 콘텐츠 추가 경로 | **숲 초소 A → 폐광 B.** 같은 월드에 B의 지형·Actor·진입점을 배치하고 지역 Data Asset에 퀘스트, NPC 정의, 연결과 진입점 ID를 기록한다. 참조·ID·진입점을 검증하고 지역 목록에 B를 추가한다. 물리적 셀 위치는 월드가 담당하고, 퀘스트와 영속 ID 등록은 지역 카탈로그가 담당한다. |

폐광이 독립 맵이 되는 요구가 생기면 월드 간 이동과 저장 상태 인계를 다시 정한다. 원거리 표현 비용이 예산에 영향을 주면 HLOD를 검토하고, 표현 LOD와 NPC 시뮬레이션 정책은 각각 결정한다. [Unreal World Partition과 스트리밍 소스](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine) · [Unreal Subsystem](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/USubsystem) · [Unreal Data Validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine)

### 콘텐츠에서 바뀌는 것과 설계 조건

폐광에 기존 매복·회수 퀘스트의 배치 변형을 추가할 때는 지역·배치·퀘스트 정의를 사용한다. 예를 들어 폐광에서 연결된 지하 통로를 통해 NPC가 다른 지역으로 이동하는 새 규칙을 추가하면, 이동 가능 경로와 화면 밖 일정, 재등장 위치를 해석하는 월드 규칙을 함께 바꾼다. 공용 시스템이나 A 에셋까지 수정되는 지점이 생기면 필요한 공유 계약이 무엇인지 확인한다.

## 2. 경영 시뮬레이션의 플레이와 계약

- **대표 흐름** — 제재소가 목재로 판자를 생산한다. 플레이어가 판자 재고를 보고 가구 공방을 배치한다. 공방이 재고와 출력 공간을 예약하면 작업을 시작한다. 판자가 완성된 틱의 마지막 단계에서 재고를 갱신하고 다음 틱부터 공방이 새 판자를 사용할 수 있다.
- **실패 흐름** — 판자를 한 공방만 사용할 수 있는 상황에서 두 공방이 같은 틱에 생산을 요청한다. 건물 ID 순서로 재고를 예약하므로 먼저 처리한 공방이 시작하고 나머지는 재고 대기 상태가 된다. 출력 창고가 차 있으면 작업을 시작하지 않는다. 진행 중 건물을 철거하면 해당 작업과 예약을 해제한다.
- **시간과 소유권** — 마을 시뮬레이션이 고정 길이의 논리 틱을 한 번씩 진행한다. 각 틱은 접수한 명령 반영 → 사용할 재고와 용량 예약 → 작업 진행 → 완료된 산출물 반영 순으로 처리한다. 배속은 일정 시간에 진행할 틱의 수를 바꾼다. 정지 중 접수된 건설 명령은 대기하며 재개 후 다음 틱에 처리된다.

```text
건설·운영 명령 ──> 시뮬레이션 ──> 확정 상태와 결과 ──> 마을 화면·재고 UI
                    │
             틱 순서·재고 예약·생산 진행
```

마을 시뮬레이션이 건물 배치·재고·주문·작업 진행·예약의 유일한 쓰기 경로다. 저장은 틱 경계에서 만들며 틱 번호, 건물과 레시피 ID, 재고와 진행 및 예약, 이미 접수한 대기 명령의 순서를 보존한다. 한 프레임에 처리할 틱을 제한하면 남은 틱을 이후 프레임으로 넘기고 순서를 유지한다. 화면에 보이는 건물과 작업자 애니메이션은 확정된 상태를 표시한다.

### Unity에서의 선택

| 결정 | 설계 |
| --- | --- |
| 프레임워크 | **순수 C# 마을 시뮬레이션과 Unity 표시 계층.** 시작 씬이 시뮬레이션, 시간 공급, 건설 입력, 마을 표시를 연결한다. 시뮬레이션 시간 담당이 프레임 경과 시간을 받아 논리 틱을 진행하고, `MonoBehaviour`와 UI는 스냅샷을 읽는다. |
| 상태 소유권 | 세션이 시뮬레이션 객체를 소유한다. 그 객체가 생산·재고·예약을 기록하며 건설 UI는 명령을 보낸다. 개별 건물 프리팹을 로드하거나 교체할 때 생산 상태는 세션에 남는다. 다른 마을을 열면 해당 세이브에서 마을 시뮬레이션을 구성한다. |
| 콘텐츠 추가 경로 | **제재소 A → 가구 공방 B.** `ScriptableObject`로 건물 정의와 레시피를 저작하고 표현 프리팹을 연결한다. 재료·산출물 ID, 수량, 제작 틱, 프리팹 참조를 검증한다. 건설 메뉴가 읽는 카탈로그에 B를 등록한다. 기존 생산 규칙이 B에서 판자를 소비하고 가구를 생산한다. |

엔진 독립 규칙의 의존 방향을 고정할 필요가 있으면 별도 `.asmdef`를 둔다. 배속에서 생산 계산이나 많은 표시 객체의 갱신이 예산을 넘으면 비용이 드는 경로를 구분한 뒤 Jobs·Burst·Entities를 검토한다. [Unity ScriptableObject](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/scriptableobject) · [Unity 어셈블리 설정](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/script-compilation/assembly-definition-files/class-assembly-definition-importer)

### Unreal에서의 선택

| 결정 | 설계 |
| --- | --- |
| 프레임워크 | **일반 C++ 마을 시뮬레이션을 소유하는 `UTickableWorldSubsystem`.** 서브시스템이 월드 시간과 논리 틱 진행을 연결한다. `PlayerController`가 건설 입력을 받고, 건물 Actor·UMG가 스냅샷을 표시한다. 생산 시뮬레이션의 순서를 논리 틱에서 한곳에 관리한다. |
| 상태 소유권 | 서브시스템이 월드 단위 시뮬레이션 객체를 소유하고 월드 종료 시 해제한다. 건물 Actor의 교체는 같은 설계 상태를 다시 표시한다. 마을을 다시 열면 저장 데이터에서 건물 ID·진행·예약을 복원하고 뷰를 연결한다. |
| 콘텐츠 추가 경로 | **제재소 A → 가구 공방 B.** 건물·레시피 Data Asset에 자원과 수량, 제작 틱, 표현 Blueprint를 작성한다. 자원 ID와 생산 제약, 에셋 참조를 검증하고 건설 카탈로그에 B를 등록한다. 건설 명령이 B를 배치하면 기존 C++ 생산 규칙이 등록된 레시피를 사용한다. |

다수 건물이나 작업자의 비용이 문제가 될 때 생산 모델과 표시·이동 비용을 분리해 관찰한다. 작업자 이동이나 대량 표현이 병목이면 Mass를, 생산 틱 계산이 병목이면 데이터 접근과 작업 순서를 각각 검토한다. [Unreal Tickable World Subsystem](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UTickableWorldSubsystem?application_version=5.8) · [Unreal Mass Gameplay](https://dev.epicgames.com/documentation/unreal-engine/overview-of-mass-gameplay-in-unreal-engine)

### 콘텐츠에서 바뀌는 것과 설계 조건

기존 투입·산출·제작 시간만 달라지는 공방은 건물과 레시피 정의로 추가한다. 전력 공급이 중단될 때 생산이 멈추고 복구된 뒤 이어지는 기능은 새 규칙이다. 전력 공급 상태의 소유자, 생산 재개 시점, 작업 진행과 예약을 보존할지 결정한 뒤 생산 틱에 배치한다.

## 3. 설계에서 확인할 내용

| 조건 | 기대하는 동작 |
| --- | --- |
| RPG에서 교전 후 지역 언로드와 재진입 | 같은 NPC ID의 HP 60과 퀘스트 단계가 유지된다. 화면 밖 순찰은 예정 횟수만큼 한 번씩 반영된다. 새 뷰는 그 상태와 위치를 표시한다. |
| RPG에서 빠른 이동 요청이 바뀌거나 로드가 실패 | 오래된 로드가 끝나도 현재 목적지가 바뀌지 않는다. 최신 목적지가 준비된 후 이동하고, 실패 시 출발 위치와 진행 상태를 보존한다. |
| 경영에서 재고 부족·만석·철거 | 공방 두 곳이 마지막 재료를 중복 예약할 수 없다. 출력 공간이 없으면 재료가 보존된다. 철거 후 해당 작업의 예약이 재고와 용량 계산에 남지 않는다. |
| 경영에서 배속 또는 저장 복원 | 동일 명령을 동일 논리 틱에 적용했을 때 배속에 관계없이 재고·예약·생산 진행이 같다. 작업 중 저장을 다시 읽어도 재료가 중복 차감되거나 결과가 중복 생산되지 않는다. |
| 두 장르에서 두 번째 콘텐츠 등록 | 폐광과 공방이 각각 어디에서 저작·검증·등록되고 어떤 공용 계약을 사용하는지 설명할 수 있다. 새 규칙이 필요하다면 변경될 소유자와 기존 콘텐츠에 미칠 영향을 지목할 수 있다. |

각 항목은 설계에서 기대하는 동작이다. 실제 프로젝트의 장르·플랫폼·저장 범위에 맞춰 필요한 항목을 확인 계획으로 사용한다.

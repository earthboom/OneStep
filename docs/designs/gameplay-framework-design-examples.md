# 턴제 전술과 실시간 협동 액션의 Unity·Unreal 설계 예시

[게임 개발 기본 전략](game-development-strategy.md)의 세 가지 결정을 두 장르에 적용한다. 장르마다 같은 플레이 요구를 두 엔진에 맞춰 배치했다. 아래 타입과 에셋 이름은 설계상 역할을 가리킨다. 프로젝트별 엔진 버전과 플랫폼이 정해지면 지원 기능과 비용을 확인한다. [새 게임의 기반 설계 지침](../../skills/vegabond-code-design/references/gameplay-framework.md#plan-a-new-game-foundation)

| 장르 | 가정 | 프레임워크 선택을 좌우하는 계약 |
| --- | --- | --- |
| 턴제 전술 | 싱글플레이, 격자 전투, 턴 중 안정된 시점에 저장 | 명령마다 규칙을 일정한 순서로 적용하고, 실패한 명령은 전투 상태를 보존한다. 보드 표시를 교체하고도 같은 전투 상태를 읽을 수 있다. |
| 실시간 협동 액션 | 2–4인, 플레이어 한 명이 호스트인 매치, 기본 이동·사격·구조·재스폰 | 호스트가 피해와 구조를 최종 판정한다. 로컬 연출은 입력에 바로 반응할 수 있고, 매치 진행은 개인 아바타 교체와 독립적으로 이어진다. |

## 1. 턴제 전술의 플레이와 계약

- **대표 흐름** — 행동력 2인 유닛이 한 칸 이동해 행동력 1을 쓰고, 사격으로 남은 1을 쓴다. 플레이어가 턴 종료를 선택하면 적 행동을 유닛 ID 순서로 처리하고 다음 턴의 입력을 연다.
- **실패 흐름** — 점유된 칸 이동이나 사거리 밖 사격은 거부한다. 점유·체력·행동력·턴 번호는 거부 전과 같아야 한다. 이동과 사격이 각각 승인되는 명령이므로 두 번째 명령이 거부돼도 앞서 확정된 이동은 보존한다.
- **시간과 소유권** — 하나의 전투 규칙 객체가 격자 점유, 유닛 상태, 행동력, 턴을 함께 소유한다. 승인한 명령이 전투를 진행시키며, 애니메이션 재생 시간은 입력 가능 여부와 표시를 조절한다. 저장 스냅샷은 승인된 명령의 처리가 끝난 시점에 얻고, 조우 ID와 규칙 상태를 기록한다.

### Unity에서의 선택

| 결정 | 설계 |
| --- | --- |
| 프레임워크 | **순수 C# 턴 규칙과 얇은 `MonoBehaviour` 연결.** 입력은 보드의 셀 ID를 선택하고 `TacticsMatch`에 이동·사격·턴 종료 명령을 전달한다. 보드 씬의 프리팹과 UI는 명령 결과와 읽기 스냅샷을 소비한다. 엔진 프레임은 표시와 입력 타이밍을 담당한다. |
| 상태 소유권 | 전투 동안 유지되는 세션 오브젝트가 `TacticsMatch`를 소유한다. 보드 씬은 격자 표시 오브젝트와 유닛 뷰만 소유한다. 보드 씬을 교체하면 새 뷰가 현재 스냅샷에 연결되고, 전투 종료 시 세션이 규칙 객체를 폐기한다. 저장은 버전이 있는 별도 스냅샷으로 처리한다. |
| 콘텐츠 추가 경로 | **훈련 격자 A → 창고 격자 B.** B의 맵 정의, 셀 점유, 적 배치, 승리 조건을 `ScriptableObject` 정의와 보드 프리팹에 작성한다. 좌표·중복 ID·배치 참조를 확인하고 같은 조우 카탈로그에 B만 등록한다. 보드 로더가 B를 조립하고 기존 턴 규칙이 처리한다. A와 B는 공용 유닛 정의를 참조한다. |

셀 배치, 수치, 기존 유형의 목표 조합은 정의로 추가한다. 적의 이동 도중 공격하는 **기회 사격**을 도입하면 명령 처리 순서를 소유한 규칙 모듈에 반응 순서와 실패 계약을 추가한다. 엔진 독립 규칙을 여러 씬이나 테스트에서 사용하면서 의존 방향을 지킬 필요가 생기면 `No Engine References`를 사용한 `.asmdef`를 검토한다. [Unity ScriptableObject](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/scriptableobject) · [Unity 어셈블리 설정](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/script-compilation/assembly-definition-files/class-assembly-definition-importer)

### Unreal에서의 선택

| 결정 | 설계 |
| --- | --- |
| 프레임워크 | **일반 C++ 턴 규칙과 Unreal Gameplay Framework.** `PlayerController`가 셀 선택을 명령으로 전달한다. 해당 전투 월드의 `UWorldSubsystem`이 C++ 규칙 객체를 소유한다. `GameMode`는 선택한 조우를 읽어 전투를 시작하는 조립점으로 쓴다. 보드 Actor와 Blueprint는 입력 연결과 결과 연출을 맡는다. |
| 상태 소유권 | 규칙 객체가 격자·유닛·턴을 변경하는 경로다. 표시 Actor의 교체나 같은 월드 안에서의 보드 연출 재구축은 규칙 객체의 수명에 영향을 주지 않는다. `UWorld` 종료 시 전투 객체를 폐기하고, 월드를 다시 열어 이어갈 때는 저장 스냅샷을 해석해 복원한다. |
| 콘텐츠 추가 경로 | **훈련 격자 A → 창고 격자 B.** 조우 Data Asset에 격자 크기, 점유 셀, 유닛 정의, 배치, 목표를 작성하고 선택할 보드 Blueprint를 연결한다. 등록 목록에서 중복 ID와 배치 유효성을 확인한 뒤 B 항목을 추가한다. `GameMode`가 해당 정의를 전투 월드에서 조립한다. A의 Blueprint나 조우 에셋은 공용 계약을 통해 독립적으로 동작한다. |

초기 조우는 한 게임 모듈과 명시적인 등록 목록으로 구성한다. 독립적으로 배포하거나 필요할 때만 로딩해야 하는 조우가 생기면 Asset Manager의 등록·로딩 경계를 검토한다. 화면 내 충돌이나 애니메이션이 격자 판정에 영향을 줘야 하는 기능이 생기면 그 의미를 턴 규칙 계약에 연결한다. [Unreal Gameplay Framework](https://dev.epicgames.com/documentation/unreal-engine/gameplay-framework-in-unreal-engine) · [Unreal Subsystem](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/USubsystem) · [Unreal Asset Manager](https://dev.epicgames.com/documentation/en-us/unreal-engine/asset-management-in-unreal-engine)

## 2. 실시간 협동 액션의 플레이와 계약

- **대표 흐름** — 플레이어가 사격 입력을 보내면 자기 화면에서 발사 연출이 시작된다. 호스트는 요청자의 현재 아바타·탄약·재발사 시점과 적중을 확인하고, 승인된 피해와 탄약을 반영한다. 참가자는 공유 상태나 결과를 받아 적의 체력과 자기 탄약을 표시한다.
- **중단 흐름** — 플레이어가 쓰러진 동료를 구조하다가 연결이 끊기거나 거리를 벗어나면 호스트가 진행 중인 구조를 종료한다. 대상은 계속 쓰러진 상태다. 다른 플레이어는 같은 구조 규칙으로 다시 시도할 수 있다. 매치 중 한 대상의 구조는 한 건만 진행한다.
- **권한과 수명** — 호스트의 매치 상태는 공동 목표와 웨이브를, 참가자 상태는 역할·선택 장비·기여도를, 아바타는 현재 체력·탄약·시전 상태를 책임진다. 재스폰하면 아바타 상태를 초기화하고 참가자 기록을 이어받는다. 매치 중 재접속을 지원하는 경우에는 참가자 식별, 이전 아바타 처리, 복원 범위를 별도로 정한다.

각 행동 요청은 현재 아바타의 식별자와 그 아바타에서 증가하는 명령 번호를 갖는다. 호스트는 연결이 그 아바타를 제어하는지와 번호를 이미 처리했는지를 확인한다. 유효한 사격만 탄약 차감과 피해를 한 번 확정한다. 재스폰할 때 아바타 식별자를 새로 부여해 이전 요청과 구별한다. 구조는 호스트가 대상마다 진행 기록을 하나만 두고, 완료 직전에도 대상·거리·구조자 상태를 다시 확인한다.

```text
클라이언트 입력 ──행동 요청──> 호스트의 검증·판정 ──상태·결과──> 참가자 UI와 연출
       └──────── 즉시 표시 가능한 발사·입력 피드백
```

### Unity에서의 선택

| 결정 | 설계 |
| --- | --- |
| 프레임워크 | **GameObject + Netcode for GameObjects의 호스트 권한 모델.** `NetworkManager`가 연결을 관리하고 시작 씬의 조립점이 매치 상태, 네트워크 플레이어와 아바타 프리팹을 연결한다. `NetworkBehaviour`가 요청과 공유 상태를 전달한다. 기본 이동은 호스트가 확인하고, 즉시 필요한 발사 연출은 로컬에서 시작한다. |
| 상태 소유권 | 서버 쪽 매치 객체가 목표와 웨이브를 기록한다. 호스트의 참가자 기록은 현재 아바타 프리팹의 생성·삭제와 별도 수명을 갖는다. 복제하는 체력·탄약·진행은 호스트가 쓰며 각 클라이언트는 자신의 UI와 연출을 소유한다. 진행 중 구조는 호스트의 상호작용 규칙이 완료 또는 취소한다. |
| 콘텐츠 추가 경로 | **기본 카빈 A → 중량 카빈 B.** B의 피해량, 재발사 간격, 탄창 크기, 표현 프리팹을 `WeaponDefinition`에 작성한다. 수치·프리팹 참조·ID를 검증하고 매치의 무기 카탈로그에 등록한다. 서버가 같은 카빈 발사 규칙으로 B를 판정한다. 네트워크에서 별도 생성되는 에셋을 추가할 때는 해당 프리팹 등록도 설계에 포함한다. |

이동의 즉시 반응과 보정이 핵심이 되면 목표 지연과 필요한 예측 수준을 정한 뒤 네트코드 선택을 다시 평가한다. 여기서는 발사 피드백과 최종 피해 판정을 구분한다. 지속 시간 동안 충전 상태가 쌓이는 무기를 추가하면 서버 행동 정책과 취소 규칙이 새로 필요하다. [Unity 네트코드 선택](https://docs.unity.com/multiplayer/netcode/netcode) · [Unity NetworkVariables](https://docs.unity.cn/Packages/com.unity.netcode.gameobjects%402.13/manual/basics/networkvariable.html) · [Unity 클라이언트 즉시 피드백](https://mp-docs.dl.it.unity3d.com/netcode/current/advanced-topics/client-anticipation/)

### Unreal에서의 선택

| 결정 | 설계 |
| --- | --- |
| 프레임워크 | **Unreal의 호스트 권한 복제와 `CharacterMovementComponent`.** `GameMode`가 서버의 매치 규칙과 승패를 운영하고, `GameState`가 공동 목표와 웨이브 상태를 참가자에게 공개한다. `PlayerController`·`Character`가 입력을 연결한다. 사격·구조의 검증과 권한 상태 변경은 서버의 게임플레이 컴포넌트에서 처리한다. |
| 상태 소유권 | `PlayerState`에 아바타 교체를 넘어 유지할 선택 장비와 기여도를 둔다. 현재 체력·탄약·시전은 `Character` 또는 소유 컴포넌트의 수명을 따른다. 클라이언트는 복제된 결과를 표시하고 자기 연출을 관리한다. 호스트의 구조 진행 기록은 대상의 유효성에 따라 완료되거나 정리된다. |
| 콘텐츠 추가 경로 | **기본 카빈 A → 중량 카빈 B.** B의 수치·장착 표현·공통 발사 규칙을 가리키는 무기 Data Asset을 작성하고 등록 목록에 추가한다. `GameMode`가 매치에 사용할 카탈로그를 선택하고 장비 컴포넌트가 B의 정의를 소비한다. 서버와 참가자가 같은 콘텐츠 ID를 해석하도록 지원 빌드와 필요한 패키지의 포함 조건을 정한다. |

기본 이동과 복제는 엔진의 캐릭터 경로를 활용한다. 여러 무기·장비·캐릭터 능력이 비용, 쿨다운, 효과, 태그, 예측을 같은 계약으로 써야 할 때 GAS를 검토한다. 무기의 충전·취소가 추가되면 우선 바뀌는 행동과 권한 계약을 적고 그 범위에 맞는 구조를 고른다. [Unreal GameMode와 GameState](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-mode-and-game-state-in-unreal-engine) · [Unreal 네트워크 캐릭터 이동](https://dev.epicgames.com/documentation/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine) · [Unreal GAS](https://dev.epicgames.com/documentation/unreal-engine/gameplay-ability-system-for-unreal-engine)

## 3. 설계에서 확인할 내용

| 조건 | 설계에서 기대하는 관찰 |
| --- | --- |
| 턴제의 점유된 칸과 실행 순서 | 점유된 칸 명령의 거부가 행동력을 소모하지 않는다. 승인된 이동과 사격의 순서가 보드 상태와 일치한다. 같은 전투의 보드 뷰를 교체해도 UI는 같은 턴·체력·점유를 읽는다. |
| 협동의 지연·중복·구조 중단 | 같은 행동 요청이 중복 도착해도 피해와 비용은 한 번 반영된다. 사격 요청이 재스폰 이전 아바타에서 출발했으면 호스트가 해당 아바타를 식별하고 거부한다. 구조자가 끊기면 진행 표시가 정리되고 대상은 계속 쓰러진 상태다. |
| 두 번째 콘텐츠 | B의 정의·표현·등록 위치를 지목할 수 있다. A와 B가 공용 규칙을 사용하는 흐름과 각 콘텐츠가 존재해야 하는 조건을 설명할 수 있다. 새 행동을 추가하는 경우 어떤 규칙과 기존 콘텐츠 계약이 영향을 받는지 설명할 수 있다. |

이 표는 설계의 기대 동작이다. 실제 프로젝트에서는 목표 플랫폼과 엔진 버전, 보드·매치 전환, 접속 범위, 콘텐츠 배포 조건을 확정한 뒤 해당하는 항목을 확인 계획으로 사용한다.

# Unity·Unreal 게임 개발 기본 전략

**장르의 핵심 플레이에서 시간·상태·권한·콘텐츠 계약을 도출하고, 그 계약에 맞는 엔진 기능으로 기본 코드 구조를 정한다.** 첫 설계에서 확정할 것은 게임 상태의 소유자, 규칙을 실행하는 시점, 콘텐츠를 추가하는 경로다. 최적화와 엔진 확장의 도입은 목표 기기와 대표 부하가 결정한다.

특정 게임과 플랫폼이 정해지기 전까지 적용할 기본안이다. 여기서 프레임워크는 개발팀이 여러 기능에 반복해 쓰는 상태 소유권, 실행 순서, 입력과 결과의 계약, 콘텐츠 조립 방식이다. 기준은 현재 게임에 맞는 첫 구조와 그 구조를 바꿔야 할 신호다.

## 1. 처음에 확정할 일곱 가지

| 설계 질문 | 결정할 내용 |
| --- | --- |
| 플레이어가 반복하는 행동은 무엇인가? | 입력 → 판정 → 피드백 → 다음 선택의 대표 흐름 두 개. 정상이 아닌 경우도 하나 넣는다. 예를 들어 공격 도중 취소되거나, 마지막 카드가 유효하지 않은 경우다. |
| 규칙은 언제 진행되는가? | 턴, 명시적 시뮬레이션 틱, 엔진 물리 스텝, 프레임, 이벤트 중 필요한 시간 기준을 고른다. 플레이 시간과 현실 시간이 함께 필요하면 각각의 기준과 일시정지·오프라인 처리 규칙을 기록한다. |
| 누가 어떤 상태를 변경할 수 있는가? | 인벤토리·전투·월드·매치의 상태 소유자와 판정 권한을 정한다. 멀티플레이는 클라이언트 입력, 권한 상태, 보여줄 복제 상태를 구분한다. |
| 무엇이 얼마나 오래 살아야 하는가? | 객체, 씬·월드, 매치·런, 플레이어 프로필, 디스크에 저장되는 진행의 수명을 각각 적는다. 씬 전환, 재스폰, 재접속, 앱 종료에서 유지될 값을 고른다. |
| 가장 자주 추가할 콘텐츠는 무엇인가? | 두 번째 무기·카드·방·퀘스트를 누가 어느 도구에서 추가하는지 정한다. 정의의 검증·등록·참조·배포 지점을 정하고 바뀌는 의미가 코드 정책인지 데이터 값인지 판단한다. |
| 어디에서 얼마만큼 동작해야 하는가? | 최소·대표 기기, 화면과 목표 프레임, 동시 NPC와 플레이어 수, 메모리·로딩 예산, 월드 이동 방식, 배포 및 패치 조건을 정한다. 미정인 수치는 미정으로 기록한다. |
| 기존 작업에서 지켜야 할 계약은 무엇인가? | 실제 진입점, 기존 데이터·저장·에셋·네트워크 형식, 사용 중인 호출자와 오류 동작을 기록한다. 기존 상태에서 기능을 추가할 때 영향을 받는 계약부터 확인한다. |

장르가 혼합된 경우 플레이 모드별로 위 질문을 적용한다. 예를 들어 실시간 탐색과 턴제 전투를 합치면 탐색은 엔진 이동과 물리를 따르고, 전투는 턴 상태를 따를 수 있다. 양쪽은 파티와 인벤토리 등 실제로 공유해야 할 상태만 약속하고, 전환 시 넘길 자원과 취소 조건을 명시한다.

## 2. 장르별 출발점

| **싱글 실시간 액션·플랫폼** | 입력 의도, 이동/물리, 공격의 시작·취소·종료, 판정 상태와 연출의 연결 | Input System과 `MonoBehaviour` 조합, 프로젝트의 물리 갱신 규칙, Prefab 조립 | Enhanced Input, `Pawn`·`Character`, `ActorComponent`, 애니메이션 연동. 여러 능력이 같은 비용·효과·태그 규칙을 요구하면 GAS 검토 |
| **세션 기반 협동·경쟁** | 판정 권한, 매치·플레이어·아바타 상태의 수명, 지연에 민감한 행동의 표현과 정정 | GameObject 기반 프로젝트라면 Netcode for GameObjects를 후보로 두고 서버와 클라이언트 수명을 정함. Entity 기반 시뮬레이션이나 예측 요구가 있으면 Netcode for Entities까지 비교 | `GameMode`에 서버의 매치 흐름, `GameState`에 공유 매치 상태, `PlayerState`에 플레이어 상태, Pawn에 현재 아바타 상태. 예측·보정은 실제 필요한 행동을 기준으로 설계 |
| **퍼즐·어드벤처·런 기반 게임** | 방·조우·런의 소유자, 콘텐츠 등록, 퀘스트·룰 변화와 진행의 경계 | Scene·Prefab·정의 에셋의 조립점, 필요한 경우 additive Scene과 지역별 로딩 | Level·Data Asset·Blueprint 조립, 월드와 런에 맞는 소유자. 콘텐츠가 독립 배포되는 경우에만 적합한 패키지 경계 검토 |
| **오픈월드·지속형 RPG** | 지역 표현과 진행 상태의 분리, 저장 ID, 화면 밖 세계의 계약, 이동 경로별 로딩 예산 | Zone별 Scene 또는 Addressables, 세션 상태와 Prefab 표시 객체 분리 | World Partition 또는 Level Streaming을 월드 제작·이동 조건에 맞게 고름. 필요한 런타임 상태는 Actor 수명과 분리 |
| **전략·대량 시뮬레이션** | 시뮬레이션 틱과 업데이트 순서, 상태의 읽기·쓰기 권한, 시각화와 게임 규칙의 갱신 비용 | 단순 관리 배열 또는 C# 시뮬레이션부터 구성하고, 실제 데이터 병목에 맞춰 Jobs·Burst·Entities 검토 | 시스템별 접근 패턴과 비용을 계측하고, 대량 개체 배치·처리 요구에 맞춰 Mass 검토. 플레이어·표시 Actor와 시뮬레이션 해상도 구분 |

엔진 선택은 목표 플랫폼과 배포 조건, 팀의 제작 도구 숙련도, 핵심 플레이에서 재사용할 엔진 기능, 향후 콘텐츠 작업의 복잡도로 비교한다. 팀이 이미 도입한 프로젝트에서 엔진을 계속 쓸 수 있다면 그 위에서 프레임워크를 선택한다. 표의 후보를 골라도 엔진의 버전과 패키지 지원은 프로젝트를 정할 때 확인한다. ## 3. 기본 코드 구조의 규칙

1. **하나의 상태에 하나의 쓰기 소유자를 둔다.** UI·연출·다른 기능은 결과를 읽거나 명령을 보낸다. 인벤토리의 슬롯 배열, 전투의 임시 캐시, 새로 계산할 수 있는 표시 값은 그 소유자 안에 둔다. 호출자가 알아야 할 것은 입력·결과·실패·순서·수명이다.
2. **기능을 플레이 책임 기준으로 묶는다.** 전투·인벤토리·진행처럼 함께 바뀌는 규칙, 상태, 정의, 확인을 가까이 둔다. 공유 코드는 실제로 같은 보장과 변경 이유를 가진 경우에 올린다. `Core`를 만들게 되면 기능 소유자를 찾을 수 없는 코드가 쌓이는지 주기적으로 살핀다.
3. **기능의 의존성과 조립점을 보이게 만든다.** 모드 또는 씬의 조립점이 필요한 기능을 선택하고 연결한다. 독립적으로 선택 가능한 기능은 형제 기능의 코드·에셋·이벤트를 직접 요구하지 않도록 한다. 의도된 통합은 조립점이나 작은 통합 모듈에 둔다. 빌드 참조, 에셋 참조, 런타임 등록·이벤트도 함께 확인한다.
4. **기존 엔진 기능을 수명과 역할에 맞게 쓴다.** 월드·물리·애니메이션·네트워크 같은 엔진 동작은 해당 엔진 객체에서 다룬다. 규칙을 엔진과 분리하면 테스트·재생·재사용이 쉬워지는 경우 독립 C#·C++를 사용한다. 상속은 엔진 계약이나 실제 대체 가능성이 있는 경우에 쓰고, 독립적으로 바뀌는 능력·정책은 조합한다.
5. **호출 방식에 실행 계약을 반영한다.** 특정 대상이 반드시 처리해야 하고 즉시 결과가 필요한 일은 대상이 보이는 요청으로 구성한다. 하나의 상태 변경을 UI·오디오·분석이 독립적으로 관찰해야 하면 이벤트를 검토한다. 구독자 생존 기간과 처리 순서가 품질에 영향을 주면 계약으로 남긴다.
6. **경계가 실제로 커질 때 빌드 단위를 분리한다.** Unity는 관련 폴더와 공개 타입을 먼저 정리하고, 의존 방향을 기계적으로 지킬 필요가 생기면 `.asmdef`로 분리한다. Unreal은 먼저 적절한 Gameplay Framework 클래스와 현재 모듈 경계를 이용하고, 독립 빌드·배포·선택이 필요하면 모듈이나 플러그인을 검토한다. [Unity Assembly Definition](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/script-compilation/assembly-definition-files/class-assembly-definition-importer) · [Unreal 모듈](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules)

```text
입력·엔진 콜백 ──요청──> 기능의 규칙과 상태 소유자 ──결과──> UI·애니메이션·오디오
                               │
                    정의 데이터 조회 · 저장 스냅샷

씬·월드·매치의 조립점이 필요한 기능과 엔진 객체를 연결한다.
```

Unity에서는 저작용 정의, 생존 기간이 정해진 씬·세션 객체, 플레이어 세이브를 분리한다. Unreal에서는 매치·월드·플레이어·액터 중 요구에 맞는 수명에서 상태를 소유한다. 예를 들어 캐릭터를 교체해도 남아야 하는 점수를 Pawn에 두면 재스폰 계약이 어긋난다. 다음 장면까지 남는 것과 프로세스를 다시 시작해도 남는 것을 각각 결정한다. [Unity ScriptableObject](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/scriptableobject) · [Unreal Gameplay Framework](https://dev.epicgames.com/documentation/unreal-engine/gameplay-framework-in-unreal-engine)

## 4. 데이터·렌더링·자원·AI 기본 정책

| 주제 | 출발 정책 | 출발 정책을 바꿀 조건 |
| --- | --- | --- |
| **데이터 추가·수정·삭제** | 저작 정의, 파생 빌드 산출물, 런타임 상태, 영속 저장을 수명별로 관리한다. 저장이나 외부 참조에 노출되는 항목은 안정적 ID를 갖는다. 추가는 검증 후 등록하고, 의미나 스키마를 바꿀 때 기존 데이터에 필요한 변환을 정한다. 삭제 전에 현재 참조를 확인하고 폐기 표식·교체 ID·명시적 오류 중 정책을 정한다. | 저장 배포, 모드, 라이브 밸런스, 다중 플랫폼, 독립 패치를 지원할 때 카탈로그 버전, 세션 고정, 구버전 지원 범위를 구체화한다. |
| **렌더링** | 대표 기기에서 프레임 예산과 시각 기준을 정한다. 오브젝트·재질·조명·그림자의 콘텐츠 예산을 둔다. 실제 병목이 나타나면 CPU 제출, GPU 패스, 로딩·업로드를 구별해 해당 비용을 줄인다. | 제출 병목이면 인스턴싱·배칭, 가림 구조가 유효하면 컬링, 거리별 상세 비용이면 LOD·HLOD, 해상도 민감 GPU 병목이면 렌더 해상도·패스 조정이 후보가 된다. |
| **생성·풀·캐시·스트리밍** | 보통 객체는 필요한 때 생성하고 소유자의 수명에 맞춰 해제한다. 동일한 정의·리소스는 공유할 수 있다. 준비와 해제 책임을 명시한다. | 빈번한 생성이 끊김을 만들면 상한과 리셋 계약이 있는 풀을 검토한다. 동일 결과를 자주 다시 계산하면 무효화와 용량 한도가 있는 캐시를 검토한다. 전체 상주가 예산을 넘거나 지역 이동으로 필요한 자원이 달라지면 스트리밍·미리 로딩을 검토한다. |
| **몬스터·NPC AI** | 감지, 판단에 사용한 기억, 결정, 행동 실행을 구분한다. 명확한 모드는 상태 머신부터 시작하고, 우선순위와 중단이 중요한 많은 행동은 Behavior Tree, 점수 비교가 필요하면 Utility, 행동 순서를 구성해야 할 때는 GOAP·HTN을 검토한다. | 행동 수, 판단 근거, 실패·중단 처리, 디자이너의 편집 비용이 커질 때 도구와 인터페이스를 바꾼다. 값만 다른 몬스터는 정의로, 행동 규칙이 다른 경우에는 적합한 정책이나 행동을 추가한다. |
| **화면 밖 객체** | 렌더, 애니메이션, 충돌, AI, 네트워크 관련성, 메모리 상주를 각각 판단한다. 플레이 중 이어져야 할 퀘스트·전투·이동 상태의 소유자를 씬 표현의 수명에서 분리한다. | 의미 있는 화면 밖 사건이 있으면 이벤트 또는 낮은 빈도의 계산으로 진행을 유지한다. 시뮬레이션을 멈출 수 있는 장식 객체는 해제하거나 재구성한다. 전투와 다중 관찰자는 거리 외의 중요도 조건으로 반영한다. |

기술 도입을 기록할 때는 **문제와 목표, 선택한 기술, 유지할 플레이·데이터 계약, 다시 판단할 조건**을 한곳에 둔다. 예를 들어 화면 밖 NPC 수가 많아도 상태 전이가 저렴하고 프레임 여유가 충분하다면 단순 스케줄로 시작할 수 있다. 반대로 퀘스트가 다른 지역의 이동 결과에 의존한다면 화면 밖에도 필요한 상태와 진행 방식을 설계한다. ## 5. 프로젝트 시작 순서와 기본 설계의 완료 기준

1. **플레이와 제약을 적는다.** 대표 흐름 두 개, 가장 자주 추가할 콘텐츠, 팀 역할과 실제 사용 도구, 배포 요구를 정한다. 현재 조건에서 프레임워크 선택에 영향을 주는 미정 사항을 남긴다.
2. **프로젝트의 기술 기준선을 정한다.** 엔진·버전·주 언어, 에셋 버전 관리, 패키지 의존, 목표 플랫폼·빌드, 장르상 필수 런타임 기능을 기록한다. 장기 지원과 도구 호환성에 영향을 주는 결정은 적용 조건을 같이 남긴다.
3. **상태 소유와 조립을 그린다.** 기능마다 누가 상태를 만들고 쓰고 파기하는지, 입력과 결과가 어디를 통과하는지, 네트워크에서는 누가 판정하는지 표시한다. 첫 기능을 구현할 때 사용할 기존 엔진 위치와 맞춘다.
4. **첫 콘텐츠와 두 번째 콘텐츠의 추가 경로를 설계로 따라간다.** 예를 들어 새 카드의 수치와 새 효과가 각각 어디에서 바뀌는지, 그 카드 없이 기본 플레이를 조립할 수 있는지 확인한다. 기존 카드의 코드·에셋까지 수정해야 한다면 그 이유를 설명한다.
5. **보존 계약을 작업 요청에 남긴다.** AI에게 코드를 맡길 때 바꿀 행동, 유지할 행동·저장·에셋, 상태 소유자, 허용 의존 방향, 실제 관찰 방법을 같은 작업 브리프에 붙인다. 작은 수정은 영향을 받는 항목만 적는다. [게임플레이 프레임워크 설계 절차](../../skills/vegabond-code-design/references/gameplay-framework.md) · [AI 코드 변경 검수](../../knowledge/code/K-CODE-AI-CHANGE-QUALITY.md)

기본 설계는 팀원이 아래 내용을 같은 답으로 설명할 수 있을 때 프로젝트의 개발 기준으로 삼는다.

- 플레이 요청이 어느 인터페이스로 들어가며, 상태는 어디에 기록되는가?
- 다음 콘텐츠는 어느 파일이나 저작 화면에서 추가하고, 무엇이 자동으로 등록되는가?
- 가까운 씬에서 멀어지거나 유저가 다시 접속하면 어떤 상태가 살아남는가?
- 기능과 자산의 의존 방향이 어긋났을 때 어느 부분에서 발견하는가?
- 프레임·메모리·로드 예산에 문제가 생기면 어떤 경로에서 무엇을 관찰해 기술 선택을 다시 판단하는가?

## 6. 같은 규칙이 다른 프로젝트로 이어지는 예

**싱글 턴제 덱빌더**라면 처음 정할 프레임워크는 덱·손패·턴의 규칙, 런의 상태 소유자, 카드 정의 등록과 저장 ID다. 연출은 턴 결과를 소비한다. 두 번째 카드가 기존 효과를 조합한다면 정의만 추가한다. 다른 카드가 턴 순서 자체를 바꾸면 그 규칙을 소유하는 모듈을 수정하고 기존 카드의 결과를 보존할 범위를 적는다.

**실시간 협동 액션**이라면 처음 정할 프레임워크는 매치·플레이어·캐릭터의 수명과 서버 판정, 입력에서 연출과 피해 결과가 도착하는 경로다. 새 무기의 수치와 공통 발동 정책의 소유자를 정한다. 매치가 유지되는 동안 아바타가 교체돼도 남을 상태와, 연결이 끊겼을 때 서버가 해제할 상태를 처음 정한다.

두 사례는 처음 세워야 할 계약이 다르다. 공통 규칙은 소유권, 모듈의 인터페이스, 콘텐츠 등록 방법을 명시한다는 데 있고, 실제 프레임워크는 그 계약을 현재 플레이와 엔진에 맞춰 구체화한다. [C++·Unreal 프레임워크](../../knowledge/code/K-CODE-CPP-GAMEPLAY-FRAMEWORK.md) · [Unity·C# 프레임워크](../../knowledge/code/K-CODE-UNITY-GAMEPLAY-FRAMEWORK.md)

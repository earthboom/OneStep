# 개발 설계를 언제 구현에 넘겨도 되는가

2026-11-25 · 소프트웨어·게임 설계 검수, 검증, 독립 교차검토 자료집

설계 검토에서 가장 먼저 물을 질문은 **“이 설계가 틀렸다면 어떤 사례에서 드러나는가?”**이다. 리뷰어가 설계자와 같은 문서를 읽고 동의하더라도 둘이 같은 요구를 오해했을 수 있다. 먼저 원래 요청과 기존 계약에서 기대 결과를 독립적으로 도출한다. 그 다음 설계를 열어 실제 호출과 실패 경로를 따라가고, 글만으로 판단하기 어려운 주장에 시간을 써서 외부 증거를 구한다.

## 무엇을 확인하려는가

| 검토 질문 | 적합한 방법 | 구현으로 넘길 때 남는 것 |
| --- | --- | --- |
| 사용자가 원한 결과가 맞는가? | 요청자 또는 대표 사용자가 정상 사례 하나와 해석이 갈리는 사례 하나의 기대 결과를 정한다. 게임은 첫 플레이에서 실제 행동도 관찰한다. | 사용자 관점의 기대 결과와 아직 선택이 필요한 정책 |
| 이 설계가 그 결과를 보장하는가? | 호출자 입장에서 순서를 써 보고, 가장 중요한 경계에서 실패 시점을 앞뒤로 옮겨 본다. | 어느 단계가 보장을 강제하는지와 이를 깨는 최소 사례 |
| 다른 사람도 설계만 보고 구현·검증할 수 있는가? | 작성자 설명 없이 다음 담당자가 호출 절차와 합격·불합격 예시를 작성한다. 서로 다른 결론이 난 첫 단계를 원문과 대조한다. | 빠진 계약, 수정된 설계, 재검사 결과 |
| 성능·복구·플레이 경험에 대한 가정이 현실에서도 성립하는가? | 자원 추정, 작은 실행 모델, 복구 연습, 플레이테스트 중 판단을 바꿀 수 있는 가장 싼 방법을 고른다. | 관찰값, 실험 조건, 아직 입증하지 못한 범위 |

## OneStep에 적용할 검토 순서

1. **설계자가 경계를 남긴다.** 원래 목표, 유지할 동작, 결과가 갈리는 입력 하나와 기대 결과를 기존 작업 개요에 적는다. 용어의 두 해석이 합격과 불합격을 바꿀 때만 해당 용어집 항목을 사용한다.
2. **검토자는 독립적으로 예상한 뒤 설계를 사용한다.** 먼저 원래 요청과 기준 문서만 보고 사용자가 보게 될 결과를 쓴다. 그 후 설계를 받아 같은 사례의 호출·상태·출력 순서를 추적한다. 불일치하면 양쪽이 갈라진 첫 단계, 근거 위치, 지킬 수 없는 요구를 기록한다.
3. **큰 불확실성 하나를 직접 검사한다.** 성능이면 호출자 경계에서 측정하고, 상태 전이면 실패 직전·직후를 비교하며, 플레이어의 이해가 문제라면 첫 플레이를 관찰한다. 검토 시간과 실험 비용은 실제로 다음 결정을 바꿀 가능성과 잘못 결정했을 때의 비용에 맞춘다.
4. **수정한 설계에 같은 반례를 다시 적용한다.** 판정과 근거가 일치하는지, 기존 호출자의 보존 조건까지 지키는지 확인한다. 착수 전에 필요한 불확실성은 영향받는 작업과 함께 명시한다. 구현 후에만 확인 가능한 항목에는 담당자·환경·합격 관찰값을 붙여 인계한다.

### 검토 깊이를 선택하는 예

| 변경 | 충분한 검토와 종료 조건 |
| --- | --- |
| 카드 제목만 변경 | 기존 판정식을 보존하고 새 문구와 표시 테스트만 대조하면 종료한다. |
| 검색 응답 2초 기준 변경 | 검토자에게 원래 요청과 계측 계약을 주고 50건 중 49건이 0.8초, 한 건이 2.0004초일 때 판정하게 한다. 회차 P95는 0.8초로 통과하고 전건 기준은 실패한다. 초과값을 반올림한 구현도 검사가 잡는지 확인한다. [프로젝트 측정 기록](2026-11-23-korean-retrieval-at-30000.md) |
| 게임 자동 저장과 복구 | 실패 지점을 저장 도중과 완료 표시 직후에 각각 두고, 재시작 시 읽히는 버전을 설계에서 유도한다. 파일 교체 보장이 플랫폼에 달렸다면 해당 플랫폼의 작은 실험을 선행한다. 결과를 확인할 때까지 그 보장에 의존하는 작업만 보류한다. |
| 튜토리얼의 시각 단서 변경 | “단서 이벤트가 발생했다”는 구현 검사와 “초심자가 단서를 보고 스스로 목적지로 갔다”는 경험 검사를 분리한다. 성공 기준을 기획자와 미리 정하고 설명 없는 첫 플레이를 관찰한다. 한 사람의 통과로 전체 이용자 성공률을 단정하지 않는다. |

**인계에 쓸 한 줄 양식** — 요구와 보존 조건 / 판정이 갈리는 사례 / 설계가 보장하는 지점 / 관찰하거나 대조한 근거 / 남은 검사와 담당자. 검토 결과는 *구현 착수 가능*, *일부만 착수 가능*, *특정 결정 보류*로 쓸 수 있다. 후자의 두 경우에는 막힌 결정과 그것을 풀 증거를 함께 적는다.

**현재 스킬과의 차이.** 기존 설계 검토 지침에는 요구 추적, 반례, 모형의 한계, 구현 후 검사 구분이 이미 있다. 우선 시험할 보완점은 다른 AI가 원래 요구에서 기대값을 독립적으로 도출하고, 이어서 설계만으로 호출 절차를 실제 작성하게 하는 것이다. 효과를 검증한다면 같은 설계 사례에서 새로 발견한 실제 결함, 근거 없는 지적, 검토 시간, 수정 후 같은 반례의 재발 여부를 기록한다. 이번 산출물은 자료 조사와 적용 제안이다.

# A game framework for adding stages over time

2026-11-22 · Authoring, validation, and distribution for puzzles, platformers, action, turn-based tactics, and racing

**When existing rules can express a new stage, a designer should be able to author and register its source, then play it under the same rules in the editor and the actual game.** Changes then center on the new content, reusable components, catalog, and progression table. If every stage requires edits to startup code or the save format, identify which facts in the shared structure can move into content before making the next stage.

This report describes design criteria and verification methods drawn from research. It extends the content addition path in the [game development strategy](../designs/game-development-strategy.md) to stage production.

## 1. Principles from research and production experience

| Source | Findings and scope of application |
| --- | --- |
| **Joris Dormans, FDG 2010 · Dormans and Bakkes, TCIAIG 2011** | Model goals and their prerequisites as missions, and visitable locations and connections as spaces. A tactical battle or dungeon that places different goals on the same terrain can vary the two definitions independently. On a simple linear course, one definition can adequately express the relationship between goals and space. [FDG paper](https://pcgworkshop.com/archive/dormans2010adventures.pdf) · [IEEE author manuscript](https://sander.landofsand.com/publications/Dormans_Bakkes_-_Generating_Missions_and_Spaces_for_Adaptable_Play_Experiences.pdf) |
| **Smith, Whitehead, and Mateas, Tanagra, AIIDE 2010** | When designers edit a layout, the tool uses constraints between the player movement model and the terrain to find feasible placements. A platformer editor can report calculations such as jump distance to the designer. Validation covers only the movement and constraints represented in the model. [AAAI paper](https://cdn.aaai.org/ojs/12379/12379-52-15907-1-2-20201228.pdf) |
| **Taylor and Parberry, 2011 · Kartal et al., AIIDE 2016** | Sokoban examples demonstrate using backwards generation or search to obtain solvable layouts. Replaying a known solution with the real game rules can also detect regressions in fixed stages after layout or rule changes. Large searches can time out, and a verified solution alone cannot establish perceived difficulty. [Taylor and Parberry paper](https://ianparberry.com/techreports/LARC-2011-01.pdf) · [Kartal et al. paper](https://cdn.aaai.org/ojs/12859/12859-52-16375-1-2-20201228.pdf) |
| **Butler et al., CHI 2015 · Refraction** | The team analyzed the skills used in solutions to decide when to introduce and combine new concepts. They observed 2,377 players of the math puzzle and, after iteration, reported engagement comparable with an expert-authored progression on the study's measures. This supports examining a stage's individual difficulty and its place in the sequence separately. [Authors' paper](https://www.ericbutler.net/assets/papers/chi2015_progression.pdf) |
| **Nathan Fouts, Pig Eat Ball, GDC 2018** | As stages were continually reordered, the team used spreadsheets, folder searches, and a level search tool to track the appearance of each mechanic and encounter. Early in production, tagging stages with `introduction / practice / combination` and making the list searchable can address the same problem. [GDC video](https://gdcvault.com/play/1025182/Level-Design-Workshop-Set-this) · [Talk slides](https://media.gdcvault.com/gdc2018/presentations/Fouts_Nathan_SetThisGame.pdf) |
| **Maddy Thorson, Celeste, GDC 2017** | The talk describes arranging and connecting more than 300 platforming stages within chapters. It informs review of each room's rhythm alongside previously learned controls, the next room's difficulty, and scene transitions. [GDC video](https://www.gdcvault.com/play/1024307/The-Gamer-s-Brain-How) |
| **Witch Beam, Unpacking, GCAP 2023** | The team built Unity tools for repetitive tasks such as editing areas that accept objects and authoring item and box placements. They authored space, placement conditions, and item lists in the units that designers actually change. [Developer talk](https://youtu.be/2j7AJj1oRSQ) · [Session and video segments](https://confpad.io/conferences/gcap-2023-empower/empowering-design-the-tools-and-pipelines-of-unpacking) |
| **Joel Burgess and Nathan Purkeypile, Skyrim and Fallout 4** | These production cases use modular environment kits and repeated placement. Matching dimensions, connections, visibility, and consistency across combinations matter. For a new dungeon or tactical map, define how walls, doors, and stairs fit together and create variation with lighting or object placement. [Text of the developers' GDC talk](https://www.gamedeveloper.com/design/skyrim-s-modular-approach-to-level-design) · [Fallout 4 GDC video](https://www.gdcvault.com/play/1022930/-Fallout-4-s-Modular) |
| **Nadeo, Trackmania course creation and review** | Creators build and validate a course, submit it, and receive a separate review. The validation ghost in the official guide preserves the inputs of a completed run. This provides a reference for designing distinct checks of course structure, completion with the applicable vehicle and rules, and driving feel. [Map submission documentation](https://doc.trackmania.com/create/map-review/submit-your-map-to-map-review/) · [Validation runs and review guidelines](https://doc.trackmania.com/create/map-review/weekly-grands-guidelines/) |
| **Brandon Moro, Bungie, GDC 2018 · Factorio migrations** | Bungie shows how recording asset dependencies affects invalidation and the cost of iterative builds. Factorio manages renames separately from data conversions when definitions stored in a game change. These examples support tracking both which inputs need rebuilding after a stage change and which IDs older saves still reference. [Bungie talk](https://www.gdcvault.com/play/1025285/Tools-Tutorial-Day-Bungie-s) · [Official Factorio migration documentation](https://lua-api.factorio.com/latest/auxiliary/migrations.html) |

## 2. Shared framework and state ownership

First map the actual play flow, `select → enter → fail and retry or complete → next stage`. Decide what varies per stage, who changes the current state, and what survives the end of the stage. The table identifies responsibilities. In a simple game, one asset or module can cover several of them.

| Owner | Owned data and rules for changes |
| --- | --- |
| **Stage definition** | Holds a stable `StageId`, the source of the space such as a board, scene, or map, the selected rules, and authored settings. Defines objectives, encounters, and components when needed. The play session reads the definition to initialize itself. |
| **Stage catalog** | Resolves definitions by `StageId` and determines which stages each distribution target offers. Choose a manual list or one generated from authoring sources according to the number of stages. Validate duplicate IDs, omissions, and exclusions before publishing. |
| **Progression system** | Determines display order, unlock conditions, and chapter composition. A list of IDs is sufficient for a linear game. Represent prerequisites when there are branches or optional objectives. The progression system chooses what comes next from the completion result and current campaign definition, removing the need for a stage to call the next scene directly. |
| **Stage runner and session** | The runner checks and loads the definition, creates the initial state, handles retries and exits, and releases resources. The session owns changing state such as the current board, timer, cleared checkpoints, and enemy waves. In cooperative play, the host or server finalizes results and clients display that state. |
| **Saves and records** | Owns completed stage IDs and results to retain, such as stars, scores, and records. Applies confirmed results at defined save points. For mid-stage resume, ghosts, or replays, record the stage and rule versions or content hash that the format depends on and define compatibility limits. |

Give the stage selection screen and editor preview the same `StageId` input and start, retry, and exit operations. The editor can inject a work-in-progress definition or bypass unlocking. Both paths should use the same runtime input checks, rule initialization, and outcome evaluation. Send saved preview results to a separate test profile. For asynchronous entry, specify that when a new request cancels the previous one, a late load releases its resources and leaves the current session intact.

Content references shared components and rules. Shared modules take IDs or rule inputs, so they need no concrete references to individual stages. Keep prerequisites for completing earlier stages in the progression definition. This allows the campaign to offer A first without B's assets needing to load A's map. [Content addition path in vegabond-code-design](../../skills/vegabond-code-design/references/gameplay-framework.md#give-content-an-extension-path) · [Feature dependency review](../../skills/vegabond-code-design/references/gameplay-framework.md#make-feature-dependencies-explicit)

## 3. The designer's workflow for each new stage

1. **Author.** Start from a representative stage or an empty template and issue a new `StageId`. Create the board layout or scene and select supported objectives, enemies, and mechanics. When duplicating a stage, generate a fresh ID and keep references to shared component definitions.
2. **Check immediately.** Report invalid board coordinates, missing starts, and unregistered components while editing. Include the stage ID, asset and field location, and the condition to correct. Let authors run the current stage directly and check initialization, failure, and retry in a short loop.
3. **Register.** Include the stage in the distribution catalog and set its order and unlock conditions in the progression table. Teams concerned with difficulty should also mark where players first encounter a mechanic and where they combine earlier lessons. Make work that needs review before publication discoverable in a preview list.
4. **Publish.** Validate IDs, references, and progression conditions across the complete list. Enter the new stage in a build for the target platform. Verify that unlocks and completion history carry over from supported existing saves.

Edit each authoring source in one place. A team starting out can use Unity or Unreal's built-in assets and editing features. Consider Tiled or LDtk when editing many 2D layouts or sharing them with external tools. If using an external editor, manage the sources and conversion rules and regenerate engine assets from those inputs. Document the mapping between the external editor's files and internal IDs and the game's saved `StageId`. If multiple people repeatedly conflict while editing the same list, measure the value of storing definitions per stage and generating the distribution list. [Tiled templates](https://doc.mapeditor.org/en/latest/manual/using-templates/) · [Tiled JSON format](https://doc.mapeditor.org/en/stable/reference/json-map-format/) · [LDtk typed entities](https://ldtk.io/docs/general/editor-components/entities/) · [LDtk JSON documentation](https://ldtk.io/docs/game-dev/json-overview/)

Put behavior in shared components when several stages should receive its updates together. Changing how a shared checkpoint is evaluated affects every course referencing it. Set per-course values such as position and sound effects on the placement. When shared behavior changes, use the reference list to find and review affected stages. Even in games that generate stages by assembling rooms, validate each room's connections and traversal conditions as well as the final stage's traversability. [Skyrim modular production example](https://www.gamedeveloper.com/design/skyrim-s-modular-approach-to-level-design) · [Terrain constraints in Tanagra](https://cdn.aaai.org/ojs/12379/12379-52-15907-1-2-20201228.pdf)

Also distinguish which parts of a content addition require code changes.

| Example request | Scope of edits |
| --- | --- |
| A puzzle that moves existing boxes and goals to new positions | Board and goal data, plus the catalog or progression table |
| A tactical map that adds a rescue objective to existing terrain | If the rescue rule exists, edit the objective definition and placement data. If it is new, add its success, failure, and turn transitions to the shared rules, then register it. |
| A wave before a boss made with existing enemies and spawn points | The encounter definition and existing components. If a flag must affect the boss fight after cancellation, also design its owner and save point. |
| A new teleport tile or a new way to evaluate racing laps | Add a rule with an explicit scope. Check defaults and effects on older content, then select it in the applicable stage. |

## 4. Authoring units and validation by genre

| Genre | What authors should be able to change per stage | Play checks after structural validation |
| --- | --- | --- |
| **Grid puzzle** | Board size, tiles, initial player and piece placements, goals, and selected rules | Replay inputs through the actual rules to verify the goal and reproducible initialization. If hints or teaching a particular solution matter, playtest for alternate solutions and mechanic discovery. |
| **Platformer** | Screens or rooms, start and exit, checkpoints, connections between rooms, reusable segments, and moving components | With the given character abilities, reach the exit and required checkpoints and resume at the intended position after death. Review the rooms that precede and follow one introducing a new mechanic. |
| **Wave action or dungeon** | Space, spawn points, enemy combinations, wave start and end conditions, doors, exits, and objectives | Verify that enemies can approach and that conditions such as kills or elapsed time end the wave. After interrupting and re-entering, timers and enemies from the previous wave must be absent from the new session. |
| **Turn-based tactics** | Terrain and initial unit positions, objectives, turn limits, reinforcement timing, and rewards | Verify that the initial template can be placed, required destinations are reachable, and reinforcements arrive in order. Changing objectives on the same terrain must keep the original mission's state and results separate. |
| **Racing** | Course, starting grid, checkpoint order or branches, lap count, respawn points, and eligible vehicle class | Finish once with the target vehicle and rules. Check that skipping checkpoints or driving backwards cannot award a false finish. Version time-trial records when a course change affects fair comparison. |

For example, a new `warehouse-03` puzzle adds a board layout using existing controls and the expected solution inputs. Replay the inputs in the same runner to complete it and show it third in the list. A new `quarry-loop` course adds a separate map with checkpoints and respawn definitions and runs to completion under existing time-trial rules. Changing display order in either example leaves completion IDs in older saves intact. [Puzzle progression research](https://www.ericbutler.net/assets/papers/chi2015_progression.pdf) · [Trackmania authoring and validation example](https://doc.trackmania.com/create/map-review/weekly-grands-guidelines/)

## 5. Default choices in Unity and Unreal

| Decision | Unity | Unreal Engine |
| --- | --- | --- |
| **2D puzzle with varying layouts in one execution environment** | Combine a shared Scene with a per-stage `ScriptableObject` or imported board asset. The session reads the initial layout, creates the C# game state, and updates the display. [ScriptableObject documentation](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/scriptableobject) | Combine a shared Map with a per-stage `UDataAsset`. The C++ session or gameplay object that runs the rules reads the definition and owns state. [Data Assets documentation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-assets-in-unreal-engine) |
| **Racing, action, or tactics centered on spatial authoring** | Place the environment, spawns, and checkpoints in a scene. Keep rules and objectives in shared Prefabs and the stage definition. Include shipping scenes through an existing path such as the Scene List in Build Profiles. Consider additive loading to replace content while retaining a shared environment or existing state. [Scene List](https://docs.unity.com/en-us/engine/6000.0/manual/building-and-publishing/build-settings/build-profile-scene-list) · [Unity Chop Chop scene authoring example](https://github.com/UnityTechnologies/open-project-1/wiki/Scene-structure-of-locations) | Place layouts and markers in per-stage Maps and connect them to a `UDataAsset` and shared game rules. Consider a Level Instance when reusing spatial components across maps. Verify that maps and dependent assets are included in the target cook and open in the package. [Level Instancing](https://dev.epicgames.com/documentation/en-us/unreal-engine/level-instancing-in-unreal-engine) · [Cooking Content](https://dev.epicgames.com/documentation/en-us/unreal-engine/cooking-content-in-unreal-engine) |
| **Managing dependencies and distribution units separately** | Inspect editor references with `AssetDatabase.GetDependencies`. When using Addressables, inspect actual bundle dependencies and duplicates in the Build Layout. For content updates, maintain the build paths paired with existing Players. [GetDependencies](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AssetDatabase.GetDependencies.html) · [Build Layout](https://docs.unity3d.com/Packages/com.unity.addressables%402.7/manual/BuildLayoutReport.html) · [Content updates](https://docs.unity3d.com/Packages/com.unity.addressables%402.7/manual/content-update-builds-overview.html) | Check dependency direction in Reference Viewer and validate definitions and reference rules with Data Validation. Consider Asset Manager and Primary Assets when independent content packs need controlled discovery, asynchronous loading, and cooking. [Reference Viewer](https://dev.epicgames.com/documentation/en-us/unreal-engine/reference-viewer-in-unreal-engine) · [Data Validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine) · [Asset Management](https://dev.epicgames.com/documentation/en-us/unreal-engine/asset-management-in-unreal-engine) |

The deciding factor is whether stages vary in their **board and rule settings** or in their **space, lighting, collision, and placements**. For the former, starting with different data in a shared scene or map is straightforward. For the latter, each scene or map is easier to edit independently. Projects that ship all content together can start with default loading and packaging. Expand the loading and distribution policies when separate requirements such as independent packs, post-release updates, or memory budgets arise.

## 6. Automated validation and production review

| Check | Problems to catch and how to verify them |
| --- | --- |
| **Sources and references** | Check for duplicate IDs, undefined types or rules, missing required markers, and unintended references to other stages in the editor and CI. Compare each platform's supported content list with the assets it requires. |
| **Rules and progression** | Verify puzzle solution inputs, racing validation runs, tactical victory and failure conditions, and restarts with the real game rules. Check for missing prerequisite IDs and required stages unreachable from a new game. Distinguish intentional loops from prerequisite cycles that block normal progression. For a puzzle solver, record separate outcomes for `solution found`, `no solution proven`, and `undetermined within time or search limits`. |
| **Actual distribution path** | Enter and leave a registered new stage through the menu of a supported Player or packaged build. If optional packs are supported, verify normal flow in builds with and without the pack. Pair forced reference loading in the editor with a separate check that the asset exists in the package. |
| **Save compatibility** | Change the content's display name, file location, and campaign order, then check that completion IDs in older saves still carry over. On removal or replacement, decide whether to retain the old ID and display completion, migrate to a new ID, or simply hide the entry. If rule changes prevent interpretation of older records, specify which records remain compatible. |
| **Player experience** | Playtest whether players can read the objective, encounter mechanics in the intended order, and retry within an appropriate time during repeated attempts. When needed, use distributions of failure locations, retries, and dropouts to choose the next revision. [Tanagra paper](https://cdn.aaai.org/ojs/12379/12379-52-15907-1-2-20201228.pdf) · [Refraction player study](https://www.ericbutler.net/assets/papers/chi2015_progression.pdf) |

For example, after moving `warehouse-03` earlier, a save that already completed it should continue to show completion. If mid-stage saves are supported, decide separately whether an edited board can load previous piece positions as they were. The conditions for comparing older `quarry-loop` records differ between a lighting-only change and a change to checkpoint evaluation. Keeping completion history IDs separate from the content versions needed for records and resume makes it easier to apply each policy. [Example of changing existing game data](https://lua-api.factorio.com/latest/auxiliary/migrations.html) · [OneStep save design](../../knowledge/game/K-GAME-TECH-SAVE.md)

## 7. Ground rules at the start of game development

- Choose two representative stages and one variation. For example, use a basic puzzle, a puzzle combining existing mechanics, and a puzzle requiring a new mechanic. Record where authors express the differences between the first two and which shared rule changes the third requires.
- Determine who manages stage IDs, authority to run and end stages, progression conditions, and persistent state. Local games and server-authoritative games can share a content format while using different authorities to finalize results.
- Document `source location → shared components → validation → registration → open in the actual game` for designers and AI. Use that path for stages expressible by existing rules. When shared rules change, record the existing stages affected and the play scenarios to check.
- As production progresses, examine how long it takes to open a new stage, which shared files were modified, and which omissions caused rework. Add mockups, previews, validation, or automatic registration at authoring steps with demonstrated recurring costs.

# When is a development design ready for implementation?

2026-11-25 · Research on design inspection, verification, validation and independent review for software and games

Ask what observable case would expose a wrong design. Two reviewers reading the same proposal can share the same misunderstanding. Derive expected behavior from the request and governing contract, walk the proposed mechanism, then seek external evidence for the uncertainty most likely to change the decision.

## Choose the review by the question

| Question | Review activity | Evidence for handoff |
| --- | --- | --- |
| Does the proposed outcome meet the user's need? | Ask the requester or a representative user to judge an ordinary example and one where interpretations diverge. For game experience, observe first-time play. | Expected outcomes in the user's terms and any unresolved product choice |
| Can the mechanism deliver the outcome? | Walk the calling sequence and move a failure to either side of the critical transition. | The step enforcing the guarantee and a minimal counterexample |
| Can the next person implement and test it? | A consumer writes a calling sequence and pass/fail examples without the author's explanation. Reconcile the first disagreement with its source. | Missing contract, corrected design and result of replaying the case |
| Is a performance, recovery or player-behavior assumption realistic? | Choose a resource estimate, executable model, recovery exercise or playtest that could overturn the decision. | Observation, conditions and remaining uncertainty |

## A review sequence for OneStep

1. **Frame the boundary.** In the existing brief record the original goal, behavior to preserve and expected outcome for one distinguishing input. Use a glossary entry only when plausible meanings would change a test verdict.
2. **Predict independently, then use the design.** Give a reviewer the original request and governing contract first. After they derive an expected outcome, give them the design and have them trace calls, state and outputs. Record the first point of divergence, source and affected promise.
3. **Test a consequential assumption.** Measure at the caller for latency, compare a failure before and after a transition for durable state, or observe a first-time player for comprehension. Scale the effort to the cost of guessing and the likelihood that evidence will change the next decision.
4. **Replay after revision.** Recheck the same counterexample and a preserved caller. Identify the work that depends on an unresolved premise. For checks that require implementation, name the owner, environment and observable pass condition.

| Change | Proportionate check and exit |
| --- | --- |
| Change only a card title | Compare the title and its display assertion, preserving the predicate. |
| Change a two-second search target | Give a reviewer 49 calls at 0.8 s and one at 2.0004 s. The round's P95 is 0.8 s, while the every-call condition fails. Verify that the proposed check rejects a rounded comparison. [Project measurement history](2026-11-23-korean-retrieval-at-30000.md) |
| Add game autosave and recovery | Interrupt during the write and just after acknowledgement. Derive the version visible after restart. Test a platform-dependent file replacement assumption before committing the work that needs it. |
| Change a tutorial cue | Check event emission in code and unaided navigation with a first-time player. Agree on success before observing play. One successful player cannot establish the population success rate. |

**Compact handoff** — Requirement and preservation condition / distinguishing case / enforcement point / evidence / remaining check and owner. Report which work can start. If a decision must wait, name it and the evidence needed to release it.

**Fit with the existing skill.** The current review already traces requirements, challenges transitions, bounds model evidence and separates downstream execution checks. The addition worth piloting is a reviewer independently deriving an expected outcome and then actively using the design to write the caller's sequence. In a future comparison, record substantiated defects, unsupported findings, elapsed review time and recurrence on replay. This report supplies research and a proposal.

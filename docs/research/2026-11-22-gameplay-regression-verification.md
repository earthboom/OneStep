# Gameplay regression testing guidelines for Unity and Unreal

2026-11-22 · AI code changes, stage additions, save compatibility, and verification in actual builds

**Before making a change, identify the play behavior to preserve and where to observe it.** When editing shared code, check that behavior in affected existing stages. When adding a stage, follow the new content from entry to completion in the actual game. Also check existing content that uses the same rules, components, or progression table. Tests should allow comparison of what the player sees and the state the rules commit. [Core game development strategy](../designs/game-development-strategy.md) · [Test oracle research](https://web.eecs.umich.edu/~weimerw/2024-481F/readings/testoracles.pdf)

This document presents research and design criteria. It includes no engine execution results or performance measurements. Choose tools based on the project's engine and package versions, target devices, and supported local and network configurations. [AI code change quality research](2026-11-21-ai-codebase-quality.md) · [Stage framework research](2026-11-22-stage-content-framework.md)

## 1. Principles from research and production

| Source | Decision it informs and scope |
| --- | --- |
| **Barr et al., test oracle research, IEEE TSE** | The basis for deciding whether a result is correct is separate from the means of executing input. Use specifications, known examples, relationships between states, or human review as appropriate. In games, these sources help prevent AI from copying expected values directly from the output after a change. [Paper](https://web.eecs.umich.edu/~weimerw/2024-481F/readings/testoracles.pdf) |
| **Claessen and Hughes, QuickCheck, ICFP 2000** | Alongside inputs with known answers, declare properties that constrain time, cost, or state and check them using generated inputs. For example, an invalid move must leave the turn, currency, and board state unchanged. The generation rules determine the range of inputs a passing property check covers. [Paper](https://www.cs.tufts.edu/comp/150FP/archive/john-hughes/quick.pdf) |
| **Rothermel and Harrold, regression test selection, 1997 · Yu et al., GameRTS, ICSE 2023** | The former uses software changes to select existing tests to run. The latter abstracts recorded game states, actions, and paths and applies them to video games. In practice, examine asset references, registration, and progression paths alongside code callers to select representative checks. Extend coverage to neighboring flows when the impact is unclear. Reported selection and detection rates apply to the study subjects and observable paths. [Regression test selection paper](https://www.cs.purdue.edu/homes/xyzhang/fall07/Papers/p173-rothermel.pdf) · [GameRTS paper](https://ttfish.cc/content/Papers/icse23.pdf) |
| **Luo et al., flaky tests, FSE 2014** | Asynchronous waits, order dependence, and concurrency were major causes in the study. Wait for scene readiness signals and reset saves, world state, and options for each run. Preserve the environment and result of the first failure when rerunning for diagnosis. [Paper](https://mir.cs.illinois.edu/~marinov/publications/LuoETAL14FlakyTestsAnalysis.pdf) |
| **Ostrowski and Aroudj, game regression automation, 2013 · Balyo et al., planning and learning for game regression, 2024** | These approaches combine input recording and replay with game scripts, or derive a model of game rules from detailed logs and explore it. The Unity RPG in the second study is a proof of concept. Teams can start by recording inputs, initial state, and outcomes to reproduce play paths they already consider important. [Record and replay research](https://link.springer.com/article/10.7603/s40601-013-0010-4) · [Planning and learning research](https://arxiv.org/abs/2402.12393) |
| **Rare, Sea of Thieves · Mojang, Minecraft, GDC** | Rare presented gameplay automation that team members could author and how to choose an appropriate scope for each test. Mojang's talk covers lessons from applying the approach in a different game and team. Test authoring cost, environment reproduction, and time to find a failure's cause all matter. [Rare talk video](https://www.gdcvault.com/play/1026366/Automated-Testing-of-Gameplay-Features) · [Rare presentation materials](https://media.gdcvault.com/gdc2019/presentations/Masella_Robert_AutomatedTestingOf.pdf) · [Minecraft talk video](https://gdcvault.com/play/1027345/Lessons-Learned-in-Adapting-the) |
| **Ubisoft, The Division, GDC 2019** | Used AI players to finish missions, collect performance data, exercise multiplayer tasks, and reproduce bugs. Bots suit long sessions and repeated checks across many paths. To know whether existing rules still produce the same decisions, record both what the bot did and what result should follow. [Talk video](https://www.gdcvault.com/play/1026382/Automated-Testing-Using-AI-Controlled) · [Presentation materials](https://media.gdcvault.com/gdc2019/presentations/Paredes_Jose_AutomatedTestingUsing.pdf) |
| **Riot, League of Legends determinism and Chronobreak** | Describes how to find the first point where gameplay-relevant server state diverges for identical input. It illustrates decisions about measurement scope and logging costs. Full cross-platform determinism throughout the game is a separate technical decision. [Implementation account](https://www.riotgames.com/en/news/determinism-league-legends-implementation) · [Tracing state divergences](https://www.riotgames.com/en/news/determinism-league-legends-fixing-divergences) |
| **Kalibera and Jones, performance changes and measurement uncertainty** | Interpret the magnitude of improvements and regressions in light of variation across repeated measurements. In games, compare baseline and candidate builds under identical conditions and record variability across devices, builds, and runs. [Paper](https://arxiv.org/abs/2007.10899) |

## 2. Minimum verification criteria at project start

1. **Choose representative play.** Write down one core genre loop and one interruption or error likely to compromise quality. For a puzzle, try `select → push once → clear` and `invalid input → restart`. For co-op, use `enter → perform role → receive reward` and `leave during loading or combat → reconnect`. Expand the scope according to the features the game supports. [Deriving the framework from representative play](../../skills/vegabond-code-design/references/gameplay-framework.md#derive-the-framework-from-representative-play)
2. **Write down what must hold.** At each checkpoint record `initial conditions → action → player-visible result → committed state`. For example, requesting a move into a blocked cell leaves the board and move count unchanged, while the screen gives feedback on the invalid move. Record only results that affect the game beyond the loop, such as saves, unlocks, and rewards, with their designated owner.
3. **Establish independent evidence for the result.** Use approved rules and specifications, previously accepted play, or small expected values calculated independently of the code under change. For an intentional rule change, record expected values that change separately from behavior to preserve. If existing output contains a known defect, specify the behavior to correct. [Oracle research](https://web.eecs.umich.edu/~weimerw/2024-481F/readings/testoracles.pdf)
4. **Record initial conditions and reproduction details.** Record a representative supported stage ID, game and content versions, starting state, input order, necessary seeds and ticks, mode, and device. For save compatibility, retain archived saves from older versions. Keep separate test accounts and data for reproduction.
5. **Start with the smallest observable path.** Check shared rules quickly. Exercise problems involving input, maps, saves, and assembly together at the actual entry point. Where QA and designers can reproduce and judge an outcome in the game, a play path and observation criteria are enough to start. Automate the checks with the highest repetition costs and failure impact first. [Existing verification guidance](../../skills/vegabond-code/references/verification.md) · [Rare automation example](https://www.gdcvault.com/play/1026366/Automated-Testing-of-Gameplay-Features)

Small contracts like these can serve both game briefs and tests.

| Example | Starting state and input | Result to preserve |
| --- | --- | --- |
| **Existing push rule** | Enter `warehouse-03` from the regular menu. Push once where the space behind the box is empty, then request another push where the space is blocked. | The first action changes the box position and move count. The blocked action preserves both. Restarting restores the initial board and move count. |
| **New stage registration** | Load a supported-version save with existing progress. Select the new board in a build that inserts `warehouse-04` into the stage order. | The new stage follows its intended unlock conditions and can be played, retried, and completed. The completion record for `warehouse-03` remains available under its previous ID. |

## 3. Choosing verification scope by change type

| Change | Fast check | What to check in the integrated flow |
| --- | --- | --- |
| **Add a stage using existing rules** | Check IDs, references, required markers, and progression conditions. Check a solution input for a puzzle, a finish through the checkpoints for racing, or valid objectives and deployment for tactics. | Follow the game's listing and unlock → enter → retry or exit → record result. Select an existing stage that shares components or the progression table to check for impact. Open a new scene, map, or pack in the target build. |
| **Change shared rules or state lifetimes** | Check valid, invalid, and boundary inputs for the changed rule and the rules to preserve. Verify whether fresh state is created after retry, interruption, and a second entry. | Inspect representative existing stages that combine the rules differently. Where code has many callers, as in shared combat, movement, saving, or loading, extend to existing callers with different behavior and to failure paths. |
| **Modify an existing stage or preset** | Check changed placement and objectives. Investigate other stages that reference shared assets or rules. | Inspect the effect on previous solutions, progress, and time-attack records. If intentionally breaking compatibility, verify that record display, a fresh start, or migration follows project policy. |
| **Change progression, saves, or the content catalog** | Copy a representative old save, read it, resave it, and read it again. Check display-name and order changes and the handling of retired or replacement IDs. | Exercise applicable cases such as missing optional packs, canceled loads, invalid or unsupported saves, and converting the same save twice. Check that valid completion history and new progress persist. [OneStep save technology](../../knowledge/game/K-GAME-TECH-SAVE.md) |
| **Change rendering, streaming, or AI costs** | Identify state that must persist offscreen and instrument the start and end of new loading or update boundaries. | Repeat a representative route with the same build settings, device, and content. Inspect frame-time and memory trends alongside NPC state after loading, world outcomes on return, and changes in required visuals or controls. |
| **Change multiplayer authority, movement, or rewards** | Check who decides and how many times a result is applied on simultaneous requests or retransmission. | Use multiple clients with supported host and dedicated-server roles. Compare authoritative state with what each client sees under delay, loss, or reconnection. |

Determine scope from **code callers, prefab, Blueprint, scene and map references, catalogs and progression, runtime subscriptions and cleanup, and deployment configurations**. Changed filenames alone rarely reveal existing paths that share a preset or unlock table. Run relevant paths quickly for each change. Schedule representative build, device, and long-running paths in integration testing or on release candidates according to the team's schedule. Choose the frequency based on actual risk and supported configurations. [Regression test selection research](https://www.cs.purdue.edu/homes/xyzhang/fall07/Papers/p173-rothermel.pdf) · [Feature dependency review](../../skills/vegabond-code-design/references/gameplay-framework.md#make-feature-dependencies-explicit) · [Asset and progression structure](2026-11-22-stage-content-framework.md#6-automated-validation-and-production-review)

## 4. Obtaining equivalent evidence in Unity and Unreal

| Verification layer | Unity | Unreal Engine |
| --- | --- | --- |
| **Rules and data** | Test engine-independent game rules and save conversions in Edit Mode. Inspect stage definitions, references, IDs, and the shipping list in the editor. [Unity Test Framework modes](https://docs.unity3d.com/Packages/com.unity.test-framework%401.4/manual/edit-mode-vs-play-mode-tests.html) | Depending on project configuration, exercise plain C++ responsibilities through Low-Level Tests (Catch2) or an Automation Test suited to the module. Data Validation can check asset rules in the editor and commandlets. [Low-Level Tests](https://dev.epicgames.com/documentation/en-us/unreal-engine/write-low-level-tests-in-unreal-engine) · [Data Validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine) |
| **Actual scene, input, and world assembly** | Load the startup scene and content in Play Mode, wait for state readiness, and exercise the real input or command path to check the result. The Input System's `InputTestFixture` supports isolated input tests. Check actual devices and project-specific input registration in the corresponding Player path. [Play Mode](https://docs.unity3d.com/Packages/com.unity.test-framework%401.4/manual/edit-mode-vs-play-mode-tests.html) · [Input Test Fixture](https://docs.unity3d.com/Packages/com.unity.inputsystem%401.11/manual/Testing.html) | Use the Automation Framework and Functional Testing to assemble the level, Actors, and authority environment. Start level streaming or a connection and check readiness in `IsReady`. Representative flows go through actual input, commands, or the same path the menu calls. [Automation Test Framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-test-framework-in-unreal-engine) · [Functional Testing](https://dev.epicgames.com/documentation/en-us/unreal-engine/functional-testing-in-unreal-engine) |
| **Player, package, and networking** | Use a standalone Play Mode test Player or project play automation on supported platforms. Run release candidate checks for scenes, bundles, and scripting settings separately with those settings. Test multiple Players and the required connection failures. [Player test workflow](https://docs.unity3d.com/Packages/com.unity.test-framework%401.4/manual/workflow-run-playmode-test-standalone.html) · [Network Simulator](https://docs.unity3d.com/Packages/com.unity.multiplayer.tools%402.2/manual/network-simulator.html) | Launch the target package and check map cooking, asset loading, menus, and exit. Use Gauntlet to launch sessions with processes such as servers and clients and collect their results. Network emulation can exercise supported latency and packet loss conditions. [Gauntlet](https://dev.epicgames.com/documentation/en-us/unreal-engine/gauntlet-automation-framework-in-unreal-engine) · [Network emulation](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-network-emulation-in-unreal-engine) |
| **Instrumentation and diagnosis** | Collect Profiler data from the Player. Use the Performance Testing package for repeated measurements when needed. Record the device, quality settings, build method, and options. [Player profiling](https://docs.unity3d.com/6000.0/Documentation/Manual/profiler-profiling-applications.html) · [Frame measurement API](https://docs.unity3d.com/Packages/com.unity.test-framework.performance%403.0/manual/measure-frames.html) | In Unreal Insights, select the traces needed for timing, memory, and networking. For screenshot comparisons, fix the reference image and conditions, then choose a tolerance appropriate to the screen's purpose. [Unreal Insights](https://dev.epicgames.com/documentation/unreal-engine/unreal-insights-in-unreal-engine) · [Screenshot Comparison](https://dev.epicgames.com/documentation/en-us/unreal-engine/screenshot-comparison-tool-in-unreal-engine) |

Report the execution environment with each result. `Edit Mode`, `Editor Play Mode/PIE`, `game Player or package`, and `physical device` each support different checks. Assess environment-dependent qualities such as graphics, timing, and physical controller behavior in the relevant mode and device. Make readiness and completion signals observable from engine entry points. Check whether hidden test-only initialization bypasses actual game initialization.

## 5. Reproduction, visual quality, and performance

- **Choose the scope of recording and replay.** For deterministic turn and puzzle rules, compare turn numbers, board positions, objective completion, and reward IDs under a fixed input sequence. For real-time games where physics, time, or scheduling can vary, specify supported conditions and check checkpoint order, resulting state, and meaningful position and time tolerances. For server reconnection, compare the client view and authoritative server state at an appropriate completion point. If results diverge, record the input and differing fields at the first divergent checkpoint. [Riot determinism implementation](https://www.riotgames.com/en/news/determinism-league-legends-implementation) · [Riot state divergence tracing](https://www.riotgames.com/en/news/determinism-league-legends-fixing-divergences)
- **Diagnose flaky tests.** Use meaningful signals such as world readiness, replication acknowledgment, or authoritative state confirmation with a timeout before resorting to arbitrary waits of several seconds. Reset saves, random state, time, subscriptions, and objects for each case, and keep the logs and state from the first failure. Investigate that failure even if the rerun passes. Identify whether the cause lies in the environment, test, or game. If running a flaky test separately, record its owner and the conditions for restoring it to the suite. [Luo et al. study](https://mir.cs.illinois.edu/~marinov/publications/LuoETAL14FlakyTestsAnalysis.pdf) · [Unreal Functional Testing readiness phase](https://dev.epicgames.com/documentation/en-us/unreal-engine/functional-testing-in-unreal-engine)
- **Choose where to evaluate visuals and game feel.** For comparison images, record platform, resolution, rendering settings, camera, and capture time. Visible layout and marker positions can be compared automatically. For camera tracking, hit feedback, or the moment a player first notices an objective, combine short representative play sessions with human assessment. When changing the image tolerance or baseline, review what actually changed on screen. [Unreal Screenshot Comparison](https://dev.epicgames.com/documentation/en-us/unreal-engine/screenshot-comparison-tool-in-unreal-engine) · [Automated playtesting of game parameters](https://sites.cc.gatech.edu/fac/riedl/pubs/zook-fdg14.pdf) · [Selecting a playtest method](../../knowledge/game/K-GAME-PROTOTYPE-PLAYTEST.md)
- **Consider performance changes and variability together.** Fix the supported device, comparison builds, resolution, quality, capture window, and representative workload. Separate first entry from repeat entries and measure multiple runs. Depending on the goal, record median and upper-percentile frame times, long-frame frequency, load time, peak memory, and resident memory after repeated transitions. Set thresholds in advance from the target device's and genre's frame, memory, and load budgets. If the change is comparable to run-to-run variation, defer judgment and investigate the variation. [Measurement uncertainty research](https://arxiv.org/abs/2007.10899) · [Performance and streaming in game development](2026-11-22-game-development-practices.md)

## 6. Working rules for AI-assisted changes

| Stage | Contract to check and evidence to retain |
| --- | --- |
| **Before work** | Specify the intended change, play outcomes to preserve, current entry, decision, and save locations, and representative existing content. For a reproducible bug, record the failure conditions before the fix. Distinguish unrelated preexisting failures in baseline and candidate runs. |
| **Implementation design review** | Use existing tests and entry points. If fixing a new stage requires changing a shared rule, check the contract other users of that rule need. When adding a test, choose a specific regression existing checks would miss. |
| **Evaluating results** | If expected values, tolerances, sample saves, or baseline screens changed, review the relevant diff and the game rule or design decision that required the change. Check how omitted or disabled tests or relaxed pass conditions affect the result. |
| **Completion record** | Record the target change, checks executed, environment, build and content versions, results, and remaining areas. Distinguish design complete, executed and passed or failed, excluded from execution, and unable to run. Report play verification only for the paths and configurations actually exercised. |

When AI edits tests alongside code, attach evidence such as results approved before the change, independently verifiable rules, older saves, and known solution inputs. If verification criteria change, their implications must be reviewable alongside the code changes. For example, when intentionally changing a puzzle solution, record both the new answer and the policy for the previous solution. [AI code change quality research](2026-11-21-ai-codebase-quality.md) · [Design review through content and play](../../skills/vegabond-code-design/references/gameplay-framework.md#review-the-change-through-content-and-play) · [Verification workflow](../../skills/vegabond-code/references/verification.md)

A work record can use one line per check: `change → execution environment → stage and starting state → input → expected result → observed result and difference → evidence location`. For example, a check that a new stage can be entered from the main menu links the target package, the `StageId` used in the list, and the save used to unlock it. At the design stage, record only the expected result and conditions to check.

## 7. Verification design examples by genre

| Game and change | Representative play to check existing quality | Observations to retain |
| --- | --- | --- |
| **Add a new puzzle board using existing rules** | Open the board from the shipping stage list and replay the solution input. Restart, then verify the same push rule on one existing board. With a supported older save, check completion records after the stage order changes. | Stage ID, clear status, positions of important tiles and pieces, completion and unlock IDs |
| **Change shared racing checkpoint code** | Choose representative tracks according to existing support for single and branching routes. Check a normal finish, a skipped checkpoint, reentry after respawn, and wrong-way driving. Assess the reuse of older ghosts under the project's record compatibility policy. | Confirmed checkpoint order and lap decision, record save result, timing tolerance criteria |
| **Change command processing in turn-based tactics** | Check an existing mission with the same initial placement and commands. Examine invalid commands, enemy turns, and the priority when victory and failure conditions occur together. | Action points, turn order, objective result, first command where states diverge |
| **Fix authority or reconnection in co-op** | Launch a host or server and multiple clients in a supported project configuration. Disconnect and rejoin immediately before objective completion or just after reward processing. | Player-to-avatar association, server-confirmed objectives and inventory, duplicate rewards and client presentation |
| **Change world streaming or offscreen AI** | Run `village → forest → skirmish → return` on a representative device and check that the same NPC ID retains the required outcomes after leaving view and returning. | NPC survival and quest state, first-load and repeat-entry times, long frames, resident resources after return |

Derive additional checks from the project's contract. For example, a puzzle without saves can check the return to the stage list after completion, while a game that retains seasonal records includes a path that reads prior-season results. Start with one core success path in existing content, one interruption or failure path, and a path that opens new content in a supported configuration. Expand package, compatibility, and performance automation as repeated work grows.

# How the next OneStep contributor can find knowledge and past defects

2026-11-23 · This investigation covers `vegabond-knowledge` and its search helper. The next contributor has limited information before searching. Before starting work, they know the intended action and constraints. Immediately after failure, they know the symptom and error text. When continuing a previous review, they know the document ID. We examined storage and retrieval for these three situations separately.

## Methods adopted from the research

| Evidence | Decision for OneStep |
| --- | --- |
| KCS preserves the requester's initial description of the problem and its environment. It adds actual inquiry language to existing articles that were hard to find. [Consortium for Service Innovation practice guide](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/030/030/010/020) | In an incident record, put the user's observed wording in `symptom` and the action someone would search for before starting work in `trigger`. Before duplicating a case with the same principle and scope, add missing expressions and checks to the existing detail. |
| In their study of duplicate bug reports, Sun et al. combined titles and descriptions with product, component, and version to rank related reports in Mozilla, Eclipse, and OpenOffice. [Original ASE paper](https://cs.uwaterloo.ca/~cnsun/public/publication/ase11/ase11.pdf) | Retrieve candidates broadly, then compare environments and causes when deciding whether to apply them. Where symptoms look similar but environments differ, defer reuse of the earlier fix. The study does not justify transferring its learned weights or duplicate scores directly to this repository. |
| A survey and log analysis of Google developers identified API usage, how things work, causes of failure, and code locations as common search goals. [Sadowski, Stolee, and Elbaum field study](https://research.google/pubs/how-developers-search-for-code-a-case-study/) | For queries with a known identifier, preserve spelling, punctuation, and the full ID. We reproduced and fixed a failure in which the generic term `music` inside `R-CODE-UE-MUSIC-STOP` caused a different document to rank first. |
| Google's SRE postmortem process connects impact, action, and follow-up review. Once incidents accumulate, the team analyzes trends in structured records. [Google SRE incident experience](https://sre.google/resources/practices-and-processes/incident-management-guide/) | After retrieving an earlier defect, check `cause_status`, `prevention_status`, and the evidence from actual revalidation. Keep resolved incidents searchable. For example, after finding an invalid name index, check whether a numeric-looking property name is mistaken for successful decoding, alongside a valid input. |
| Across 18 datasets, BEIR showed that lexical retrieval can provide a strong baseline and that reranking offers gains at a computational cost. MIRACL provides multilingual queries and relevance judgments, including Korean. [BEIR paper](https://datasets-benchmarks-proceedings.neurips.cc/paper/2021/hash/65b9eea6e1cc6bb9f0cd2a47751a186f-Abstract-round2.html) · [MIRACL paper](https://aclanthology.org/2023.tacl-1.63/) · [Language-specific dataset composition](https://project-miracl.github.io/) | Evaluate Korean questions, English technical names, incident IDs, and misleading candidates with similar symptoms separately. Public benchmarks help select candidate techniques. Measure hit rates on the project's short recurrence-prevention records using local cases. |
| Stanford's public CS224U lecture distinguishes inverted indexing from ranking evaluation and explains first-relevant rank and recall separately. In the published video chapters, 7:25 covers inverted indexes, 20:01 Success and MRR, and 21:13 Precision and Recall. [Stanford Online lecture](https://www.youtube.com/watch?v=e8zKKDMAze8) | Report how high the first required item ranks and whether all required items were retrieved as separate outcomes. ## Applications

**Identifiers embedded in Korean sentences.** Originally the search found `RenderDocPlugin` but returned nothing for the Korean input `RenderDocPlugin을`. It also failed on `UAsset.GetNameReference에서` despite an existing record. The search now handles the boundaries of commonly used Korean particles and points to the actual source line even if the particle appears in the text. Negative controls checked that `Widget::FlushExtra` did not spuriously match `Widget::Flush` and that the search did not arbitrarily strip the ending of `RenderDocPlugin용`. When the query is a full ID alone, an ID match takes priority over topic expansion from its parts.

**An existing record lacks the searcher's wording.** In the existing pathfinding evaluation, the correct document for `packed priority PriorityKey ties state distance` ranked sixth against a top-three requirement. The document already explained that a packed key must preserve sort order. Adding checks that compare the original tuple's sort order with the packed key at equal distance, at the final tie-breaker, and at field limits moved the document to first. After this addition, the previous search implementation also passed every existing evaluation case. This isolated the document's contribution to the ranking improvement from the algorithm's. [Expanded pathfinding knowledge](../../knowledge/game/K-GAME-TECH-PATH.md)

**Tasks with multiple questions.** When investigating reverse camera framing and duplicate stops against the same project, store, and filters, pass `--query` twice. Documents load once. Results, empty results, related records, and source checks are returned per question. Run questions separately if they require different environment conditions. Internally, the search checks for a literal string before testing a regular expression and reuses a bounded number of frequently used boundary patterns. Judge retrieval scores and the accuracy of the underlying material separately. [Search command and result format](../../skills/vegabond-knowledge/references/retrieval.md#separate-questions-in-one-call)

**Decisions after retrieval.** In the same command, the Korean query `UAsset.GetNameReference에서` returned the parser incident first, with prevention status `verified`. The query `R-FIC-N2-DIALOGUE-20261106의` returned the fiction dialogue incident first, with prevention status `proposed`. For the former, check that the verification environment matches the current work and reuse the check. For the latter, first try the proposed check on the current manuscript. Promoting the first result directly to a rule would erase the most important difference between the two records.

## When to choose a different approach

- **SQLite FTS5** is a candidate for comparison when a persistent inverted index and per-column weighting are needed. If Markdown is canonical, verify synchronization on additions, edits, and deletions as well as index rebuilding. First test how the default tokenizer handles technical-name punctuation and Korean particles on the same cases. Consider this option when loading all documents becomes a bottleneck. [SQLite FTS5 official documentation](https://sqlite.org/fts5.html) · [Project measurement criteria by scale](../../skills/vegabond-knowledge/references/search-scale.md)
- **Korean morphological analysis and hybrid lexical and semantic retrieval** merit comparison if real paraphrased questions repeatedly elude the current boundary handling. Korean analyzers can lose meaningful prefixes through compound decomposition or part-of-speech filtering. Test a user dictionary and nearby wrong answers together. Retain the step that checks the source and its applicable scope after candidate retrieval. [Elastic Nori part-of-speech filter documentation](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori-speech) · [MIRACL](https://aclanthology.org/2023.tacl-1.63/)

## Verification scope

The evaluation used 172 actual knowledge and incident records on Windows 11 with Python 3.12.3. The previous helper used the search code at commit `ca13c55`. We distinguished the 218 questions in seven existing case files, five new regression cases, and three additional controls held out from implementation tuning. The controls were a fiction incident ID, a game knowledge ID, and a long nonexistent plugin name. The small number of new cases limits generalization to arbitrary Korean questions.

| Evaluation | Before | After search and document changes |
| --- | ---: | ---: |
| Existing 218 cases passed | 217/218 | 218/218 |
| Required IDs retrieved in existing cases | 208/209 | 209/209 |
| Mean reciprocal rank of the first required ID in existing cases | 0.9326 | 0.9379 |
| Five new regression cases passed | 1/5 | 5/5 |
| Three separate controls passed | 1/3 | 3/3 |

For timing, we warmed each version on the same expanded documents, then alternated execution order. Across four batch evaluations of the existing 218 queries against documents already in memory, median time went from **16.25 seconds to 1.98 seconds**. This excludes process startup, loading documents from disk, and verifying external originals. Both versions still scan the entire corpus. Latency at much larger scale requires separate measurement.

The existing evaluation comprised 23 common cases, 11 game application cases, 25 game extension cases, 150 native game cases, and three each for TechniqueLab Dynamic, Traffic, and Stream. The separate Korean control queries were `R-FIC-N2-DIALOGUE-20261106의`, `K-GAME-TECH-WATER로`, and `RenderDocPluginExtended를`. We expected the specified ID to rank first for the first two and an empty result for the last. The SHA-256 of the final document hash list was `a825aa20ba5320fbef86d3be103bb31546a9e8a2cf8fffffceeb13a72bd90d42`. Verification covered 92 knowledge helper tests and five distribution tests.

We timed actual commands separately after the full test suite finished. The queries were `reverse camera framing`, `duplicate stop fade`, and `work brief`, using `--store records --limit 3 --no-cache`. We rotated the execution order of the three methods, measured each three times, and verified that the top result IDs for each query agreed on every run. Including Python startup and canonical document reads, median time for all three questions was **9.17 seconds** for individual invocations of the previous helper, **5.33 seconds** for individual invocations of the improved helper, and **2.43 seconds** for the improved helper in batch. The respective ranges were 5.69–10.18 seconds, 5.04–6.47 seconds, and 2.04–2.92 seconds. The filesystem cache was not cleared. Three measurements cannot estimate tail latency.

Rerun the common regression cases with the commands below. The existing evaluation file specifies required and forbidden IDs and rank limits for each situation. The actual queries and negative controls from this investigation were added to the same file.

```powershell
python skills/vegabond-knowledge/scripts/search.py evaluate --project . --cases skills/vegabond-knowledge/tests/retrieval_cases.json --no-cache
python skills/vegabond-knowledge/scripts/search.py search --project . --store records --query "UAsset.GetNameReference에서" --query "R-FIC-N2-DIALOGUE-20261106의" --limit 1 --no-cache
```

# Preserving quality when AI changes an existing codebase

2026-11-21 · Research for OneStep · Applicable to existing codebases, with C++ and Unreal Engine examples

**Define the change contract first, run separate checks for existing behavior and new requirements, and evaluate the structure through subsequent changes.** The person assigning the task need not write detailed instructions each time. The proposed workflow has the agent identify the contract in the request and repository, summarize it in the existing task brief, and leave evidence that addresses it. It uses OneStep's current verification process and starts by adding executable checks for recurring regressions.

| What to preserve | Evidence for the decision |
| --- | --- |
| **Existing behavior and compatibility** | Exercise representative inputs and failure paths through existing public entry points. When changing an API, save file, asset, or network contract in use, also exercise an actual older caller or fixed data from an earlier version. |
| **Structure and extensibility** | Identify responsibilities, state owners, and permitted dependency directions. Add one more piece of content or policy in a follow-up task to see how far edits spread and what the developer needs to understand. |
| **Operational quality** | When a task has performance, lifetime, or recovery requirements, check the baseline under the same conditions, the actual execution target, and the observed state after failure. Focus expensive checks on paths exposed to the relevant risk. |

## 1. Empirical evidence on AI adoption and quality

| Source and evidence type | Findings and scope |
| --- | --- |
| **METR, 2025 and 2026 · Randomized experiment and follow-up** | Across 246 tasks performed by 16 experienced open-source developers in familiar repositories, the early-2025 AI condition took 19% longer on average. The 2026 account explains that sample selection and the difficulty of measuring parallel work in the follow-up experiment make a reliable estimate of the current effect difficult. Measuring our own work directly, including review and rework, is warranted. [Original experiment](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) · [Follow-up design](https://metr.org/blog/2026-02-24-uplift-update/) |
| **Borg et al., Echoes of AI, 2026 · Preregistered two-stage experiment** | Of 151 participants, 95% were professional developers. They implemented a feature in a Java web app with or without AI, and other developers continued the work without AI. The randomized follow-up stage found no significant difference in time or code quality. These results cover that feature and follow-up task. The cumulative effects of repeated agent work remain a separate question. [Journal article](https://link.springer.com/article/10.1007/s10664-026-10889-1) |
| **DORA, 2025 · Team surveys and interviews** | In research that included a survey of approximately 5,000 people, AI use correlated positively with throughput and negatively with delivery stability. These organizational observations make causal attribution difficult. They give teams a reason to track throughput and stability separately. [DORA report](https://dora.dev/research/2025/dora-report/) · [Research team announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report) |
| **Ogenrwot and Businge, 2026 · GitHub observational study** | The 24,014 merged agent PRs and 5,081 merged human PRs differed in commit counts, breadth of files modified, scale of deletions, and other characteristics. These observations cover merged PRs and the changes they contain. Reviewers can read the description alongside the actual changes and examine why the scope grew for the task in question. [MSR paper](https://arxiv.org/abs/2601.17581) |
| **Gloaguen et al., 2026 · Comparison of repository instructions, preprint** | The researchers evaluated generated instructions and instructions committed by developers. On the tasks evaluated, files such as `AGENTS.md` generally failed to improve success rates and increased inference costs by more than 20% on average. Agents tended to follow the instructions themselves. A reasonable starting point for OneStep is a short entry document that points to hard-to-find rules and explains how to run the relevant checks. [Paper v3](https://arxiv.org/abs/2602.11988) |
| **SWE-CI and SlopCodeBench, 2026 · Repeated-change benchmarks, preprints** | SWE-CI follows continuous integration on 100 tasks drawn from real repository histories. SlopCodeBench v2 had agents extend their own code across 36 problems and 196 checkpoints. The researchers' measure of structural deterioration increased in 77% of trajectories. Explicit quality instructions improved the initial measure, but the researchers observed no difference in subsequent deterioration rates. The percentage describes this benchmark. OneStep can adopt the practice of evaluating both the initial result and the next task. [SWE-CI](https://arxiv.org/abs/2603.03823) · [SlopCodeBench v2](https://arxiv.org/abs/2603.24755v2) |
| **Needle in the Repo, 2026 · Evaluation with structural constraints** | Across 23 model and tool combinations, 64 of 483 evaluation results passed every functional test and still failed a stated structural condition. In one example, a function transferring ownership also took over validation that belonged to the receiving module. These controlled problems illustrate a concrete reason to check ownership and dependency direction alongside functionality. [ASE paper, §§4–5](https://cs.ucr.edu/~qzhang/nitr-ase26.pdf) |
| **OpenAI, SWE-bench Verified audit, 2026 · Reassessment by the evaluation creators** | The authors reexamined 138 tasks that models consistently failed to solve over multiple runs. They found serious issues with test design or the problem statement in 59.4% of this selected failure sample. When a test fails because of an omitted instruction or an enforced internal implementation name, compare it with the product contract first. [Audit findings and examples](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) |

Developer use of assistants, agents carrying out successive tasks, and team-wide adoption involve different interventions and outcome measures. The conclusion this research applies is to **record preservation of existing quality on representative tasks separately from operating costs**. The available public evidence cannot establish the magnitude of the long-term effect for OneStep.

## 2. Established engineering methods and their limits in this setting

| Method | Original sources and application to OneStep |
| --- | --- |
| **Encapsulation and actual compatibility contracts** | Parnas proposed decomposing systems so that modules hide design decisions likely to change. Hyrum Wright's experience operating APIs shows that callers may depend on observable, undocumented behavior. Preserve stable entry points and investigate behavior existing callers rely on, such as sorting, event order, and failure codes. Actual dependencies and compatibility costs determine whether an incidental behavior should enter the formal contract. [Parnas's original paper](https://doi.org/10.1145/361598.361623) · [Hyrum’s Law](https://www.hyrumslaw.com/) |
| **Characterizing behavior and refactoring incrementally** | Feathers's characterization tests capture what the code currently does. Use callers and requirements to identify which behaviors need support. Fowler's refactoring boundary helps determine the interface at which to preserve observable behavior. Reviewing small preparatory refactorings separately from deliberate behavior changes clarifies why expectations changed. A Microsoft field study examined developers' stated motivations and risks alongside code metrics. [Feathers interview](https://techleadjournal.dev/episodes/195/) · [Fowler](https://martinfowler.com/bliki/RefactoringBoundary.html) · [Kim et al., FSE field study](https://thomas-zimmermann.com/publications/files/kim-fse-2012.pdf) |
| **Testing through public boundaries and real dependencies** | Google's testing guidance gives criteria for checking outcomes and public contracts and for using real dependencies or faithful doubles where the path requires them. Derive expected normal, failure, and boundary results from a specification, independent calculation, previous-version output, or fixed data. For deterministic paths, give the baseline and candidate identical inputs and compare meaningful outputs. Include independent cases that can catch errors both versions share. [Tests and change](https://abseil.io/resources/swe-book/html/ch12.html) · [Test-double fidelity](https://testing.googleblog.com/2024/02/increase-test-fidelity-by-avoiding-mocks.html) |
| **Checking that tests detect real faults** | In Inozemtseva and Holmes's Java experiments, the correlation between coverage and detection of mutation faults was low to moderate after controlling for test count. Use coverage to find missed paths. Google's practical research restricts mutation to code changed during review and filters low-value mutations. Even when working alone in OneStep, establish an independent expectation first, then deliberately break one or two important contracts and check that the tests fail for the expected reason. [ICSE coverage paper](https://cs.uwaterloo.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf) · [Google mutation testing study](https://research.google/pubs/practical-mutation-testing-at-scale-a-view-from-google/) |
| **Invariants and boundary input generation** | The original QuickCheck paper distinguishes input generation from property evaluation. Define externally observable invariants, such as applying a duplicate request only once or preventing a canceled operation from writing state. Record the seed and minimized failing input. Check how often the generator produces rare inputs such as long time gaps, empty state, or stale IDs. [Original QuickCheck paper](https://www.cs.tufts.edu/comp/150FP/archive/john-hughes/quick.pdf) |
| **Small review units and structural checks** | Google's review practice explains how reviewable units aid understanding and subsequent edits. Microsoft's code review field study observed knowledge transfer and understanding of changes alongside defect detection. In evolutionary architecture, a fitness function automates a structural condition that can be stated explicitly, such as dependency direction. In a mature codebase, record existing violations as the baseline and start by blocking new ones. Evaluate structural choices through a specific subsequent change. [Google code review](https://abseil.io/resources/swe-book/html/ch08.html) · [Bacchelli and Bird paper](https://www.ifi.uzh.ch/dam/jcr%3A4d711d23-ce10-4069-8214-eae91797e44b/icse2013.pdf) · [Building Evolutionary Architectures](https://evolutionaryarchitecture.com/precis.html) |
| **Fast feedback and overall suitability** | Meta's test selection example uses historical changes and failures to narrow the tests run in CI. In OneStep, run affected paths quickly, then supplement those runs with the broader checks the project supports for changes to shared foundations or important merges. Record the selection rationale and actual number run. [Meta Engineering](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/) · [Google regression test selection study](https://research.google/pubs/regression-test-selection-at-scale-4/) |
| **Migration with coexisting versions** | In `expand → migrate → contract`, add the new contract, move consumers, then retire the old contract. Branch by Abstraction breaks a large implementation replacement into small steps. Where a system is deployed, a canary can also use comparison groups, metrics, and stopping criteria. After a save-format change, data already written persists even if a feature switch is turned off. Verify actual reads and writes after rollback. [Parallel Change](https://martinfowler.com/bliki/ParallelChange.html) · [Branch by Abstraction](https://martinfowler.com/bliki/BranchByAbstraction.html) · [Google SRE on canaries](https://sre.google/workbook/canarying-releases/) |

## 4. Assigning a task in OneStep

OneStep already connects requirements and preservation conditions to their rationale during design. During implementation it calls for baseline runs, independent expectations, review of test changes, and checks through actual use. The repository's maintainability guidance also treats code size and complexity as two of several observations and calls for verification with representative change tasks. The first application is to decide **which evidence to fix in the current workflow and which boundaries to enforce automatically**. [Design review](../../skills/vegabond-code-design/references/review.md) · [Code verification](../../skills/vegabond-code/references/verification.md) · [Maintainability evidence](../../knowledge/code/K-CODE-MAINTAINABILITY-EVIDENCE.md) · [Agent instruction audit](../../knowledge/code/K-CODE-AGENT-INSTRUCTION-AUDIT.md)

1. **Define the task and the preservation contract.** In the existing brief, record the baseline revision, one sentence describing the behavior to change, the contracts that must continue to hold, representative callers, state owners, external data, and the run that will demonstrate success. Document the basis for behavior known only from past observation and for behavior the project promises to support. Investigate current callers or requirements when the distinction changes the outcome.
2. **Capture a baseline run.** For a bug, reproduce the failure for the intended reason before fixing it and record normal behavior in neighboring cases. For refactoring, preservation checks must pass on the baseline. For an intentional behavior change, establish the basis for the new expectation and the neighboring expectations to preserve. Record actual targets and execution counts so existing baseline failures, new failures, and environmental failures can be distinguished.
3. **Keep changes near the owner.** Define the contract exposed at the public boundary and the state the module manages internally. If migration needs stages, set preservation conditions for each. Update the brief and verification scope with new dependencies, compatibility changes, and side effects on failure discovered during implementation.
4. **Review the candidate product and its tests together.** Rerun preservation cases through the same public entry points under the same conditions. Compare expectations in added tests with requirements or fixed material. Read changes to assertions, fixtures, skips, filters, lint suppressions, and settings together and establish their reasons. Check that important protections detect a deliberately broken candidate and accept other valid implementations. A second reviewer or separate review session should use the same contract and firsthand execution results.
5. **Leave enough evidence to check the result again.** Hand over the commands run, revision, target, environment, results, accepted compatibility changes, and outstanding verification gaps. When deployment or persistent data is involved, verify the state after recovery. Link the evidence so the next agent can reach the same conclusion.

| Task risk | Additional evidence |
| --- | --- |
| Narrow local fix | Relevant existing tests and the reproduction path. Keep the record proportionate to the verified scope. |
| Shared boundary, content extension, or ownership transfer | Old and new callers, normal and failure paths, dependency directions, and a standalone run of removable optional content. Perform one actual follow-up change and examine the editing scope and effort needed to understand it. |
| Saves, API, ABI, multiplayer, asynchronous lifetimes, or frame budget | Applicable older data or mixed versions, interruption, retry and shutdown order, and actual runtime and build configuration. Measure performance contracts repeatedly with the same input, platform, build, and warm-up, using the project's budget and variability. |

Documents hold entry points, exceptions, and decision rationale. Put mechanically decidable conditions, such as commands, supported targets, and allowed dependency directions, in reproducible local checks. Once repeated use shows a check catches faults and accepts valid changes, connect it to the target project's CI. Diffs that change the meaning of a CI result or the test criterion itself need review. Projects using GitHub can designate required checks and reviews with rules where the repository supports them. [GitHub Rulesets documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)

For example, when adding an encounter pack to an existing game, record the execution contracts for the existing pack and base game, the owners of the pack loader and runtime state, the registration boundary the new pack may depend on, and commands that load each pack alone. Calculate test expectations from game rules and fixed inputs. Judge completion using both behavior and the files changed. Add the next pack through the same path and check whether this requires editing the loader or existing pack.

## 5. Verification in C++ and Unreal

| Verification target | Standalone C++ | Unreal C++ |
| --- | --- | --- |
| Behavior and failure | Pass fixed input to the actual public API or CLI and compare return values, state, and side effects. On paths with suspected lifetime errors or data races, also run a platform-supported sanitizer with that input. [AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html) · [ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html) | Check engine-independent rules with small tests. For behavior that depends on worlds, timers, shutdown, replication, or cooking, verify the relevant engine target and execution mode. [Epic Automation Test Framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-test-framework-in-unreal-engine) |
| Dependencies and encapsulation | Inspect `#include` scope, the CMake target link graph, and runtime registration. Check whether public headers and registration points reveal state ownership and the scope of change. Build or run with optional functionality physically removed to expose hidden connections. [CMake Graphviz options](https://cmake.org/cmake/help/latest/manual/cmake.1.html#cmdoption-cmake-graphviz) | Check public and private `Build.cs` dependencies, asset references, and runtime loading and activation order separately. When the contract covers both editor and packaged behavior, run both targets. [Epic Modules](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules) · [Reference Viewer](https://dev.epicgames.com/documentation/en-us/unreal-engine/reference-viewer-in-unreal-engine) |
| Save and recovery example | Load a previously generated save in the current version, induce a failure, then reread the existing file. If the contract covers concurrent saves or duplicate retries, check the final state on each path. | Shut down a world or transition maps with a timer or save callback still live. Observe whether the old world's owner writes after shutdown or old state enters the next world. |

OneStep already has limited firsthand evidence. **Crossing Tactics** detected a deliberately introduced hidden dependency between content packs by testing B alone. **Pulse Arena** reopened an actual Unreal Game world to check distinct file inventories and cooldowns, and its verifier rejected six cases with tampered results. This supports the execution scope recorded in the documents. Long-maintained existing code, multiplayer and packaging, and the cost of subsequent changes require separate evaluation. Earlier Unreal records also include a fix to a verifier that accepted an invalid combination of time and value. ## 6. An initial pilot to measure the effect

**Compare the existing process with the same process supplemented by one or two automated checks.** Select code with an existing contract and a history of changes in preference to a new feature demo. Start with a local bug, a content extension after a structural change, and a change involving compatibility or lifetime issues. Give separate working copies the same baseline revision and requirements and match the model, tools, time budget, and review criteria. Where possible, counterbalance run order by task and use the same independent checks for the final decision in both conditions.

| Observation point | Data to collect |
| --- | --- |
| Immediately after the first change | Failures of existing contracts relative to baseline, fulfillment of new requirements, new forbidden dependencies, weakened tests or verification settings, actual execution environment, and areas left unverified. |
| Two subsequent changes | Time to locate the owner and understand the contract, affected modules and registration points, rework requested in review, and detection of known faulty patches. Check other valid implementations to count excessive blocking. |
| Entire task | Time from generation through review and rework, tool and CI costs, waiting due to environmental failures, and counts of unnecessary blocks and actual defects. |

The first candidates are **a check for newly introduced forbidden dependencies** and **one preservation test through an actual entry point**. For an extension task, run with the existing pack, the new pack, both, and neither. Include a broken version in which the new pack silently requires the existing one. Expand coverage if the protections catch meaningful regressions at an affordable cost in the next two changes. Record the small pilot's results by task and trace deteriorating metrics to code, requirements, tests, or environment. This proposed application to OneStep is a hypothesis for the pilot to test.

# Research on Unity and C# game frameworks

2026-11-22 · Genre-specific architecture, content expansion, and preserving quality in existing projects

**Establish who owns game rules and state, then check that C# assemblies, asset references, and runtime lifetimes respect those boundaries.** Plain C# suits rules that can run independently, such as turn resolution and reward calculations. Implement and test Unity-owned behavior, including Inspector configuration, scene loading, input, physics, and animation, at the relevant engine boundary. A game can combine both approaches as needed. Test both adding and removing content to judge its independence. [Unity assemblies](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/script-compilation/assembly-definition-files/class-assembly-definition-importer) · [UnityBench-Mini3D](https://arxiv.org/abs/2610.35980)

Following the [C++ and Unreal framework survey](2026-11-21-cpp-game-framework.md) and the [survey on preserving quality during AI code changes](2026-11-21-ai-codebase-quality.md), this review focuses on the boundaries and execution evidence specific to Unity. Unity 6.3 LTS is the reference version for engine documentation. Package references give individual versions. In a real project, first check `ProjectSettings/ProjectVersion.txt`, `Packages/manifest.json`, `Packages/packages-lock.json`, deployment platforms, and the scripting backend. Official announcements about CoreCLR and .NET 10 in Unity 7.0 report development progress. Check feature availability in existing 6.x versions against the corresponding documentation and build. [Unity release policy](https://unity.com/releases/unity-6/support) · [Project manifest](https://docs.unity.com/en-us/engine/6000.3/manual/packages-list/managing-packages-manifest/upm-manifest-prj) · [CoreCLR progress update](https://discussions.unity.com/t/coreclr-scripting-and-net-update-october-2026/1738338)

## 1. Findings from papers and research

| Original source | Findings and scope |
| --- | --- |
| **Mizutani, Daros, and Kon, 2021 · literature review of game mechanics architecture** | Analyzed design requirements, constraints, and implementation trade-offs across 36 papers. Reducing development complexity was a common goal, and many solutions targeted particular games or genres. This supports identifying representative actions and changes first for turn-based, action, and real-time networked games. [Authors' copy](https://users.ime.usp.br/~kon/papers/SoftwareArchitectureForDigitalGameMechanics2021.pdf) |
| **Borrelli et al., MSR 2020 · empirical study of Unity code smells** | Investigated candidate game-specific issues through a survey of 68 respondents, including developers, and 100 open-source Unity projects. The study can help identify candidates related to performance, maintenance, and incorrect behavior. Prioritize them using the team's hot paths and actual failures, and examine the context of code flagged by a detector. [Conference paper and materials](https://2020.msrconf.org/details/msr-2020-papers/15/Detecting-Video-Game-Specific-Bad-Smells-in-Unity-Projects) · [Follow-up UnityLint tool paper](https://mdipenta.github.io/files/icpc2023-unitylinter.pdf) |
| **Redmond et al., OOPSLA 2025 · ECS concurrency theory and examples** | Gives conditions under which a program in the Core ECS model produces deterministic results regardless of scheduling and compares frameworks in actual use. Unity systems likewise need explicit read and write sets, update order, and a defined point when structural changes become visible. Reproduce network or physics determinism separately in the target environment. [Paper](https://arxiv.org/abs/2508.15264) |
| **Tasnim and Zhao, SAC 2026 · ECS model and comparison experiment** | Defines state transitions in an archetype-based ECS and compares alternatives in the same tower defense simulation. The authors report improved frame rate and stability under those conditions. The design can inform experiments comparing upper-percentile frame times and memory using identical input, entity counts, and hardware. [Paper](https://arxiv.org/abs/2606.14919) |
| **Zhou et al., UnityBench-Mini3D, 2026 · agent evaluation preprint** | Applied 1,178 human-written checks to 77 Unity project tasks, examining Scene structure, component configuration, and runtime behavior together. The tasks were short-term, so long-term maintenance requires separate measurement. This directly informs evaluation of AI work using the C# diff, serialized state, and observed play together. [Paper](https://arxiv.org/abs/2610.35980) |

| **Ryan Hipple · Unite Austin 2017** | Connects settings, variables, and events using ScriptableObjects. In the speaker's sample, trace which asset event publishers and listeners share. [Official Unity video](https://www.youtube.com/watch?v=raQ3iHhE_Kk) · [Speaker's code](https://github.com/roboryantron/Unite2017) |

Consult the Unity 6 documentation for current serialization constraints. | **Chop Chop · Unity Open Project** | The `SceneLoader` in `PersistentManagers` controls additive scenes. `SceneDataSO` represents a scene reference and associated data, and an Event Channel connects scenes. The public example shows both the ease of adding an area and the cost of tracing event connections in the same code. [Public source and architecture wiki](https://github.com/UnityTechnologies/open-project-1/wiki/Game-architecture-overview) · [Official development video](https://www.youtube.com/watch?v=WLDgtRNK2VE) |

When applying this pattern, check the RPC and synchronization APIs for the installed version. | **V Rising · Stunlock Studios** | Uses ECS to handle dynamic objects and a large world, with SubScene baking and streaming. Read the team's development account alongside Unity's case study to see why they separated content authoring inputs from runtime representation. This shipped game provides context for decisions about data scale, profiling results, and team tooling costs. [Development team's account](https://blog.stunlock.com/v-rising-dev-update-4-v-rising-engine-and-cutting-edge-technology/) · [Unity case study and developer interview](https://unity.com/resources/stunlock-studios-v-rising) |
| **MARVEL SNAP · Second Dinner** | Focuses on card content, Addressables packaging, and the build and test workflow for changing individual cards. Examine the authoring tools and delivery boundaries needed to add and distribute a single new card definition independently. [Unity case study with developer interview](https://unity.com/resources/marvel-snap) |
| **Unpacking · Witch Beam, GCAP 2023** | A talk on tools and pipelines for creating levels and objects. It shows how editing tools and validation support the addition of puzzle content. [GCAP video](https://www.youtube.com/watch?v=2j7AJj1oRSQ) · [Talk details](https://confpad.io/conferences/gcap-2023-empower/empowering-design-the-tools-and-pipelines-of-unpacking) |
| **Vampire Survivors · poncle** | The existing PC implementation and a new Xbox engine coexisted for a time. The developer interview explains the practical difficulties and workflow of keeping levels and content equivalent across both versions. It illustrates how a team compared existing play outcomes during an engine and framework change. [Xbox Wire developer interview](https://news.xbox.com/en-us/2023/04/13/vampire-survivors-dlc-2-launch/) |
| **Unity pattern examples and Robert Nystrom's book** | Unity 6 examples make it easy to compare state, strategy, command, and observer patterns in small pieces of code. Nystrom's `Component`, `Type Object`, and `Event Queue` also explain the costs of recombining components, adding data definitions, and separating event timing. [Unity 6 pattern resources](https://unity.com/blog/game-programming-patterns-update-ebook) · [Sample repository](https://github.com/Unity-Technologies/game-programming-patterns-demo) · [Author's edition](https://gameprogrammingpatterns.com/contents.html) |

The videos are listed alongside information checked against official descriptions, speaker samples, and creator documentation. Interpret the results of Unity's shipped-game case studies in each team's context. For data and events, read **Hipple → Chop Chop**. For runtime authority and large-scale simulation, follow **Boss Room → Stunlock**. For content authoring and delivery, follow **Unpacking → MARVEL SNAP**.

## 3. Choosing a framework to suit the genre

| Genre and representative play | Responsibilities and extension boundaries | First check to try |
| --- | --- | --- |
| Resolve a move or a single card in **turn-based tactics or deckbuilding** | Put command validation, turn-effect resolution order, and state in plain C# rules. Unity input and animation send commands and consume results. Register cards and encounters using stable IDs and definition data. | Use identical inputs and seeds to check legal and illegal commands and next-turn state. Add a new card or pack, examine the extent of core changes, and check how old saves resolve IDs. |
| Handle attacks, dodges, and interaction in **single-player real-time action** | Define where input becomes intent, who owns cooldown and hit state, and what physics and animation callbacks do. Build abilities from Unity components and configuration assets. Extract common rules as needed. | Exercise attack start, cancellation, death, respawn, and fixed-step boundaries in a real scene. Check both the core calculation and whether its result connects to input and animation. |
| Input and results arrive at different times in **cooperative or competitive multiplayer** | Specify authoritative server state, client input, prediction and presentation, and replicated state. Put IDs, ticks, and versions whose interpretation matters into the contract. Choose the engine and netcode based on concurrency, prediction, physics, and deployment conditions. | Run the target server with two or more clients and reproduce supported paths for success, failure, delay, loss, ordering, and reconnection. Exercise the host configuration separately. [Unity Network Simulator](https://mp-docs.dl.it.unity3d.com/tools/current/tools-network-simulator/) |
| Rooms or quests change in **puzzle, adventure, or content-driven games** | The scene or prefab owner assembles features. Definition assets contain authorable values and connections. Make duplicate IDs and broken references discoverable during editing. | Load the reference room and the new room separately. Check registration, save restoration, events before and after scene transitions, and behavior with the content removed. |
| Many entities update under the same rules in **simulation or high-entity-count games** | Measure bottlenecks and access patterns first. If needed, consider Jobs/Burst/Entities for that path and keep scene authoring at the baking boundary. Specify system reads and writes, their order, and when structural changes occur. | Compare frame-time distributions, memory, and correctness on the same device under the same load. If GameObjects and Entities exchange state for the same object, also test write authority and synchronization order. [Entities system order 1.4](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/systems-update-order.html) · [Baking 1.4](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/baking-overview.html) · [Official ECS samples](https://github.com/Unity-Technologies/EntityComponentSystemSamples) |

## 4. Boundaries in code, assets, and the runtime

| Design decision | Default approach and exceptions |
| --- | --- |
| **C# modules and dependency direction** | State the dependency direction the project will enforce, for example `Unity entry point → gameplay rules`. If an engine-independent group is useful, enable `No Engine References` on its `.asmdef` and configure Editor tools and tests for their respective targets. Verify new references in the `.asmdef` and by compiling. A small project can start with folders and a limited set of public types. Consider a UPM package when an independent delivery or reuse boundary emerges. [Assembly Definition settings](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/script-compilation/assembly-definition-files/class-assembly-definition-importer) · [Unity packages](https://docs.unity.com/en-us/engine/6000.3/manual/packages-list/packages/upm-overview) |
| **Inheritance, composition, and encapsulation** | Use a common base type when callers depend on the same initialization, error, and cancellation contract. Represent content differences through values, policies, components, or configuration data. Callers work through state transitions such as `TryUse`, and the module manages reservations, deductions, and error state together. Expose authoring inputs that require Inspector configuration through private fields marked `[SerializeField]`. Keep state changes with the owner. [Unity pattern examples](https://github.com/Unity-Technologies/game-programming-patterns-demo) · [Serialization rules](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/code-reload-serialization/script-serialization/rules) |
| **ScriptableObject and session state** | Normally use shared definition assets as read inputs. Sessions, components, or runtime instances own per-user progress, health, and cooldowns. If shared mutable state is required, document and test its initialization, readers, writers, and reset behavior when changing matches or scenes. Use an Event Channel for the publishing and subscription it needs. Consider direct requests for commands whose target and execution order must be known. [Separating data and logic](https://unity.com/how-to/separate-game-data-logic-scriptable-objects) · [Chop Chop architecture](https://github.com/UnityTechnologies/open-project-1/wiki/Game-architecture-overview) |
| **Scene, prefab, and asset dependencies** | Inspect serialized references with `AssetDatabase.GetDependencies`. With Addressables, inspect bundle duplication and grouping using Analyze or Build Layout. Identify the owner of any required shared asset. Check dynamic keys, loading from code, and remote catalogs in an actual launch. When independence is part of the contract, remove the optional content from the target catalog and build, then run it. [GetDependencies](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AssetDatabase.GetDependencies.html) · [Analyze 1.21](https://docs.unity3d.com/Packages/com.unity.addressables@1.21/manual/AnalyzeTool.html) · [Build Layout 2.7](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/BuildLayoutReport.html) |
| **Serialization and migration** | Preserve a baseline of GUIDs in `.meta` files and existing Scene and Prefab field references. When renaming a field, consider `[FormerlySerializedAs]` and load existing assets to check values and Prefab overrides. Consider `[SerializeReference]` when polymorphism or shared references are needed. Verify type or assembly moves by reloading old assets. Test game save files separately with actual older files and the conversion rules for supported save formats. [Asset metadata](https://docs.unity.com/en-us/engine/6000.3/manual/assets-and-media/import-assets/asset-metadata) · [FormerlySerializedAs](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Serialization.FormerlySerializedAsAttribute.html) · [SerializeReference](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/serializereference) |
| **Execution order, asynchronous lifetimes, and cleanup** | Decide whether the scene, object, or session owns initialization and cancellation. Release subscriptions scoped to activation on deactivation. Connect asynchronous work owned until object destruction to a lifetime signal such as `destroyCancellationToken`. Implement token observation and resource release. Check that an earlier completion cannot update state after pool reuse or a scene transition during loading. With Domain Reload disabled, check static state and subscriptions across consecutive Play sessions. [Event execution order](https://docs.unity.com/en-us/engine/6000.3/manual/scripting/managing-update-order/event-functions) · [Domain Reload](https://docs.unity3d.com/6000.3/Documentation/Manual/domain-reloading.html) · [Awaitable and threads](https://docs.unity.com/en-us/engine/6000.3/manual/scripting/programming-distribute-work-threads/async-await-support/async-awaitable-continuations) · [Destruction cancellation token](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/MonoBehaviour-destroyCancellationToken.html) · [.NET cancellation model](https://learn.microsoft.com/en-us/dotnet/standard/threading/cancellation-in-managed-threads) |
| **Build and performance** | Check the editor's C# language and API support, target backend, and managed code stripping. Unity 6.3 documents C# 9 and places constraints on using `record` with Unity serialization. Check platform-sensitive paths such as reflection-based registration, generated code, and generics in an actual IL2CPP Player. Compare frame times and memory with the same device, build options, content, and warm-up. [C# version](https://docs.unity3d.com/6000.3/Documentation/Manual/csharp-compiler.html) · [IL2CPP restrictions](https://docs.unity3d.com/6000.3/Documentation/Manual/scripting-restrictions.html) · [Code stripping](https://docs.unity3d.com/6000.3/Documentation/Manual/managed-code-stripping.html) · [Profiler documentation](https://docs.unity3d.com/6000.3/Documentation/Manual/profiler-profiling-applications.html) · [Official Unity Profiler video](https://www.youtube.com/watch?v=xjsqv8nj0cw) |

Consider Addressables for dynamic loading, remote delivery, or resource lifetime management. Identify who owns each acquired load handle and when to release it. Exercise that path on cancellation, failure, and reentry. For content updates in a shipped game, test the update build and recovery with supported combinations of older Players and catalogs. [Addressables memory 2.7](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/MemoryManagement.html) · [Content updates 2.7](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/content-update-builds-overview.html)

## 5. Verifying AI-assisted changes in a Unity project

1. **Establish the baseline and the behavior to preserve.** Identify editor, packages, platform, backend, and entry scene. Add the conditions under which current behavior must hold, representative assets and saves, intended changes, and owners of state, subscriptions, and loads to the existing work brief. For a bug, establish a baseline that fails for the intended reason. For a refactor, establish that the preservation cases pass.
2. **Match verification to the boundary.** Test deterministic rules and asset validity in Edit Mode. Observe input, scenes, prefabs, initialization, world state, and failures in Play Mode. For a deployment contract, run an actual Player with the same content to check differences in IL2CPP, stripping, remote loading, and networking. When using the CLI, check the selected filters, test counts, XML, and logs. [Unity Test Framework modes 1.4](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/edit-mode-vs-play-mode-tests.html) · [Command line 1.4](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/reference-command-line.html)
3. **Read code and authoring-data diffs together.** Inspect contract-relevant changes in `.cs`, `.asmdef`, Scenes, Prefabs, ScriptableObjects, `.meta`, `ProjectSettings`, and packages. When a script or field name changes, read the old assets in the editor to inspect connections and values, and find out why any related tests became less stringent. Text serialization makes the diff readable. Base the final judgment on observations in the editor and Player. [Prefab YAML](https://docs.unity.com/en-us/engine/6000.3/manual/working-with-scenes/text-scene-format/yaml-prefab-serialization) · [Smart Merge](https://docs.unity.com/en-us/engine/6000.3/manual/get-started/project-configuration/version-control/smart-merge)
4. **Introduce a defect the check should detect.** For example, verify that a candidate which mistakenly links pack B to a Prefab from pack A, or continues to receive events after scene exit, fails for the expected reason. Also confirm that another valid implementation passes. If the implementation and test duplicate the same formula, add a fixed, independently established expected value.
5. **Make the next one or two changes.** Record which modules and assets a new rule or piece of content affects, whether existing contracts still pass, and the review and rework costs. For small tasks, check the nearest boundary. For changes spanning versions, assets, or lifetimes, add the corresponding checks. ### Example for a first pilot

Take an existing tactics game with **encounter pack A installed and add pack B**. Preserve movement, turn resolution, and outcomes in the base game and pack A, along with restoration of existing saves. Pack B must register using its own definitions and Prefabs and be able to call required shared rules. In addition to inspecting the Editor tools' reference graph, run the actual Player with `base only`, `A only`, `B only`, and `A+B`. Use two deliberately faulty versions, one in which B's Prefab directly requires A and one that changes how existing turns resolve. Then add pack C and make a separate rule change. Compare whether each requires edits to existing packs or the core.

This example adapts the earlier C++ and Unreal [independent content execution example](../examples/cpp-gameplay-workflow/README.md) to Unity's Scene, Prefab, and Player boundaries. Building on OneStep's [gameplay framework design workflow](../../skills/vegabond-code-design/references/gameplay-framework.md) and general code verification, an initial approach for Unity work is to report **asset compatibility and verification in an actual Player** explicitly. This survey compares original sources with repository procedures. It includes no Unity sample project build or pilot execution results.

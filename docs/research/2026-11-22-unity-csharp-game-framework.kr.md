# Unity와 C# 게임 프레임워크 자료 조사

2026-11-22 · 장르별 구조, 콘텐츠 확장, 기존 프로젝트의 품질 보존

**게임 규칙과 상태의 소유자를 먼저 정하고, C# 어셈블리·에셋 참조·런타임 수명에서 그 경계가 실제로 지켜지는지 확인한다.** 순수 C#은 턴 처리나 보상 계산처럼 독립적으로 실행할 수 있는 규칙에 적합하다. Inspector 설정, 씬 로딩, 입력, 물리, 애니메이션처럼 Unity가 소유한 동작은 해당 엔진 경계에서 구현하고 테스트한다. 같은 게임에서도 두 접근을 필요한 만큼 섞을 수 있다. 콘텐츠는 추가와 제거를 모두 실험해야 독립성을 판단할 수 있다. [Unity 어셈블리](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/script-compilation/assembly-definition-files/class-assembly-definition-importer) · [UnityBench-Mini3D](https://arxiv.org/abs/2610.35980)

앞선 [C++·Unreal 프레임워크 조사](2026-11-21-cpp-game-framework.kr.md)와 [AI 코드 변경의 품질 보존 조사](2026-11-21-ai-codebase-quality.kr.md)에 이어, 이번에는 Unity에서 달라지는 경계와 실행 증거를 중심으로 다룬다. 엔진 문서는 Unity 6.3 LTS를 기준 예시로 삼았고 패키지 문서는 개별 버전을 표시한다. 실제 프로젝트에서는 `ProjectSettings/ProjectVersion.txt`, `Packages/manifest.json`, `Packages/packages-lock.json`, 배포 플랫폼과 스크립팅 백엔드를 먼저 확인한다. Unity 7.0의 CoreCLR과 .NET 10 관련 공식 발표는 개발 진행 상황이므로 기존 6.x의 기능 여부는 해당 버전의 문서와 빌드에서 확인한다. [Unity 릴리스 정책](https://unity.com/releases/unity-6/support) · [프로젝트 매니페스트](https://docs.unity.com/en-us/engine/6000.3/manual/packages-list/managing-packages-manifest/upm-manifest-prj) · [CoreCLR 진행 공지](https://discussions.unity.com/t/coreclr-scripting-and-net-update-october-2026/1738338)

## 3. 장르에 맞춰 프레임워크를 고르는 기준

| 장르와 대표 플레이 | 책임과 확장 경계 | 가장 먼저 시도할 검증 |
| --- | --- | --- |
| **턴제 전술·덱빌딩**에서 이동·카드 한 장을 처리한다 | 명령 검증, 턴 효과의 처리 순서와 상태를 순수 C# 규칙에 둔다. Unity 입력·애니메이션은 명령을 보내고 결과를 소비한다. 카드·조우는 안정적인 ID와 정의 데이터로 등록한다. | 동일한 입력·시드로 합법/불법 명령과 다음 턴 상태를 검증한다. 새 카드·팩을 추가해 코어 수정 범위와 구 저장에서의 ID 해석을 본다. |
| **실시간 싱글 액션**에서 공격·회피·상호작용을 처리한다 | 입력에서 의도로 넘어가는 경계, 쿨다운·피격 상태의 소유자, 물리와 애니메이션 콜백의 책임을 정한다. 능력을 Unity 컴포넌트와 설정 에셋으로 조립하고, 공통 규칙은 필요한 만큼 분리한다. | 공격 시작·취소·사망·재생성의 순서와 고정 스텝 경계를 실제 씬에서 실행한다. 코어 계산의 통과와 결과가 입력·애니메이션에 연결됐는지를 모두 확인한다. |
| **협동·경쟁 멀티플레이**에서 입력과 결과가 다른 시점에 도착한다 | 서버 권한 상태, 클라이언트 입력, 예측·연출, 복제 상태를 명시한다. 해석이 중요한 ID·틱·버전을 계약에 둔다. 엔진/넷코드 선택은 동시 접속, 예측, 물리와 배포 조건에 따른다. | 대상 서버와 둘 이상의 클라이언트에서 성공·실패, 지연·손실, 순서·재접속 등 지원 경로를 재현한다. 호스트 구성은 별도 실행 대상이다. [Unity Network Simulator](https://mp-docs.dl.it.unity3d.com/tools/current/tools-network-simulator/) |
| **퍼즐·어드벤처·콘텐츠 중심 게임**에서 방·퀘스트가 교체된다 | 씬이나 프리팹의 소유자가 기능을 조립하고, 정의 에셋은 저작할 값과 연결을 담는다. 중복 ID·깨진 참조는 편집 단계에서 찾을 수 있게 한다. | 기준 방과 새 방을 각각 로드한다. 등록, 저장 복원, 씬 전환 전후 이벤트, 콘텐츠 제거 상태를 확인한다. |
| **시뮬레이션·대량 개체 게임**에서 많은 개체가 같은 규칙으로 갱신된다 | 먼저 병목과 데이터 접근 패턴을 측정한다. 필요하면 해당 구간에 Jobs/Burst/Entities를 검토하고, 씬 저작은 baking 경계에 둔다. 시스템별 읽기·쓰기·순서와 구조 변경 시점을 정한다. | 동일한 부하와 기기에서 프레임 시간 분포, 메모리, 정확성을 비교한다. GameObject와 Entities가 같은 대상의 상태를 주고받는다면 쓰기 권한과 동기화 순서도 시험한다. [Entities 시스템 순서 1.4](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/systems-update-order.html) · [Baking 1.4](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/baking-overview.html) · [공식 ECS 샘플](https://github.com/Unity-Technologies/EntityComponentSystemSamples) |

## 4. 코드, 에셋, 런타임에서 지킬 경계

| 설계 판단 | 기본 접근과 예외 |
| --- | --- |
| **C# 모듈과 의존 방향** | 프로젝트가 지킬 방향을 `Unity 진입점 → 게임플레이 규칙`처럼 명시한다. 엔진 독립 그룹이 유용하면 `.asmdef`의 `No Engine References`를 사용하고, Editor 도구와 테스트는 대상별로 구성한다. 신규 참조는 `.asmdef`와 실제 컴파일로 확인한다. 작은 프로젝트는 폴더와 제한된 공개 타입부터 시작할 수 있다. 독립 배포·재사용 경계가 생기면 UPM 패키지를 검토한다. [Assembly Definition 설정](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/script-compilation/assembly-definition-files/class-assembly-definition-importer) · [Unity 패키지](https://docs.unity.com/en-us/engine/6000.3/manual/packages-list/packages/upm-overview) |
| **상속·조합·캡슐화** | 공통 기반 타입은 호출자가 실제로 의존할 초기화·오류·취소 계약이 같을 때 사용한다. 콘텐츠별 차이는 값, 정책, 컴포넌트, 설정 데이터로 표현할 수 있다. 외부는 `TryUse` 같은 상태 전이로 작업하고 모듈이 예약·차감·오류 상태를 함께 관리한다. Inspector 설정이 필요하면 `[SerializeField]`의 비공개 필드로 저작 입력을 열고, 상태 변경은 소유자에게 둔다. ## 5. AI에 맡긴 변경을 실제 Unity 작업에서 확인하는 흐름

1. **기준과 보존 계약을 잡는다.** 에디터·패키지·플랫폼·백엔드와 진입 씬을 확인한다. 현재 동작의 유지 조건, 대표 에셋과 세이브, 달라질 동작, 상태·구독·로드 소유자를 기존 작업 브리프에 남긴다. 버그면 의도한 이유로 실패하는 기준을 확보하고, 리팩터링이면 보존 사례가 통과하는 기준을 확보한다.
2. **검증을 경계에 맞춘다.** Edit Mode에서 결정적인 규칙과 에셋 유효성을 검사한다. Play Mode에서 입력·씬·프리팹·초기화·월드 상태와 실패를 관찰한다. 배포 계약이 관련되면 같은 콘텐츠로 실제 Player를 실행해 IL2CPP, 스트리핑, 원격 로딩, 네트워크의 차이를 확인한다. CLI를 쓰면 실행 대상으로 삼은 필터·테스트 수와 XML·로그를 확인한다. [Unity Test Framework 모드 1.4](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/edit-mode-vs-play-mode-tests.html) · [커맨드라인 1.4](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/reference-command-line.html)
3. **코드와 저작 데이터의 diff를 함께 읽는다.** `.cs`, `.asmdef`, Scene, Prefab, ScriptableObject, `.meta`, `ProjectSettings`와 패키지 변경 중 계약에 닿는 것을 확인한다. 스크립트 이름이나 필드가 바뀌면 에디터에서 구 에셋의 연결·값을 실제로 읽고, 관련 테스트가 약해진 이유를 확인한다. 텍스트 직렬화는 diff를 읽는 데 유용하며 최종 판정은 에디터와 Player의 관찰에 둔다. [Prefab YAML](https://docs.unity.com/en-us/engine/6000.3/manual/working-with-scenes/text-scene-format/yaml-prefab-serialization) · [Smart Merge](https://docs.unity.com/en-us/engine/6000.3/manual/get-started/project-configuration/version-control/smart-merge)
4. **보호 장치가 잡아야 할 결함을 넣어 본다.** 예를 들어 팩 B에 팩 A의 Prefab을 잘못 연결하거나, 씬 종료 뒤에도 이벤트를 수신하도록 만든 후보가 기대한 이유로 실패하는지 본다. 별도의 유효한 구현도 통과하는지 확인한다. 구현·테스트가 같은 계산식을 복제하는 경우에는 고정된 외부 기대값으로 보완한다.
5. **다음 한두 변경을 실제로 수행한다.** 새 콘텐츠나 규칙이 어느 모듈·에셋으로 퍼지는지, 기존 계약이 계속 통과하는지, 검토와 재작업 비용이 어느 정도인지 남긴다. 작은 작업은 가까운 경계의 확인만 적용하고, 버전·에셋·수명에 걸친 변경에는 해당 검증을 추가한다. [OneStep 코드 검증](../../skills/vegabond-code/references/verification.kr.md) · [변경 테스트 지식](../../knowledge/code/K-CODE-CHANGE-TESTS.kr.md) · [의존 방향 지식](../../knowledge/code/K-CODE-DEPENDENCY-DIRECTION.kr.md)

### 첫 파일럿으로 적합한 예시

기존 전술 게임의 **조우 팩 A가 있는 상태에서 팩 B를 추가**하는 과제를 쓴다. 보존 조건은 기본 게임과 A의 이동·턴·결과, 기존 세이브 복원이다. 추가 조건은 B가 자체 정의·Prefab만으로 등록되고 필수 공유 규칙을 호출할 수 있는 것이다. Editor 도구의 참조 그래프와 별도로 실제 Player에서 `기본만`, `A만`, `B만`, `A+B`를 확인한다. 통제 결함은 B의 Prefab이 A를 직접 요구하는 버전과 기존 턴 해석이 달라진 버전이다. 이후 팩 C를 추가하고 별도의 규칙 변경도 수행해 기존 팩과 코어까지 손대는지 비교한다.

이 예시는 앞선 C++·Unreal의 [독립 콘텐츠 실행 사례](../examples/cpp-gameplay-workflow/README.md)를 Unity의 Scene·Prefab·Player 경계로 옮긴 것이다. OneStep의 [게임플레이 프레임워크 설계 절차](../../skills/vegabond-code-design/references/gameplay-framework.kr.md)와 일반 코드 검증을 바탕으로, Unity 작업에서는 **에셋 호환성과 실제 Player 검증**을 명시적으로 보고하는 방식이 첫 적용 후보다. 이 문서는 원 자료와 저장소 절차를 대조한 조사이며, Unity 샘플 프로젝트의 빌드나 파일럿 실행 결과는 포함하지 않는다.

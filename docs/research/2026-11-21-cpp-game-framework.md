# Research on C++ gameplay frameworks

2026-11-21 · Gameplay code in standalone C++ and Unreal Engine 5

**Judge a framework by how far a change spreads.** When the inventory's internal data structure changes, do the edits stop at the inventory? When you add an ability, do the changes concentrate in its implementation and registration point? When the map changes, does the world clean up its state and subscriptions together? These three changes give you a starting point for evaluating modularity, extensibility, and lifetime management in practice.

Here, the framework is the code responsible for game rules, state ownership, feature composition, and integration with the engine. Renderer and physics engine implementations are relevant where their dependencies affect gameplay structure. Revisit the conditional suggestions below once the genre, multiplayer requirements, deployment targets, and performance budgets are known.

## Sources for design decisions

| Source | What to look for in the original | Question for our code |
| --- | --- | --- |
| Parnas, 1972 · paper | Decomposes the same system by processing stage and by information hiding. In `Improvement in Circular Shift Module`, an interface guarantees an ordering that callers do not actually need, limiting implementation choices. [ACM](https://doi.org/10.1145/361598.361623) · [Full paper](https://ckrybus.com/static/papers/decomposing_systems_into_modules_1972.pdf) | Which details must an inventory caller know: the slot array, the sort order, or the save format? Can we replace the array and preserve the contract for granting and querying items? |
| Liskov and Wing, 1994 · paper | Invariants and properties of state changes that can be inferred from a supertype must also hold for its subtypes. See §4.3 and §5.1. [Authors' copy](https://www.cs.cmu.edu/~wing/publications/LiskovWing94.pdf) | Do implementations of the same ability interface honor the same promises about cost and cooldown on failure and cancellation? |
| Daly et al., 1996, and Unger and Prechelt, 1998 · original experiment and replication | The relationship between inheritance depth and maintenance time varied with experimental conditions and tasks. The replication also reported a correlation between task time and the number of methods participants traced to understand the code. Both studies compare experimental tasks. [Daly paper](https://strathprints.strath.ac.uk/2676/1/strathprints002676.pdf) · [Replication](https://page.mi.fu-berlin.de/prechelt/Biblio/inheritTR.pdf) | Before capping hierarchy depth, can we count the overrides and indirect calls we have to follow to find the actual implementation and state change for one request? |
| Ullmann et al., 2025 · SyDRA paper | Groups `#include` relationships in 10 C++ engines into subsystems. In a 16-participant experiment on Godot, the resulting map helped with code comprehension and change-impact analysis. See §5–6 for the sample and experimental scope. [Paper](https://espace2.etsmtl.ca/id/eprint/29117/1/Petrillo-F-2024-29117.pdf) | If we examine source and build dependencies, asset references, and runtime call and lifetime relationships separately, can we explain the paths by which changes spread? |
| Redmond et al., 2025 · Core ECS paper | Models when ECS system queries and state changes are observed under different execution orders. Compares the conditions that preserve determinism with 5 real frameworks. See §4–5. [Paper](https://arxiv.org/abs/2508.15264) · [OOPSLA talk](https://www.youtube.com/watch?v=z2vqiVtmsuY) | Can we specify what each system reads and writes, and when structural changes take effect? Does changing the order change the result for identical input? |
| C++ Core Guidelines and WG21 P3019R14 · guidelines and standards proposal | Rules C.120, C.129, and C.133 cover the purpose of hierarchies, interface and implementation inheritance, and the costs of `protected` data. P3019R14 proposes the vocabulary types `indirect` and `polymorphic` for composition with value semantics using dynamic allocation. Check toolchain support for these types separately. [Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c-hier-class-hierarchies-oop) · [WG21 proposal](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3019r14.pdf) | Which representation for a replaceable policy makes ownership and the call contract clearest: a value, function, component, or runtime polymorphism? |

## Choosing how to modularize and extend gameplay

These design suggestions draw on the sources above. A single game can combine several approaches depending on the problem.

| Problem | Approach to consider first | Costs and contracts to check |
| --- | --- | --- |
| Rules shared by callers, such as item capacity, reward approval, or cooldowns | Put state and the operations that change it in the same C++ type or module. Rules whose implementation needs no engine state can be checked without the engine. | Check inputs, results, state after failure, cancellation, and retries. Look for added conversion code or duplicated state when extracting a rule. |
| Several Actors use features such as interaction and inventory in different combinations | Consider member composition in standalone C++ or Unreal's `UActorComponent`. Express content-specific values and combinations in assets or configuration that can be validated. | Check required companion components, Actor lifetimes, duplicate registration, and when configuration errors surface. Measure call and memory costs on performance-sensitive paths. |
| Swap implementations of one contract at runtime or override an engine hook | Use a narrow interface or a hook on an existing engine base class. Compose independently varying policies from types, functions, or components. | Use shared tests to verify that substitutes honor preconditions, postconditions, and invariants, and handle failure and cleanup consistently. |
| Isolate build dependencies or editor features | In Unreal, inspect public and private dependencies in `Build.cs` and the `Public` and `Private` headers. For standalone C++ projects that use CMake, inspect target dependencies. | Identify public headers that propagate dependencies and measure what actually rebuilds after a change. Trace asset dependencies separately in Unreal's Reference Viewer. [Unreal Modules](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules) · [CMake target linking contract](https://cmake.org/cmake/help/latest/command/target_link_libraries.html) · [Reference Viewer](https://dev.epicgames.com/documentation/en-us/unreal-engine/reference-viewer-in-unreal-engine) |
| Bundle mode-specific content or activate an optional feature independently | Ordinary modules can establish build boundaries. If runtime activation is required, consider Unreal Game Features and their activation and deactivation hooks. | Check cleanup of actions, input, subscriptions, and asynchronous requests, as well as reactivation, asset references, and cooking and packaging in the intended environment. `Deactivate` and `Unload` are separate stages. [Game Features](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-features-and-modular-gameplay-in-unreal-engine) · [Game Feature Action lifecycle](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameFeatures/UGameFeatureAction) |
| Repeatedly update the same data across many entities | Measure the target workload first. Compare archetype-based Flecs or MassEntity with EnTT's sparse-set storage. Include a simple contiguous array in the same scenario. | Inspect per-frame reads and writes, creation and deletion rates, changes in composition, scheduling, storage costs, debugging, and synchronization between data and Actors. [Flecs Quickstart](https://www.flecs.dev/flecs/Quickstart.html) · [EnTT developer talk](https://skypjack.github.io/pdf/the_cpp_of_entt.pdf) · [MassEntity documentation](https://dev.epicgames.com/documentation/unreal-engine/overview-of-mass-entity-in-unreal-engine?lang=en-US) |

### Concrete criteria for encapsulation

The inventory owns the invariants for quantity held and capacity. Define success, failure, and when state changes take effect in an operation such as `TryAdd`. Give the UI the values it needs to display and notifications of changes. Returning a mutable reference to an internal container can bypass the protection of a `private` field. If avoiding a copy requires a read-only view, include its lifetime and invalidation conditions in the interface. Validate save data at the read boundary, then apply it through the owning module. [Information hiding](../../knowledge/code/K-CODE-INFORMATION-HIDING.md) · [Data invariants](../../knowledge/code/K-CODE-DATA-INVARIANTS.md)

### Boundaries that matter in Unreal

- **Authority and presentation.** In multiplayer, `GameMode` exists only on the server, while `GameState` exists on the server and clients. Use this distinction to place match rules and the match state clients observe. Decide whether player state that must survive a respawn belongs to the lifetime of a Pawn or of `PlayerState`. Lyra's Pawn Extension tracks abilities granted because of the Pawn and removes them when the Pawn is destroyed or unpossessed. [Gameplay Framework Quick Reference](https://dev.epicgames.com/documentation/unreal-engine/gameplay-framework-quick-reference-in-unreal-engine?lang=en-US) · [Lyra ability initialization](https://dev.epicgames.com/documentation/unreal-engine/abilities-in-lyra-in-unreal-engine?lang=en-US#how-are-lyra-characters-initialized)
- **Lifetimes and references.** Match per-world state to the lifetime of the world and Game Instance-wide state to the lifetime of the instance. Consider a `TObjectPtr` marked with `UPROPERTY` when GC needs to trace a persistent strong reference to a `UObject`, a `TWeakObjectPtr` for a non-owning reference to an object that may be destroyed, or a `TSoftObjectPtr` for an asset to load on demand. Verify Actor cleanup in `EndPlay`, which also runs on map travel, streaming unload, and PIE shutdown. [Subsystems](https://dev.epicgames.com/documentation/en-us/unreal-engine/programming-subsystems-in-unreal-engine?lang=en-US) · [Object Pointers](https://dev.epicgames.com/documentation/en-us/unreal-engine/object-pointers-in-unreal-engine?lang=en-US) · [Actor Lifecycle](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-actor-lifecycle)
- **Requests and notifications.** Send a button's request to use an ability to the state owner through an operation that can return a result. On success, notify the UI or audio system of the confirmed result. For events consumed later, specify the data captured at publication, consumption order, and how to handle items remaining after shutdown. For subscribers that attach after initialization, design current-state queries alongside change notifications. [Event Queue chapter](https://raw.githubusercontent.com/munificent/game-programming-patterns/master/book/event-queue.markdown) · [Unreal Component Manager extension events and Init State](https://dev.epicgames.com/documentation/unreal-engine/game-framework-component-manager-in-unreal-engine?lang=en-US)

## A first feature for validating a design

Use **one ability with a cooldown** as the example. Request its use through input, check the conditions, apply the cost and cooldown, and display the result in the UI. Add a second ability and record which rules were reused and where the new implementation required changes. If abilities are peripheral to the game, a representative feature such as granting and consuming inventory items can also exercise state changes, failure, and presentation together.

| Scenario | Result to observe |
| --- | --- |
| Add a second ability | Locate the new ability's policy and registration point. Run the same tests for the contract shared with the existing ability. |
| Failure, cancellation, duplicate input | Check the request result and changes in cost and cooldown. Check whether a duplicate request charges the cost again and what state remains at every stage that allows cancellation. |
| Replace the UI or run without a HUD | Identical gameplay input yields the same authoritative result. Test with an actual client if multiplayer is required. |
| Late initialization, respawn, map transition | Even when required data arrives late, the feature runs only after readiness. Events, input bindings, timers, and asynchronous completion handlers associated with the previous Pawn or world are cleaned up. |
| Activate, deactivate, and reactivate a feature | Test this when introducing optional runtime features. Registration and cleanup are symmetrical, and handler counts do not grow after reactivation. The target package can enter the default play path with the feature disabled. |
| Save, update, and recover | When persistence is required, read older data and restore a valid state. Check for partial changes to existing state when loading fails or is canceled. |
| Compare bulk processing | If there is a bottleneck, compare frame-time distributions and peak memory with identical inputs, entity counts, and creation and deletion patterns. Check that required results agree even when processing order varies between frames. |

Check independent rules in the corresponding C++ tests. Exercise engine ownership, replication, and assets through functional tests and target builds. To compare maintainability, record the modules and files changed, public interfaces added, paths traced to locate normal and failure flows, and any regressions in existing behavior. The scenarios above are checks to apply to a proposed design. [Unreal Automation Test Framework](https://dev.epicgames.com/documentation/unreal-engine/automation-test-framework-in-unreal-engine?lang=en-US) · [Testing networked games](https://dev.epicgames.com/documentation/en-us/unreal-engine/testing-and-debugging-networked-games-in-unreal-engine)

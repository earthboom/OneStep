# Research on game development practices

2026-11-22 · Data changes, rendering, spawning and caching, monster and NPC AI, and offscreen simulation

**Separate the lifetime of authoritative game state from the lifetime of the object that represents it.** A distant monster can disappear from view and update its animation less frequently while its defeated status and quest state persist. If an individual bystander's route has no effect on the game, the game can create the actual object only when the player is nearby. Decide what to retain using camera distance together with **outcomes that players can observe or rules depend on**. [Simulation Level-of-Detail](https://pages.cs.wisc.edu/~schenney/research/culling/chenney-gdc2001.pdf) · [Unreal Mass Gameplay](https://dev.epicgames.com/documentation/unreal-engine/overview-of-mass-gameplay-in-unreal-engine)

This document applies the [C++ and Unreal framework survey](2026-11-21-cpp-game-framework.md), [Unity and C# framework survey](2026-11-22-unity-csharp-game-framework.md), and [survey of quality preservation during AI code changes](2026-11-21-ai-codebase-quality.md) to production and operational decisions. Read numbers and engine APIs in the context of the genre, hardware, and engine or package version at the time of each example. The implementation and verification suggestions below are candidates to test in the game.

| Decision | First question | Evidence to collect |
| --- | --- | --- |
| Add, modify, or delete data | Do older saves or mods use the ID and value? | Asset dependency graph, loading and migration of older files, release data validation results |
| Reduce rendering cost | Where does a real long frame wait: CPU, GPU, or I/O? | Target build capture, reproduction route, frame-time distribution, comparison of pixel and motion quality |
| Load, spawn, release, or cache | How long does it take from request to readiness, and how often is it reused? | Cold and warm latency, resident and peak memory, requests after cache eviction, spawn latency |
| Monster and NPC AI | Where do observation, decision-making, movement, animation, and world direction meet? | Decision rationale and cancellation logs, path failures and replanning, response latency within budget |
| Offscreen NPCs and objects | What outcomes must persist while the object is absent? | Transitions in both directions, reentry, continuity of quests, combat, sound, and replication |

## 1. Data lifetimes and change contracts

### Identify who writes each kind of data and when it ships

- **Authoring sources** contain values that designers edit, such as NPC definitions, dialogue and localization keys, combat numbers, and scene connections. They need source control, validation, and change history. If the engine's asset GUIDs or paths can change, explicitly fix the game IDs that saves and networking depend on.
- **Generated shipping data** includes validated catalogs and bundles, NavMeshes, lightmaps, and precomputed tables. It must be reproducible from the input data, conversion tools, and target platform. Invalidate the build cache when any of these changes, and compare build artifacts where identical results are required. If AI can edit generated output directly, check whether the next build overwrites the change.
- **Play session state** includes current HP, position, action, occupied slots or locations, and collected items. Assign ownership to the actual writer, such as the world, session, or server. Save the persistent subset, `schemaVersion`, and the necessary content versions and IDs. Appearance, NavMesh pointers, and load handles can be reacquired.
- **Live configuration** serves values that must change between deployments, such as balance and content availability. For settings that affect game rules, pin the version for the match or save, or swap a validated snapshot at a safe boundary. Check whether tasks mix old and new data during loading and whether server and client use the same version. [Bungie's asset pipeline](https://www.gdcvault.com/play/1025285/Tools-Tutorial-Day-Bungie-s) · [Factorio data lifecycle](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html) · [Unity bundle reproducibility](https://docs.unity.com/en-us/engine/6000.3/manual/building-and-publishing/build-deterministic-builds/assetbundles-addressables)

| Operation | Contract and handling | Examples that expose failure |
| --- | --- | --- |
| **Add** | Assign a unique ID and validate defaults, units, ranges, resource references, and package boundaries. In an actual build, check that the independent Beta monster pack does not implicitly pull in an existing optional pack. | Duplicate ID, invalid negative value, missing animation key, build without a particular optional pack |
| **Modify** | Separate display names from IDs used for compatibility. Changing a stat such as attack power, renaming a field, and changing its meaning or unit have different effects. Decide first whether existing entities in old saves retain their values or take the new definition. | The same monster in an older save, a value recorded in the old unit, a path where old and new versions coexist |
| **Delete** | First remove the entry from new spawn and drop tables, then inspect older references still in use. During the support period, provide a replacement ID, tombstone, safe fallback representation, or explicit load failure, as the contract requires. Once consumers finish using old data, remove the definition and associated assets. Do not reuse retired IDs while old data remains. | A save with the deleted item equipped, a quest or mod using its ID, a Player without the asset, rerunning migration |

Renaming the display name of `ForestWolf`, for example, leaves its ID intact. Before deleting `ForestWolf`, decide whether to migrate existing instances to a replacement monster, preserve existing instances only, or end support according to the save policy. Fail build validation for a missing required release reference. If development allows placeholders, record which input was substituted and why. Where save conversion can fail, replace the original only once the successfully converted result can be read back, and verify recovery after forced termination on the platform. ## 2. Rendering optimization sequence

1. **Reproduce the long frame.** Fix the target device, resolution, build, and quality options. Separate warm-up from measurements on a representative route and a near-worst-case route. Inspect median, p95, and p99 frame time, and the frequency and duration of over-budget frames. At 60 FPS the frame interval is about 16.67 ms. CPU and GPU execution overlap, so read stage times and waits on a timeline. [Unity profiling](https://unity.com/how-to/best-practices-for-profiling-game-performance) · [Unreal profiling](https://dev.epicgames.com/documentation/en-us/unreal-engine/introduction-to-performance-profiling-and-configuration-in-unreal-engine) · [Unreal Fest frame timing video](https://www.youtube.com/watch?v=dKSHw_8vz3I)
2. **Change one suspected cause at a time.** If lowering resolution shortens a GPU pass, investigate pixel cost. If CPU rendering submission takes a long time, consider state changes, draw calls, and batching. If shadows, skinning, or particles dominate, examine individual passes. If only first entry is slow, distinguish I/O, decompression, GPU upload, and PSO compilation. When using dynamic resolution, remeasure the relationship between quality and GPU cost on that platform. [Unity rendering captures](https://docs.unity.com/en-us/engine/6000.3/manual/analysis/graphics-performance-profiling/profile-rendering) · [Unreal dynamic resolution](https://dev.epicgames.com/documentation/en-us/unreal-engine/dynamic-resolution-in-unreal-engine) · [Unreal PSO Precaching](https://dev.epicgames.com/documentation/unreal-engine/pso-precaching-for-unreal-engine) · [Unity PSO warm-up](https://docs.unity.com/en-us/engine/6000.3/manual/materials-and-shaders/shaders/shader-troubleshooting/shader-reduce-stalling/shader-prevent-stutter/shader-pso-trace-warming/shader-pso-introduction)
3. **Measure the time saved and the new costs together.** Instancing and batching can reduce submissions. Different batching methods change memory use, culling granularity, and shader requirements. Frustum and occlusion culling reduce submissions, but the tests may be less worthwhile in scenes with few large occluders. For distance LOD and HLOD, inspect silhouettes, transitions, shadows, and rapid camera movement. After removing a pass, check whether the loss of effects such as reflections, transparency, or postprocessing is acceptable. [Unity draw call optimization](https://docs.unity.com/en-us/engine/6000.3/manual/analysis/graphics-performance-profiling/reduce-draw-calls/optimizing-draw-calls-choose-method) · [Unity URP GPU culling](https://docs.unity.com/en-us/engine/6000.3/manual/analysis/graphics-performance-profiling/in-urp/gpu-culling) · [Unreal visibility and occlusion](https://dev.epicgames.com/documentation/en-us/unreal-engine/visibility-and-occlusion-culling-in-unreal-engine)

## 3. Choosing runtime spawning, pooling, caching, and streaming

| Choice | When it fits | How to check costs and failures |
| --- | --- | --- |
| **Create and release on demand** | Calls are infrequent and latency is within budget, or the state is complex to initialize and reuse poses a high risk. | Check p99 and memory in a representative scene with many simultaneous spawns. Check that GC or native release occurs when expected. |
| **Reuse through a pool** | Similar objects such as projectiles and transient effects recur frequently, and creation and release are demonstrably expensive. | Set a capacity and exhaustion policy, and specify HP, timers, callbacks, and physics state to reset. Test whether a delayed callback from the previous generation can affect the reused object. Measure resident memory and activation cost. |
| **Cache derived results** | Recomputing or reading the same input is costly and reuse is likely. Partial navigation paths, build results, and selected resources are candidates. | Include inputs, version, and the relevant spatial range in the key. Invalidate on change. Measure the resident memory budget, time saved by hits, and use of stale values. Check whether areas traversed only once evict frequently used results. |
| **Bake ahead of time** | State changes infrequently, as with NavMeshes, lightmaps, and static placement, and offline work can reduce runtime costs. | Check that updated results ship after source changes and that update cost and artifact size are acceptable. Use a separate update strategy for changing conditions such as destruction or opening doors. |
| **Asynchronous prefetching and streaming** | Location or progress predicts the next resources needed, and keeping everything resident is expensive. | Budget I/O, decompression, and activation or upload separately. Prioritize immediate needs and safely release stale request results if the route changes. Measure round trips, teleports, slow storage, and memory pressure. |
| **Runtime procedural generation** | There are too many input combinations to store all fixed outputs, or generation itself is part of play. | Assign ownership of the seed, generator version, and changes made during play. Test cases requiring identical state after reload or a version change. Cache expensive results only when measurements show reuse. |

A pool **holds objects for reuse**. A cache **holds results that are expensive to obtain again**. To choose an effective tool, distinguish creation costs from first-load or shader compilation costs. An initial preload range estimate is `expected movement speed × resource preparation time + distance margin`. Then measure high-speed travel, the difference between entry and exit ranges, and repeated loading and unloading of the same resource. Activating too many loaded resources in one frame can cause a hitch, so give activation its own budget. [Nystrom, Object Pool](https://gameprogrammingpatterns.com/object-pool.html) · [Dirty Flag](https://gameprogrammingpatterns.com/dirty-flag.html) · [Unity pooling guidance](https://docs.unity.com/en-us/engine/6000.3/manual/analysis/performance-memory/managed-memory/optimizing-code-managed-memory/reusable-code)

## 4. Designing monster and NPC AI

**Start by writing down the behavior players should see and understand.** Will a guard investigate a sound? Does taking a hit interrupt an attack? What signal does a player see when an enemy loses its way? Trace `sensing → observation memory → decision → action execution → result` and record the evidence, time, and expiry. Separate movement planning, local avoidance, animation, and damage calculation so each can fail independently. As roles and actions multiply, test goals, preconditions, failure handling, and cancellation. [Halo 2 behavior design](https://www.gamedeveloper.com/programming/gdc-2005-proceeding-handling-complexity-in-the-i-halo-2-i-ai) · [Analysis of planning in games](https://cdn.aaai.org/ojs/12728/12728-52-16245-1-2-20201228.pdf)

| Choice | When it fits | Failure modes and sources |
| --- | --- | --- |
| **FSM or hierarchical state machine** | Relatively clear modes, such as boss phases, attack telegraph → execution → recovery, or guards patrolling, becoming alert, and returning | As transitions multiply, define common cancellation policies and the responsibilities of substates. Inspect entry and exit side effects. [Unreal StateTree](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-state-tree-in-unreal-engine) |
| **Behavior Tree** | Monsters with clear conditions and priorities, reusable subtrees, and designers who edit paths visually | Check that actions stop and clean up if priorities change during execution. Fix the meaning of `running/success/failure` for nodes and trace who writes the Blackboard. Unreal documents event-driven BT execution. [Iovino et al. literature review](https://arxiv.org/abs/2005.05842) · [Unreal BT](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---overview) · [Unity Behavior graphs](https://docs.unity.cn/Packages/com.unity.behavior%401.0/manual/behavior-graph.html) |
| **Utility AI** | NPCs score health, distance, resources, and allies' situations to choose among valid actions | Tune score units and response curves, tie-breaking, and the criteria for retaining the current action. Log candidate scores and the reason for selection. Watch for repeated switching over small score differences. [Dave Mark and Kevin Dill, GDC 2010](https://media.gdcvault.com/gdc10/slides/MarkDill_ImprovingAIUtilityTheory.pdf) |
| **GOAP or HTN** | Obstacles or multiple means of reaching a goal change the sequence of actions an NPC needs | Cap planning time, expanded nodes, and the number of replans. Provide fallback actions when no plan exists or execution fails, and verify cases where planning data and execution state diverge. GOAP in F.E.A.R. and HTN in games including Killzone 3 illustrate the distinction between planning success rate and suitability in play. [Orkin talk](https://gdcvault.com/play/1013459/Three-States-and-a-Plan) · [Planning analysis of three FPS games](https://cdn.aaai.org/ojs/12728/12728-52-16245-1-2-20201228.pdf) |
| **Group control and encounter direction** | Managing a group's attack order, the order of entry onto a road, or tension and rest in an encounter | Assign ownership of shared resources such as spawns, seats, and attack slots separately from individual NPC decisions. Check whether the group exceeds its budget or multiple NPCs simultaneously claim the same resource. Left 4 Dead used a director to control encounter flow. [Valve talk video](https://www.gdcvault.com/play/1422/) · [Original presentation](https://cdn.fastly.steamstatic.com/apps/valve/2009/GDC2009_ReplayableCooperativeGameDesign_Left4Dead.pdf) |

Separate path selection from avoidance as well. NavMeshes and shared paths find traversable routes, local avoidance reacts to nearby movement, and occupancy and entry limits manage traffic order at narrow doors and bottlenecks. Without an escape or yielding rule, local avoidance can leave agents stuck. In the actual layout, inspect path failures, budget overruns, wait times, and deadlock recovery. Unity AI Navigation and Unreal AI Perception provide starting points for navigation and sensing. The game defines the contract for behavior decisions. [Recast and Detour source](https://github.com/recastnavigation/recastnavigation) · [ORCA paper and code](https://gamma-web.iacs.umd.edu/ORCA/) · [Unity AI Navigation](https://docs.unity.com/en-us/engine/6000.3/manual/packages-list/packages-all/pack-safe/com-unity-ai-navigation) · [Unreal AI Perception](https://dev.epicgames.com/documentation/en-us/unreal-engine/ai-perception-in-unreal-engine) · [OneStep crowd resources](../../knowledge/game/K-GAME-TECH-CROWD.md)

## 5. Objects and NPCs outside the camera view

Beyond visibility, games have sound, shadows and reflections, collisions, combat effects, quests, and other cameras or network observers. **Decide rendering visibility, animation, physics and collision, AI, network replication, and memory residency separately.** A nearby offscreen pursuer may still need sound, collision, and threatening actions. For a distant citizen walking the same commute, some games need only a schedule and the next arrival time. [Carlson and Hodgins, 1997](https://graphicsinterface.org/proceedings/gi1997/gi1997-1/) · [Unreal Mass Gameplay](https://dev.epicgames.com/documentation/unreal-engine/overview-of-mass-gameplay-in-unreal-engine)

| State | Work to perform | What to check before transitioning |
| --- | --- | --- |
| **Full updates** | Maintain sensing, movement, animation, and collision at the necessary fidelity for close combat, important NPCs, and objects prominent on camera. | What raises the cost in long frames and the minimum update conditions the game rules require |
| **Partial updates** | Reduce AI, sensing, and animation frequencies independently and distribute entity updates across frames. Let important events wake an entity immediately. | Maximum response latency, collision and message ordering, and visual artifacts when a stationary object suddenly moves |
| **Summary simulation** | Retain a stable ID, area, goal, expected time of arrival, HP, and quest state. Advance on events or at low frequency. Compute group-level outcomes if needed. | Before promotion to normal simulation, apply results exactly once, restore at a valid location, and honor guaranteed combat and quest rules |
| **Suspend or unload** | For objects allowed to stop acting, save their next scheduled time or persistent state and release heavy representations and resources. Distinguish removed objects with saved defeat or retirement records. | Duplicate spawns on reentry, defeated entities returning, resource leaks, or hitches from bulk respawning after a long absence |

Alongside distance and onscreen status, consider **combat involvement, potential damage, objective importance, recent interactions, and the nearest relevant player** when deciding transitions. Reduce oscillation at boundaries using different promotion and demotion thresholds or a minimum residence time. Hand off authority over timers, events, and area occupancy during transitions so only one side writes them. For long absences, compute only required outcomes and limit catch-up work in any single frame. In split-screen and multiplayer, verify against all relevant observers, including cases where only some cameras see the object. [Chenney, GDC 2001](https://pages.cs.wisc.edu/~schenney/research/culling/chenney-gdc2001.pdf) · [Epic Significance Manager](https://dev.epicgames.com/documentation/unreal-engine/significance-manager-in-unreal-engine)

For example, a closed door outside the camera view may still need to participate in NPC pathfinding and collisions even if drawing it is skipped. When a quest companion transitions, preserve dialogue, objectives, death state, and server authority. Reconstruct animation and incidental foot placement on reentry. Decorative crowds can retain just local density and flow when individual identity need not persist. Once preservation requirements are clear, run full updates and summary simulation with the same long-term inputs to decide which differences are acceptable. [Simulation Level-of-Detail](https://pages.cs.wisc.edu/~schenney/research/culling/chenney-gdc2001.pdf) · [S.T.A.L.K.E.R. developer interview](https://www.gamedeveloper.com/game-platforms/interview-inside-the-ai-of-i-s-t-a-l-k-e-r-i-)

## 6. Testing the decisions together in one scene

Use a small **village → forest entrance → skirmish → return to village** route as the baseline. Put a quest NPC and decorative citizens in the village and combat monsters and an optional content pack in the forest. Choose the target device and frame interval. For each case, specify the behavior the game promises for offscreen combat, movement, or saving. It should be possible to reproduce the return trip, including preceding state, in a fresh engine run.

| Experiment | Method | Result to record |
| --- | --- | --- |
| Add, modify, and delete data | Add a monster pack, change stats and the display name, and replace a definition referenced by a save. Load an older save. Also use candidates with duplicate or missing references. | Supported saves continue combat and quests, and invalid data reports the problematic ID and reference. |

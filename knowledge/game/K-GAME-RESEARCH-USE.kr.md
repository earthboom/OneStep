# 게임 개발 단계에서 적용 가능한 근거 찾기

**K-GAME-RESEARCH-USE** · 작업 관례 · 사용 중 · 근거 확인 2026-11-11

이 저장소를 사용하도록 허용된 게임 기획, 아키텍처, 구현, 디버깅, 최적화 작업에 적용한다. 실제 결정이나 관찰한 증상에서 출발해 자료가 목표 게임의 조건에 맞는지 비교하고, 채택 여부와 확인할 결과를 작업 요약에 기록한다. 현재 게임의 설계와 코드, 인수 조건이 우선한다. 검색어는 게임 기획, 기술 선택, 구현, 디버깅, 최적화, 장르, 지식 조회, GDD, 프로토타입, 플레이테스트, 근거와 채택이다. 과거 엔진 실험의 범위와 자료 접근 조건은 개별 항목을 따른다. 등록된 출처는 과거 자료의 식별자이며 현재 접근이나 재실행을 보장하지 않는다.

## 지침

먼저 결정해야 할 사항, 기능 또는 재현된 증상을 적는다. 프로젝트와 리비전, 엔진·패키지 버전, 플랫폼과 입력, 의도한 경험, 프레임·자원 예산, 네트워크와 상태의 권한을 필요한 만큼 확인한다. 결함이 있다면 재현 절차와 측정한 증상을 남기고, 모르는 조건은 명시한 채 확인할 수 있는 근거부터 찾는다.

구체적인 단서 한두 가지에서 시작해 [게임 목록](index.md)과 [조회 절차](../../skills/vegabond-knowledge/references/retrieval.md)를 따른다. 관련 코드 지식과 문제 기록도 확인한다. 의존성, 충돌, 답을 얻지 못한 질문이 있을 때 검색을 넓힌다. 표현만 달라 결과가 없을 수 있으므로 증상, 동작 원리, 다른 언어의 표현을 활용하고 [기법 안내](K-GAME-TECH-GUIDE.md)를 참고한다. 검색 순위는 후보를 찾는 용도다.

콘셉트나 복합 장르는 [경험 설계](K-GAME-DESIGN-FRAMEWORK.md), 경험에 대한 불확실성은 [프로토타입과 플레이테스트](K-GAME-PROTOTYPE-PLAYTEST.md), 자원 상호작용은 [게임 경제](K-GAME-ECONOMY.md), 상호작용 장벽은 [접근성과 온보딩](K-GAME-ACCESSIBILITY-ONBOARDING.md)에서 시작한다. 협동 로그라이크에서도 전투, 협동 페이싱, 회차 구조, 자원 설계는 서로 다른 질문이다.

조회 실패가 생기면 표현 문제인지, 필요한 규약 자체가 확인되지 않았는지 구분한다. 기법 이름이나 유사어를 바꿔 좁은 범위에서 다시 찾는다. 특정 업체 API, 비공개 형식, 버전별 보장이 여전히 불명확하면 정확히 무엇이 부족하고 어느 결정이 그에 의존하는지 적는다. 가장 작은 공식 문서나 실험으로 이를 해결하고, 독립적으로 근거를 확보한 작업은 진행한다. 일반적인 유사 사례나 검색 결과 부재만으로 특정 보장을 확정할 수 없다.

여러 후보가 나오면 결정을 먼저 나눈다. 각 후보의 표현 방식, 요구 입력, 보장, 권한, 버전과 관측 비용을 비교한다. 경로 탐색과 국소 회피, 시각 표면과 물리 충돌, 그래픽 품질과 경쟁 상황에서의 시인성은 각각 다른 확인이 필요하다. 각 부분의 역할과 전제 조건이 맞는 경우에 조합한다.

각 항목의 지침, 적용 범위, 확인 방법과 근거를 읽고 실제 엔진 버전, 데이터 소유권, 하드웨어와 설계 제약을 비교한다. 중요한 선택마다 **채택**, **조건부 채택**, **기각** 중 하나와 이유를 남긴다. 요약에서 확정할 수 없는 API나 동작은 원 출처를 보거나 필요한 부분만 조사한다. 출처에서의 관찰, 전용을 위한 해석, 목표 게임에서 시험할 가설을 구분한다.

기존 작업 요약에 ‘문제와 제약 → 항목 ID와 관련 절·출처 → 결정과 이유 → 예정 변경 → 확인한 결과 또는 남은 질문’을 짧게 기록한다. 늦은 점프 입력은 CONTROLLER의 입력 버퍼와 TIMESTEP의 시뮬레이션 규칙을 함께 검토하고, 숲 장면의 비용은 지오메트리·픽셀·그림자 비용을 나눠 측정한 뒤 FOLIAGE의 인스턴싱이나 LOD를 고른다. 선택한 기법을 대표 프로토타입이나 회귀·성능 검사와 연결한다.

조사나 구현을 마치면 실제 결과, 기각한 유추, 실패 조건과 수정점을 [지식 절차](../../skills/vegabond-knowledge/SKILL.md)에 돌려준다. 새로운 근거가 재사용 조건을 바꿀 때 기존 공유 항목을 보강한다. 프로젝트 고유의 사건·데이터·코드·로그·튜닝값은 원 프로젝트에 둔다. 재현 절차, 플랫폼, 권한 또는 기획 의도가 바뀌면 영향받는 판단을 다시 확인한다.

큰 기획은 [대규모 계획 조율](../../skills/vegabond-planning/references/large-plans.md)에 따라 선택한 방법을 기존 구조, 의존 시스템, 인수 검사와 연결한다. 해당 게임의 설계와 플레이테스트 결과가 우선한다.

## 적용 범위와 예외

게임 작업을 위해 요청된 조회 관례다. 다른 프로젝트를 변경할 권한은 별도다. 단순하고 안정된 패턴은 기존 조사가 여전히 적용되는 이유만 남겨도 된다. 복합 장르의 권고가 충돌하면 목표 경험을 기준으로 해당 절충점을 시험한다. 액션 RPG의 전리품, 공장 관리, 개별 4X 설계로 장르 전체를 일반화할 수 없다.

입력 자료만으로 해결되는 철자나 서식 수정은 정확한 변경 사항과 보존할 필드를 확인한다. 게임 관련 파일이라는 이유만으로 기법을 검색할 필요는 없다. 실제 규약, 의존성 또는 불확실성이 영향을 줄 때 검색한다.

특정 스포츠, 격투 형식, VR 신체감, MMO 사회 구조, 플랫폼 정책 등은 필요할 때 추가 자료를 찾는다. 접근하지 못한 영상이나 검색 요약과 시험하지 않은 제안은 검증된 동작의 근거가 될 수 없다. 다른 프로젝트에서는 허용된 출처 범위 안에서 이 저장소를 조회한다.

## 확인

- 자료가 실제 결정·증상, 엔진 버전, 하드웨어, 권한, 장르 기법과 제작 조건에 맞는가?
- 인용을 통해 구체적으로 달라진 행동이나 검사 항목이 있는가?
- 채택 여부와 이유가 있고, 과거 관찰과 목표 게임 가설 및 필요한 시험을 구분했는가?
- 현재 프로젝트의 권한, 의도한 모호성, 접근성, 경쟁 공정성이나 다른 시스템과 충돌하는가?
- 부족한 자료를 밝혔고, 실제로 이에 의존하는 결정만 보류했는가?

카탈로그와 스키마 검사는 저장 구조와 검색 가능 여부를 확인한다. 재미, 밸런스, 사용성, 시장 성과는 별도의 근거가 필요하다.

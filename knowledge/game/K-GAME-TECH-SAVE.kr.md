# 버전이 있는 복구 가능 세이브와 소형 비밀번호 상태 설계

## 지침

런타임 포인터 대신 영속 상태, 안정적인 객체 ID, 스키마 버전을 직렬화한다. 독립 플래그는 필요에 따라 비트 단위로 묶는다. 비밀번호 세이브는 작은 복원 가능 상태를 제한된 문자 집합으로 인코딩하고 오류 검출 정보를 포함한다. 마지막 정상 슬롯을 교체하기 전에 새 세이브를 검증하고 복구할 세대를 남긴다.

### 구현 조사 후속 — 2026-11-07

포켓몬 에메랄드의 공개 재구현에서는 저장 카운터로 슬롯을 선택해 섹터를 쓰고, 마지막 정상 상태를 추적한다. 로드는 섹터를 검증해 유효한 세대를 선택한다. 이 근거에는 원본 제작사 소스나 로컬 실행이 포함되지 않는다. 새 구현에는 세대 ID, 페이로드 검증, 슬롯 반영과 복구 순서를 명시한다. 사이먼스 퀘스트 역공학 자료는 상태 7바이트, 합산 검증값 2바이트와 스크램블링 1바이트를 16글자로 인코딩하는 사례를 설명한다. 복원 대상은 아이템·경험·날짜 상태다.

## 적용 조건과 예외

체크섬은 일부 데이터 손상을 탐지한다. 데이터 인증이 필요하면 별도 수단이 필요하다. 8비트에는 독립적인 참·거짓 플래그 8개를 담을 수 있다. 파일 두 개를 유지하는 설계에는 교체 경계와 오류 처리 규약이 필요하다.

언리얼의 USaveGame은 게임에서 정의한 영속 상태를 담는다. AsyncSaveGameToSlot은 게임 스레드에서 객체를 직렬화하고, 작업 스레드에서 저장한 뒤, 게임 스레드의 완료 델리게이트로 결과를 전달한다. 완료 결과를 확인하고 대상 플랫폼에서 쓰기 실패 시 이전 정상 세대가 읽히는지 검증한다. [Epic AsyncSaveGameToSlot](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UGameplayStatics/AsyncSaveGameToSlot?application_version=5.8)

## 적용 전 확인

실험마다 후보, 슬롯 반영 경계, 예상 세대를 기록한다. 외부 프로세스에서 쓰기 단계별로 저장 프로세스를 강제 종료하고 기존 저장 디렉터리로 재시작한다. 슬롯 바이트와 복원된 전체 월드 상태를 비교한다. 유효하지 않은 값이나 누락된 객체 연결 때문에 로드가 거부되면 월드 상태가 그대로인지 확인한다. 프로세스 강제 종료, 용량 제한 쓰기, 물리 전원 차단은 각각 별도의 검증이다.

## 이전 언리얼 검증 — 2026-11-14

게임 스레드에서 체력, 체크포인트, 아이템 32개와 스위치 8개를 안정 ID로 저장했다. 348바이트의 상태를 USaveGame에 직렬화했고 패키지의 전체 컨테이너는 2,433바이트였다. 기본 방식은 A 슬롯 하나를, 복구 방식은 A/B 두 슬롯을 사용했다.

엔진 역직렬화 전에 식별자, 버전, 스키마, 길이, 헤더와 페이로드 CRC32를 검증했다. 상태의 개수, ID, 값도 검증한 뒤 가장 높은 정상 세대를 골랐다. 유효한 슬롯이 없거나 같은 세대 번호의 충돌이 있으면 실패했다. 로드는 파일을 수정하지 않았고, 월드 복원 전에 객체 연결 전체를 확인했다. 재실행한 프로세스는 오브젝트를 역순으로 생성했다. 체력, 체크포인트, 아바타 변환, 아이템 가시성과 스위치 회전을 별도로 검사했다.

규칙 검사 89개, USaveGame·저장소 검사 23개와 실제 PIE·패키지 사례 48개를 확인했다. 재실행 6건에는 정상 로드, 잘림과 손상, 이전 세대 복구와 무효 파일에서의 월드 보존이 포함됐다. 같은 1280×720 환경에서 기본·복구 방식 각 3회, 회당 준비 32프레임과 측정 256프레임을 실행했다. 저장, 로드, 월드 반영과 전체 프레임 비용은 당시 직접 쓰기 방식의 측정치다. 30Hz로 캡처한 420프레임을 같은 속도로 재생한 14초 영상도 보관했다.

신뢰한 로컬 파일과 고정 상태를 검증했다. V54 비밀번호 포맷의 구현과 실제 게임 저장의 비동기 최적화는 별도 작업이다.

## 언리얼 임시 파일 반영과 스키마 이행 — 2026-11-21

정상 세대와 교체 대상 슬롯을 유지한 채 같은 디렉터리의 임시 파일에 후보를 쓴다. 임시 파일의 버퍼를 플러시하고 닫은 뒤 바이트와 상태를 다시 읽어 검증한다. 이후 교체 대상 슬롯에 반영한다. 시작 시에는 반영된 슬롯만 후보로 삼는다. 슬롯 교체가 끝나면 호출자가 성공을 전달받기 전에 프로세스가 종료되더라도 재시작에서 새 세대를 선택할 수 있다. 이 예제는 Windows에서 같은 디렉터리 안의 파일 교체와 단일 게임 스레드 작성자를 사용한다. [Microsoft MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)

Win64 Development에서 직렬화, 임시 파일 열기, 첫 부분 쓰기, 전체 쓰기, 플러시·닫기, 재검증 직후를 시험했다. 이 경계에서는 임시 후보를 무시했다. 교체가 끝난 뒤에는 새 세대를 선택했다. 용량을 제한한 시험에서는 임시 파일 128바이트를 실제로 쓴 다음 공간 부족 오류를 주입했다. 운영체제가 반환하는 실제 공간 부족 오류는 용량이 제한된 별도 대상 볼륨에서 확인해야 한다.

구버전은 현재 형식의 새 값에서 이행한 뒤 월드에 적용한다. 시험용 v0의 체력, 체크포인트, 아이템 플래그는 그대로 옮기고 v1에 추가된 스위치 8개는 모두 꺼진 값으로 채웠다. 구버전 데이터가 유효하지 않으면 다른 정상 슬롯을 선택하거나 명시적으로 실패한다. 디코딩 실패나 월드 연결 누락 시 복원 전후 상태 전체가 같고 저장 파일도 변하지 않는지 확인한다.

이 근거의 범위는 시험한 파일 배치, 단일 작성자와 API 호출 사이의 종료 경계다. 물리 전원 장애, 파일 시스템 호출 도중의 종료, 실제 볼륨 고갈, 여러 작성자, 이미 출시한 파일 형식은 각각 검증해야 한다. 임시 파일 쓰기 경로를 플레이 중 사용한다면 플러시가 포함된 게임 스레드 지연을 다시 측정한다.

같은 UE 5.8.3 Win64 Development 패키지에서 12개 조건을 3회씩, 총 36쌍으로 검증했다. 외부 강제 종료 21건에는 7개 경계가 포함됐다. 나머지 사례는 제한 용량, 정상 v0, 대체 슬롯이 있는 손상 v0, 대체 슬롯이 없는 손상 v0, 월드 연결 누락이다. 재실행 전후 A/B 슬롯과 임시 파일의 바이트를 독립적으로 확인했다.

## Windows의 실제 NTFS 디스크 공간 부족 — 2026-11-21

Windows 파일 작업이 실패하면 정리나 로그 기록 전에 오류 코드를 확보한다. 실패한 작업, 오류 코드, 요청한 바이트와 실제 쓴 바이트를 함께 남긴다. 여유 공간은 안내에 쓸 수 있으며, 임시 파일의 검증과 슬롯 반영 여부는 실제 파일 작업 결과로 결정한다. [Microsoft WriteFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-writefile) · [Windows 오류 코드](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-)

64MiB 고정 VHDX에 포맷한 NTFS 볼륨과 UE 5.8.3 Win64 Development 패키지를 사용했다. 정상 조건 3회는 2,433바이트의 3세대를 저장하고 재실행 시 복원했다. 여유 공간 0바이트인 실제 고갈 조건 3회는 임시 파일에 64바이트를 쓴 뒤 페이로드 쓰기의 WriteFile이 오류 112(ERROR_DISK_FULL)를 반환했다. 기존 A/B 슬롯의 해시와 게임 월드 상태는 그대로였다. 가득 찬 상태로 재실행하면 2세대가 복구됐고, 공간을 확보한 뒤에는 새 3세대가 저장되고 다시 불러와졌다.

시험용 채움 파일을 닫은 뒤 여유 공간을 확인한다. 닫을 때 사용하지 않은 예약 공간이 반환될 수 있다. 파일 쓰기·플러시·교체 실패 시 기존에 반영된 슬롯을 보존하고 호출자에게 실패를 알린다. 공간을 확보한 뒤에는 정상 저장 경로로 다시 시도하고, 재실행에서 슬롯 바이트와 월드 전체를 비교한다. 이 결과는 기존 저장 디렉터리와 단일 작성자를 사용한 NTFS 시험 범위에 적용한다.

## V54 진행 코드 저장 — 2026-11-21

복원할 진행 상태의 필드 순서와 버전을 고정한다. 이 예제는 버전 4비트, 체력 0–100에 7비트, 체크포인트 0–3에 2비트, 아이템 32개와 스위치 8개의 플래그를 합쳐 53비트에 담았다. 7바이트 페이로드의 CRC-16 16비트와 예약 비트 1개를 더해 5비트씩 14자로 표현한다. 사용 문자는 I·O·0·1을 제외한 32종이다. 길이·문자·예약 비트·체크섬·버전·값 범위와 대상 오브젝트 연결을 확인한 뒤 월드를 변경한다. 새 버전을 도입할 때는 기존 코드가 참조하는 필드 순서와 객체 ID 연결을 보존한다.

UE 5.8.3 Win64 패키지에서 대표 상태를 별도 프로세스에서 생성해 같은 코드를 얻었다. 시작 인자로 코드만 전달한 재실행 4쌍에서 대표·반복·최소·최대 상태와 오브젝트 40개가 일치했다. 잘못된 입력 8건에서 디코더 출력과 월드 전체가 유지됐다. 정상 체크섬을 가진 미지원 버전과 체력 101도 거부했다. 각 생성 실행에서 가능한 한 글자 치환 434개를 모두 거부했다.

같은 정상 상태 4개를 같은 순서로 인코딩·디코딩·월드 반영했다. 3회 모두 단계당 8,192개를 측정했다. 32회 묶음에서 구한 작업당 평균의 p95는 인코딩 0.291–0.375µs, 디코딩 0.609–0.728µs, 월드 반영 4.178–6.972µs였다. 이 값은 고정된 오브젝트 40개의 유효 입력을 적용하는 조건에 해당한다.

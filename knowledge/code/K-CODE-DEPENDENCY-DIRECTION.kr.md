# 정책을 보호하는 계약을 향해 의존성 정하기

## 지침

출처에서 확인한 내용: Martin의 1996년 DIP 글은 정책과 구현이 추상화에 의존하고 추상화는 구현 세부 사항에 의존하지 않아야 한다고 주장한다. Effective Go는 동작 중심의 인터페이스를 보여준다. Google의 빌드 장은 명시적인 직접 의존성과 우연히 따라오는 전이 의존성을 구분한다. 이 자료들은 서로 다른 의존성 메커니즘을 다룬다.

종합 지침: 보존할 정책과 변할 가능성이 큰 세부 사항을 찾고 정책의 필요를 표현하는 계약을 고른다. 의도적으로 필요한 경우가 아니라면 공급자 타입, 데이터베이스 행, 전송 오류, 설정 선택으로 계약을 정의하지 않는다. 객체 구성을 이해할 수 있는 곳에 생성과 구체 구현 선택을 모은다.

소스, 빌드, 런타임 관계를 따로 그린다. 런타임에 어댑터를 호출한다고 해서 정책 소스가 구체 구현을 가져와야 하는 것은 아니다. 반대로 인터페이스를 전달해도 의미, 수명, 순서, 공유 상태에 대한 의존성은 남는다. 가져오기 개수와 함께 변경 전파와 알아야 할 지식을 평가한다. 변동이 잦은 공유 스키마 하나가 여러 안정적인 라이브러리보다 더 큰 영향을 줄 수 있다.

## 적용 조건과 예외

대체 경계, 외부 연동, 비용이 큰 부수 효과, 독립적으로 진화하는 정책에 역전을 적용한다. 유용한 분리 지점에 실제 운영 구현이 하나뿐일 수도 있다. 구현이 여러 개라도 계약이 다르면 공통 추상화를 공유할 필요는 없다.

클래스마다 기계적으로 인터페이스를 만들거나 의존성 주입 컨테이너 또는 어댑터 두 개를 만들지는 않는다. 안정적인 구체 타입이나 내부 보조 기능에는 간접 참조가 필요 없을 수 있다. 매개변수, 콜백, 프로토콜, 트레이트, 표준 계약으로 충분할 수 있다. Martin의 C++ 예시는 역사적인 논거이며 Go의 암시적 인터페이스 충족은 해당 언어의 기능이다. 프레임워크의 소유권과 생성된 인터페이스가 배치 위치를 제한할 수 있다.

## 점검

선택한 구현에 적용할 제안 점검이다.

- 어댑터 API를 고르기 전에 정책이 요구하는 연산과 보장을 적는다.
- 소스와 빌드 그래프에서 금지한 구체 구현 참조, 순환, 선언하지 않은 직접 의존성을 찾는다.
- 현실적인 세부 사항 변경을 가정하고 유출된 데이터 타입과 오류 타입을 포함하여 정책 수정 위치를 찾는다.
- 해당하는 경우 실제 어댑터로 계약 동작을 확인한다. 테스트 대역만으로는 연동 호환성을 입증할 수 없다.
- 인터페이스를 없애는 사고 실험을 한다. 변동성, 지식 의존성, 테스트 비용이 늘지 않는다면 가치를 재검토한다.

## 근거

- [Martin, The Dependency Inversion Principle](https://www.cs.utexas.edu/users/downing/papers/DIP-1996.pdf): 5–7쪽과 10–11쪽의 Copy, 계층, 어댑터 논의를 대학 미러의 원문으로 확인했다.
- [Effective Go](https://go.dev/doc/effective_go#interfaces): “Interfaces and other types”의 동작 계약을 확인했다. 페이지는 2009년 지침이 활발히 갱신되지 않는다고 경고한다.
- [Software Engineering at Google 18장](https://abseil.io/resources/swe-book/html/ch18.html): “Internal dependencies”에서 빌드에 한정된 권고를 확인했다. 실제 프로젝트의 아키텍처나 성능 결과는 확립하지 않았다.

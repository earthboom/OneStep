# 구체적인 후속 변경으로 유지보수성을 판단하기

K-CODE-MAINTAINABILITY-EVIDENCE · 참고 지식 · 2026-11-21. 리팩터링의 이익을 평가할 때 대표적인 이해·수정 작업, 보존할 계약과 변경의 파급을 함께 살핀다.

## 지침

Kim·Zimmermann·Nagappan의 Microsoft 조사에서는 의존성과 복잡도가 줄면서 크기는 커진 사례가 있었다. 인터뷰·설문·Windows 이력에서 나온 상관관계로 독립적인 인과 효과를 확정할 수 없다. Tempero·Blincoe·Lottridge의 학생 40명 실험에서는 모듈화 수준이 더 높은 Java 설계에서 수정 성공이 높았고, 이해도 저하 경향의 p값은 .07이었다.

향후 대표 변경과 유지할 동작을 먼저 정한다. 유지보수자가 알아야 하거나 바꿔야 하는 소스·결정·의존성·테스트를 따라간다. 정확성·노력·변경의 국소성·빌드와 런타임 비용·설명 부담을 비교하고 상충 관계가 있으면 종류가 다른 후속 변경도 시도한다. 코드 지표는 확인할 지점을 찾는 데 쓰고 예측·완료된 변경·장기 효과를 나눠 기록한다.

AI 변경은 기준 리비전과 기존 공개 진입점을 대표 입력이나 구버전 호출자로 확인한다. 실제 보존 계약과 아직 결정이 필요한 관찰을 구분한다. 패치와 함께 어설션·건너뛴 검사·픽스처·억제 변경도 검토하고, 반례로 검사가 실패할 수 있는지 확인한다. 실제 런타임이나 지원 빌드가 필요한 주장은 그 환경에서 검증한다. [변경 검증](K-CODE-CHANGE-TESTS.kr.md)

같은 리비전·과업·모델·도구·예산·인수 조건에서 현 절차와 의존성·보존 검사를 추가한 절차를 비교한다. 국소 수정, 콘텐츠 확장, 수명·호환성 변경과 후속 변경을 포함한다. 정상 인수·의도치 않은 영향·리뷰와 재작업 시간·과도한 거부·결함을 기록한다. 선택 모듈은 각각·동시·둘 다 없는 경우와 이웃에 몰래 의존하는 반례를 확인한다.

## 적용 조건과 검증

Windows 관찰 연구와 학생 Java 실험만으로 이상적인 클래스 수나 간접화 수준을 정할 수 없다. 팀의 경험과 도구, 작업 분포를 고려한다. 반증 가능한 유지보수 이득과 원래 기능 계약을 선언하고 영향받은 호출자와 통합 작업을 확인한다. 담당자가 표현 방식의 이유와 다음 변경 위치를 설명할 수 있는지 본다.

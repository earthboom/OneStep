## 활용 지침

출처 관찰: Kim·Zimmermann·Nagappan은 설문·면담·Windows 이력으로 리팩터링을 연구했다. 의존·복잡도 감소와 코드 크기 증가가 함께 나타났고 인과 해석을 제한했다 [S1]. Tempero·Blincoe·Lottridge는 학생 40명에게 Java 설계 둘을 비교했다. 높은 모듈성에서 수정 성공이 높았지만 이해도 저하는 통계적 경향이며 보편 효과로 확정되지 않았다 [S2].

응용 방법: 대표적인 후속 변경과 보존할 동작을 정한다. 유지보수자가 알아야 하거나 바꿔야 할 출처·결정·의존·시험을 추적한다. 현재와 제안 구조를 정확성·노력·변경 국소성·빌드와 실행 비용·설명 부담으로 비교한다. 상충점이 드러날 수 있으면 다른 종류의 변경도 포함한다.

지표는 질문을 찾는 데 쓰고 실제 작업·근거를 확인한다. 구조 이익이 불확실하면 범위가 정해진 실험·변경 흐름 검토를 선호한다. 논리적 예측·완료한 수정·장기간 결함과 생산성 근거를 구별한다.

## 적용 조건과 예외

Windows 연구는 특정 대규모 작업의 상관이며 독립된 인과 증명이 아니다. 학생 실험은 제한된 과제·이해 질문을 사용했고 이해도 경향은 p=.07이었다. 이상적 클래스 수나 간접 계층을 늘리는 보편 선호를 도출하지 않는다. 팀 경험·도구·과제 분포에 따라 결과가 다를 수 있다.

## 확인 항목

제안 점검: 반박 가능한 유지보수 이익과 보존할 기능 계약을 명시한다. 국소 코드뿐 아니라 변경 호출부·통합 의무를 확인한다. 표현의 이유와 다음 변경 위치를 설명할 수 있는가? 줄 감소·인터페이스 증가·점수 하나로 더 좋은 소프트웨어를 입증했다고 주장하지 않고 관찰 결과·한계를 보고한다.

# 전체 추론 비용을 줄일 때 추상화 도입하기

## 지침

출처에서 확인한 내용: Ousterhout는 단순한 인터페이스 뒤에 풍부한 기능을 두고 그대로 전달하기만 하는 계층을 경고한다. 일반성 권고 역시 현재 기능에 연결된다. Fowler의 YAGNI는 추측에 따른 기능 추가를 피하되 리팩터링은 허용한다. Design Stamina 글은 생산성 보상을 객관적 증명이 없는 가설로 명시한다.

종합 지침: 추출 전후에 호출자가 이해해야 하는 내용을 비교한다. 안정적인 개념, 규칙의 소유권, 숨겨지는 결정의 이득을 추가 계약, 코드 탐색, 설정, 간접적인 제어 흐름, 디버깅, 호환성 비용과 비교한다. 줄을 옮기기만 하면 복잡성의 위치만 달라질 수 있다.

의미상 중복과 우연한 유사성을 구분한다. 함께 바뀌어야 하는 하나의 규칙을 공유하면 불일치를 막을 수 있다. 반면 독립적으로 진화하는 규칙을 구문이 비슷하다는 이유로 합치면 무관한 변경이 결합된다. 이는 제안하는 판단 기준이지 인용 자료에서 실증한 결과는 아니다. 도메인을 더 이해할 때까지 일시적인 중복이 선택의 자유를 보존할 수 있다.

현재 필요를 충족하는 최소한의 유용한 일반화를 고른다. 지역 보조 함수, 구체 모듈, 표준 인터페이스로 충분할 수 있다. 계약이 클라이언트를 단순하게 해 준다면 깊은 모듈은 상당한 구현을 담을 수 있다. 깊이가 무관한 책임이나 불투명한 동작을 정당화하지는 않는다.

## 적용 조건과 예외

중복 코드 추출, 계층 도입, 재사용 API 설계에 적용한다. 반복 횟수는 단서일 뿐 보편적 기준이 아니다. 구현 두 개나 복사본 세 개가 자동으로 올바른 경계를 뜻하지 않는다. 복잡한 연동 하나가 즉시 추상화를 필요로 할 수도 있고, 비슷한 계산 여러 개가 별도 소유를 유지해야 할 수도 있다.

공개 API, 호환성 약속, 비싼 마이그레이션, 알려진 변화는 이른 설계 노력을 정당화할 수 있다. YAGNI는 변경 용이성을 유지하는 일을 허용한다. 예상 재사용만으로는 가치를 확립할 수 없다. 저자들은 일반성의 강조점이 다르며 보편적인 크기 목표, 투자 공식, 측정된 회수 시점 대신 판단 근거를 제공한다.

## 점검

제안하는 설계 검토 항목이다.

- 현재 호출자를 변경 전후로 보여 주고 각각 알아야 하는 결정과 보장을 적는다.
- 공유 규칙과 클라이언트가 함께 바뀌어야 하는 이유를 명시한다. 단지 닮은 연산은 분리한다.
- 삭제한 줄뿐 아니라 추가 개념과 설정 분기도 센다.
- 가능한 새 사례와 서로 달라지는 사례를 따라가며 추상화가 일관성을 유지하는지 확인한다.
- 정책, 격리, 의미 있는 계약이 없는 전달 계층을 재검토한다. 리팩터링 후 실제 동작을 검증한다.

## 근거

- [Ousterhout, Modular Design](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign): “Classes Should be Deep”, “Generic Classes are Deeper”, “New Layer, New Abstraction”을 저자가 제공하는 2018년 노트에서 확인했다. 책 전체를 읽은 것은 아니다.
- [Fowler, Yagni](https://martinfowler.com/bliki/Yagni.html): 2015년 글의 추측성 기능 비용과 리팩터링 설명을 확인했다.
- [Fowler, Design Stamina Hypothesis](https://martinfowler.com/bliki/DesignStaminaHypothesis.html): 2007년 글의 개념 그래프, 가설의 한계, 설계 비용 회수 논의를 확인했다. 실제 프로젝트 구현은 평가하지 않았다.

# Measure what an AI change preserves across successive edits

## Guidance

Record the baseline revision, changed behavior, supported public contract, representative callers, state owner and failure effects. Characterization tests describe observed behavior. Check callers or requirements before promising to preserve an accidental behavior. For a bug, reproduce the failure and adjacent successes. For a refactor, establish a passing preservation baseline. For a new behavior, derive its expected outcome independently.

Review production and test changes together, including skipped cases, rewritten fixtures, baselines, filters, suppressions and thresholds. Compare saved inputs or independently calculated expectations through the normal entry point. Challenge a critical check with a deliberately broken candidate and another valid implementation. Use coverage to find unexercised paths. For generated inputs record seed, minimized counterexample and the frequency of rare cases.

Use fast affected tests on routine edits. Widen the scope for shared dependencies, compatibility, lifecycle and performance. Check optional packs individually and together. During staged migration add the new contract, migrate consumers and retire the old contract. A feature switch can leave persistent data in its new format. Exercise reading and writing after rollback.

## Applicability and exceptions

Measure delivery stability, throughput, follow-up effort and total review/rework separately. METR's 16 experienced developers took 19% longer across 246 familiar-repository tasks in its early-2025 experiment. Follow-up selection and parallel-work measurement complicated a current estimate. Borg et al.'s 151-person Java experiment found no significant difference in the randomized follow-up. DORA's roughly 5,000-person survey reported associations. Merged PR observations omit rejected changes.

SlopCodeBench reported structural deterioration in 77% of its trajectories. Needle in the Repo found 64 of 483 results passed functional tests while violating structural constraints. SWE-bench's 59.4% finding concerns 138 selected consistently failed tasks. Repository instruction experiments reported over 20% extra inference cost on average. These populations and outcomes do not establish an expected effect size for another team.

## Checks

Compare the normal process against the addition of one dependency rule and one public-path preservation test. Match revision, requirements, model, budget and final independent checks. Counterbalance order when possible. For two subsequent edits record owner-location time, files and registrations touched, false blocks, missed defects, review and rework. Record command, target, count, environment and unresolved cases. C++ can inspect CMake/public includes and optional builds. Unreal additionally needs asset references and the applicable world, cook, package or replication path.

## Evidence

The November 21 source review distinguished controlled studies, observational studies, preprints, benchmark audits and team retrospectives. Crossing Tactics detected a hidden pack dependency, and Pulse Arena checked an actual reopened Game world and rejected six altered results. These examples did not evaluate long-term maintenance or all packaging and network configurations. The comparison above is a proposed pilot.

## When to investigate “AI slop” in a code change (source review, 2026-11-26)

Use “AI slop” (AI 슬롭, AI 코드 부실, 과잉 설계) as shorthand for a concrete review question. Which supported behavior is wrong, which dependency is unnecessary, or what will the next person have to rediscover? Attribution, verbosity and line count alone cannot answer those questions.

| Finding | Evidence and boundary | Decision for this repository |
| --- | --- | --- |
| Passing behavior tests can conceal a new coupling. | In Needle in the Repo, 64 of 483 evaluated outcomes passed the functional checks and failed a specified structural constraint. In SlopCodeBench v2, structural erosion rose in 77% of trajectories across an iterative benchmark of 36 problems and 196 checkpoints. Both measure particular constraints or proxies. [Needle in the Repo](https://cs.ucr.edu/~qzhang/nitr-ase26.pdf) · [SlopCodeBench v2](https://arxiv.org/abs/2603.24755v2) | For independently installable features, run the feature alone. For two implementations of one rule, change the rule once and check both callers. A second abstraction is warranted when a present caller or contract needs it. [Fowler on YAGNI](https://martinfowler.com/bliki/Yagni.html) |
| A maintenance penalty is not universal. | In a preregistered two-phase study with 151 participants, new developers extending Java solutions without AI showed no significant difference in time or code quality by whether AI had assisted the original change. One follow-up task cannot settle the cost of a long change sequence. [Borg et al., Echoes of AI](https://link.springer.com/article/10.1007/s10664-026-10889-1) | Compare a matched subsequent change, including reviewer effort. Avoid labelling a short, adequate implementation as low quality because another team used more structure. |
| An explanation can make a wrong expected result sound credible. | In a study with 86 Python programmers, judgment accuracy was 74% for correct generated assertions and 49% for incorrect ones. Explanations gave no overall improvement. This tests assertion assessment, not all code review. Ask which input distinguishes a wrong version from a correct alternative. |
| An API or package name that reads naturally still needs a contract. | Spracklen et al. studied package recommendations across 16 models, 576,000 code samples, Python and JavaScript. The study establishes the failure mode, not the error rate for Unreal APIs or this environment. [USENIX Security paper and talk](https://www.usenix.org/conference/usenixsecurity25/presentation/spracklen) | For a new dependency, verify identity, installed or pinned version, and the one operation the real caller needs. | Review can shift work onto the maintainer. | LLVM explains why contributors must understand the work they submit. Google's review guide advocates cohesive, independently understandable changes. Both describe project practice. Tufano et al.'s November 24 preprint classifies 87 kinds of developer-attributed issues from selected commits, conversations and interviews; it supplies examples, not prevalence among all patches. ## Conditional development pilot, 2026-11-26

Two fresh AI workers received identical copies of a small Python booking app, its written contract and the same local English guidance. Only the design and implementation skill paragraphs differed. Each worker corrected the caption, reviewed the pending rollout before editing, repaired it, then maintained its own result through two requests revealed in sequence. Review means the implementer's timed review of the same incoming patch. Timings include reasoning, shell and test latency between local monotonic markers. Session setup, inter-request waits and independent scoring are outside the timers. These are AI elapsed times from one pair on a shared Windows host. | Seeded defects missed during review, out of three | 0 | 0 |
| Valid alternate implementations rejected, out of one | 1 | 0 |

Both suites exposed an explicit closure reopening under the default, admission at the closing hour and a feed ignoring the venue. Independent checks passed at delivery (9), after overnight support (15) and after pickup (50) for each arm. No extra repair was required after scoring. The existing suite also required the feed to work with the desk module removed. The published contract promises feed hours when the desk is closed, and the fixture ships both modules. An alternative that calls the installed desk function passed every public check. Only the conditional suite accepted it. If independent installation becomes a requirement, the standalone check gains a contractual basis.

Each follow-up changed one runtime file in each arm. Combined follow-up time was 94.0 versus 78.9 seconds, with 20 versus 30 added test lines. Both workers handled the caption directly and changed one line in one file. This trial supports keeping the check conditional. ## OneStep repository trial, 2026-11-26

**Decision. Keep the distinguishing case for changes where existing evidence leaves a concrete ambiguity.** Record the governing caller and the observable difference in the usual handoff. Run an additional faulty or valid alternative when the available test could pass the suspected defect or reject a supported implementation. An existing public-path check that settles the question is sufficient. This recommendation retains the lightweight exception demonstrated by the booking pilot. The field results give no reason to routinely execute another comparison for every shared-rule or dependency edit.

Eight fresh workers used the actual production scripts at revision `99cd60c`. Each task ran twice per procedure. Both members of each pair reviewed the same proposed partial patch and requirement, repaired it, and then received the same follow-up. The incoming defects were deliberately introduced and stayed in isolated copies. The installer gained a read-only check, followed by single-adapter selection with the shared strategy still required. The knowledge reader gained a project-relative JSON selector file with a standard-library-only dependency contract, followed by BOM and empty-list support. The historical distribution ZIP supplied the installer integration environment. The reader also ran its six existing tests. ## Stopping when existing assertions settle the case, 2026-11-26

The design handoff now points to the caller's expected result and the existing public-path assertion. Implementation runs the relevant test on the change. A passing assertion that would reject the suspected fault and allow an equivalent implementation ends this check. A remaining doubt calls for the smallest comparison that can settle it. [Design rule](../../skills/vegabond-code-design/SKILL.md) · [Implementation rule](../../skills/vegabond-code/SKILL.md)

Eight fresh workers repeated the installer and section-reader follow-ups above. Within each pair the starting production code, tests, request, risk hint and optional comparison runner matched. The control used the previous conditional paragraphs. Each task ran once per procedure with an adequate existing assertion and once with a known gap. Independent calibration verified that only the weakened suite accepted the faulty implementation. One suite omitted the check for a current selected adapter with a missing shared strategy. The other stripped whitespace before comparing stdout with an empty string.

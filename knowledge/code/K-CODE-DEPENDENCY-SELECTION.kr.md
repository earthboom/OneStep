# 수명주기 가치와 소유 비용으로 의존성 선택하기

## 지침

출처에서 확인한 내용: Cox는 재사용을 지속적인 위험을 수반하는 엔지니어링 외주로 보고 의존성을 살피고, 시험하고, 격리하고, 재검토하라고 권고한다. Go 문서는 모듈 목록 확인, 업데이트, 정리 절차를 제공하며 버전 지침은 호환성 신호와 불안정한 개발 릴리스를 구분한다.

종합 지침: 필요한 기능을 기준으로 기존 프로젝트 기능, 표준 라이브러리, 성숙한 외부 패키지, 작은 자체 구현을 비교한다. 재사용이 제공하는 전문성과 경계 사례 처리를 플랫폼 지원, 전이 의존성 그래프, 빌드·배포 무게, 라이선스 적합성, 유지보수, 업그레이드, 제거 부담과 견준다. 직접 선언 수가 적어도 전이 의존성 범위는 클 수 있다.

사소한 편의 기능 때문에 큰 프레임워크를 도입하기보다 지원 동작이 필요에 잘 맞는 패키지를 선호한다. 반대로 성숙한 파서, 코덱, 보안상 중요한 기본 기능을 다시 구현하면 잘 지원되는 의존성을 유지할 때보다 훨씬 큰 유지보수 부담이 생길 수 있다. 목표는 패키지 수를 0으로 만드는 것이 아니라 책임질 근거가 있는 선택이다.

Go의 문서화된 절차에는 `go list`로 업데이트를 찾고 `go mod tidy`로 선언한 요구 사항을 동기화하는 작업이 포함된다. Go 버전 지침은 안정 릴리스와 안정성을 보장하지 않는 개발·시험판 버전을 구분한다. 종합 지침: 유지보수 책임을 정하고 업그레이드 전에 관련 동작을 검토한다. 대응하는 작업은 생태계마다 다르다.

## 적용 조건과 예외

패키지를 추가하기 전과 지원 상태, 신뢰, 요구 사항, 플랫폼 전제가 바뀔 때 적용한다. 작고 이해하기 쉬운 기능은 자체 소유 비용이 더 낮을 수 있다. 복사나 벤더링도 버그 수정과 업데이트 책임을 넘겨받는 것이며 필요한 고지를 보존해야 한다.

규제, 오프라인, 임베디드, 배포 제약이 있는 환경에서는 비교 결과가 달라질 수 있다. 호환성 버전 규칙은 의도한 약속을 전달할 뿐 정확성이나 적합성을 입증하지 않는다. Go 예시를 다른 패키지 관리자에 적용해서는 안 된다. 보안과 라이선스 판단에는 최신 패키지별 근거가 필요하며 이 항목은 어떤 패키지도 인증하지 않는다.

## 점검

도입과 유지보수를 위한 제안 점검이다.

- 필요한 기능, 검토한 대안, 선택 버전, 총비용을 감수할 근거를 적는다.
- 직접·전이 의존성, 지원 대상, 라이선스, 릴리스 이력, 유지보수 책임을 확인한다.
- 도입 전에 대표 입력, 실패 동작, 중요한 연동 제약을 시험한다.
- 업데이트, 롤백, 교체 경로를 정하고 중요한 업그레이드 후 관련 동작을 다시 검증한다.

## 근거

- [Cox, Our Software Dependency Problem](https://research.swtch.com/deps): “What is a dependency?”, “Inspect”, “Abstract”, “Avoid”, “Upgrade”를 2019년 저자 원문에서 확인했다. 사례는 역사적 사례이며 현재 패키지 평가가 아니다.
- [Go: Managing dependencies](https://go.dev/doc/modules/managing-dependencies): 작업 흐름, 업데이트 발견, 의존성 동기화 항목에서 공식 명령을 확인했으며 실행하지는 않았다.
- [Go: Module version numbering](https://go.dev/doc/modules/version-numbers): 개발·시험판·메이저·마이너·패치 항목의 공식 호환성 규칙을 확인했다. 이 문헌 확인만으로 실제 런타임 결과가 성립하지 않는다.

# 숨겨야 할 설계 결정을 중심으로 모듈 경계 정하기

## 지침

출처에서 확인한 내용: Parnas는 처리 단계에 따른 분해와 변경 가능한 결정을 숨기는 경계를 대조한다. 그가 말하는 모듈은 반드시 프로시저일 필요가 없는 책임 할당 단위다. Abseil은 더 좁은 C++ 사례를 제시한다. 파일 내부에서만 쓰는 보조 함수는 가시성을 제한하고 입력을 명확히 할 수 있지만, 객체 상태와 복잡하게 상호작용할 때는 예외가 있다.

종합 지침: 표현 방식, 저장 형식, 순서 정책, 자원 소유권, 프로토콜 규칙처럼 변경이 여러 곳으로 번질 결정을 찾는다. 그 결정의 해석과 변경을 일관된 계약 안에 둔다. 호출자가 의존해도 되는 내용과 내부에 남길 내용을 명시한다. 한 모듈이 여러 파일에 걸칠 수 있으며, 아주 작은 클래스 여러 개가 여전히 하나의 구현 결정을 공유할 수도 있다.

경계를 넘어가는 지식을 추적한다. 내부 컨테이너 반환, 특정 초기화 순서 요구, 저장 기술에 종속된 오류 노출은 필드가 비공개여도 클라이언트를 결합할 수 있다. 이런 지식을 없앨 수 있다면 호출자의 목적을 표현하는 연산을 선호한다. 필요한 동작은 드러낸다. 소유권, 실패, 수명, 동시성, 순서 보장을 호출자가 알아야 한다면 계약에 포함한다.

## 적용 조건과 예외

변경이 모듈 경계를 반복해서 넘거나 검토자가 많은 내부 사항을 함께 이해해야 할 때 사용한다. 처리 단계는 실행, 스트리밍, 스케줄링을 설명한다. 단계 사이의 계약이 안정적이고 독립적으로 유용하다면 유지보수 경계로도 쓸 수 있다.

모든 구현 사실을 추가 계층으로 숨기지는 않는다. 공개 데이터 형식 자체가 의도한 계약일 수 있다. 성능에 민감한 경계에는 일괄 처리, 값 타입, 인라이닝이 필요할 수 있으며 Parnas도 구현 오버헤드를 명시적으로 다룬다. 그의 역사적 예시나 Abseil의 C++ 기본 권고가 보편적인 모듈 크기 또는 언어와 무관한 보조 함수 규칙을 확립한 것은 아니다.

## 점검

다음은 제안하는 검토 항목이며 효과가 입증된 예방 장치는 아니다.

- 후보 모듈마다 숨길 결정과 현재 그 결정을 아는 클라이언트를 적는다.
- 가능한 표현 방식 또는 정책 변경을 따라가며 필요한 클라이언트 수정과 각각의 계약상 의존성을 설명한다.
- 노출 타입, 변경 가능한 별칭, 호출 순서, 오류, 공유 상태에서 지식 누출을 검토한다.
- 클라이언트가 내부를 재구성하지 않고 정상 작업을 할 수 있는지 확인한다. 성능 주장을 받아들이기 전에 실제 주요 실행 경로를 측정한다.

## 근거

- [Parnas의 1972년 1차 문헌](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html): “Changeability”, “The Criteria”, “Efficiency and Implementation”을 확인했다. 대학이 제공하는 전사본에는 정확성 보장이 없다는 경고가 있다. ACM 출판사 PDF는 403 응답으로 열지 못했다.
- [1971년 CMU 원 보고서 스캔](https://prl.khoury.northeastern.edu/img/p-tr-1971.pdf): 제목과 “The Criteria”, 인쇄 쪽수 17–21을 확인했다. 기관 저장소 표지가 붙은 대학 미러 자료다. 1972년 판이 아닌 앞선 보고서로 교차 확인했다.
- [Abseil Tip 186](https://abseil.io/tips/186): “Benefits”와 “Reasons to Look Elsewhere”의 C++ 권고를 확인했다. 이 자료들은 설계 논거를 제공하며 이 저장소에서 측정한 결과는 아니다.

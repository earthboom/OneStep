# 최적화의 가독성 비용을 치르기 전에 대표 부하 측정

ID: K-CODE-PERFORMANCE-MEASUREMENT. 유형: 참고 자료. 상태: 사용 가능. 근거 확인일: 2026-11-07.

요약: 지연·처리량·메모리 예산을 정하고 대표 부하와 제한 작업을 확인한 뒤 최적화한다. 벤치마크가 의도한 작업을 측정하는지 확인하고 개선과 함께 정확성·유지보수성을 지킨다.

범위: 게임 프레임 시간·할당을 포함한 애플리케이션·시스템 성능 판단. 도구와 측정 해석은 런타임별로 적용한다.

## 활용 지침

출처 관찰: Gregg는 문제·부하를 먼저 정의하고 제한 동작에 따라 CPU·대기·자원 분석을 고른다 [S1]. 능동 벤치마크는 실행 중 시스템을 살펴 실제로 무엇을 부하 주는지 확인한다 [S2]. Google Benchmark는 반복·시간 선택·컴파일러 제거의 주의를 설명한다 [S3].

응용 방법: 성능 민감 설계를 확대하기 전에 중요한 사용자 작업과 허용 비용을 정한다. 빌드 모드·하드웨어·런타임·데이터·부하·측정 경계를 기록한다. 전체 지연과 국소 마이크로벤치마크, 유지 메모리·할당률·최대 작업 집합을 구별한다.

시간·메모리의 사용 위치를 확인한다. 같은 계약·대표 조건에서 근거 있는 최소 알고리즘·배치·할당·스케줄 변경을 비교한다. 캐시·일괄 처리·풀·공유 상태·동시성이 만드는 무효화·수명 비용을 기록한다. 명료한 기준을 유지하고 국소 개선 뒤 전체 작업을 재검증한다.

## 적용 조건과 예외

측정을 이유로 이미 필수인 실시간·메모리 제약을 제작 후반까지 미루지 않는다. 디버그 결과·인위적으로 데운 캐시·비대표 입력은 배포 동작으로 자동 전이되지 않는다. DoNotOptimize가 표현 안의 모든 최적화를 막지는 않는다. 풀은 메모리를 유지할 수 있고 캐시는 지역성·정확성을 해칠 수 있으며 동시성 증가는 경합을 늘릴 수 있다.

## 확인 항목

제안 점검: 의도한 작업이 실행되고 결과가 사용되었는가? 제한 요인과 설명이 맞는가? 반복된 개선이 꼬리 지연을 포함한 예산에서 의미 있는가? 실패·정리·가독성 비용을 비교하고 환경·결과를 보존한다. 현재 저장소를 최적화해 측정했다는 주장은 아니다.

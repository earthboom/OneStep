# Cross-check a software design by asking a consumer to use it

## Guidance

Give a reviewer the original request and governing contract first. Ask for one ordinary input and one case where two plausible interpretations give different observable outcomes. Then give the reviewer the design and ask them to write the caller's sequence or pseudocode. Record the first step where a required fact must be guessed. Resolve a product choice with its owner and a technical question with the relevant contract or experiment.

## Applicability and exceptions

Useful for shared APIs, changes of ownership, persistence and failure recovery. A clear display-only edit can be checked directly. This is a source-based method. Agreement between reviewers does not establish implementation behavior.

## Checks

Example: feedback files exist in the working directory, but the configured inbox contains only the English file. Derive the expected delivery state, trace which path the caller checks, then repair the missing file and repeat the same check. Hand off the expected transition, its evidence, and any check that must wait for implementation. [OneStep inbox contract](../../feedback/README.md)

For a threshold change, give the consumer 49 calls at 0.8 s and one at 2.0004 s. A round P95 of 0.8 s passes while the every-call condition fails. Ask the consumer to show where the design compares the caller's unrounded duration. For a display-only change check the title and binding. A walkthrough ends with the requirement, preserved behavior, distinguishing input, enforcement point, evidence and owner of any unresolved check. Replay the same case and a preserved caller after revision. ## Evidence

NASA §4.4 distinguishes requirements conformance from suitability for intended use. ARID §2.2 has intended consumers exercise the design. Porter and colleagues tested two specifications with 48 graduate students in sixteen teams of three. Scenario reading found more defects, while gains at collection meetings were offset by losses. Huang and colleagues observed that intrinsic LLM self-correction could degrade reasoning on their tasks. For AI review, independent predictions and source evidence are an application of these findings. A local effectiveness comparison would need substantiated defects, unsupported findings, elapsed time and recurrence on replay. [NASA handbook](https://www.nasa.gov/reference/4-4-design-solution-definition/) · [ARID report](https://www.sei.cmu.edu/documents/1962/2000_004_001_13685.pdf) · [Porter et al.](https://www.cs.umd.edu/~basili/publications/technical/T101.pdf) · [Huang et al.](https://arxiv.org/abs/2310.01798)

For review depth and who should read a design, compare the author's account of the cost of a design document and the role of affected teams. [Malte Ubl, Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)

### Judging a game design finding before implementation (research, 2026-11-26)

OneStep already traces caller expectations, challenges state transitions and hands untested player experience to playtesting. The proposed addition concerns the decision to act on a finding. In the existing review, ask which source establishes the expected outcome, what reachable situation changes the verdict, and who or what could settle any remaining question. Use this only when the disposition would change work. Rank the consequence for players separately from the strength of the evidence. [Current design review](../../skills/vegabond-code-design/references/review.md) · [Existing playtest method](../game/K-GAME-PROTOTYPE-PLAYTEST.md)

| Finding | Evidence and action |
| --- | --- |
| Design defect | Show the agreed constraint, reachable event sequence and observable violation. Check whether the proposed mechanism already prevents it. Repair the affected decision and replay the same case. |
| Missing product decision | Show two player-visible outcomes consistent with the governing sources. Ask the decision owner one question using that situation. A missing engine fact goes to the declaration or a small experiment instead. |
| Improvement candidate | Keep the current design as a candidate. Compare one concrete alternative on a named goal, its cost, and what it might sacrifice. State the observation that would reverse the preference. |
| Player-experience hypothesis | Record the observed or predicted action, plausible competing explanations and the smallest representative playtest that would distinguish them. A loss rate alone cannot identify whether a cue was missed or a risk was taken deliberately. |
| Resolved concern | If the cited contract already permits or settles the behavior, close the finding. An existing observation can be sufficient. |

**Worked example from this checkout.** Crossing Tactics promises physically independent optional packs. A proposed design that registers Bulwark only when Harrier is present violates the promise in the Bulwark-only configuration. Allowing a counterattack only if the guarding player survives is already documented, so rejecting that design solely because simultaneous deaths are conceivable is a false alarm. If a *new* poison effect kills both actors and the sources leave the outcome open, ask who wins. A proposal to add a common encounter base class would need to show a present variant it helps: the recorded Bulwark extension left the runtime source unchanged. Whether newcomers can learn the counter from this encounter needs an unaided first play and a question about what they expected. These are worked judgments using existing documents and a saved diff. The poison effect is hypothetical. **Research behind these judgments**

- Letier and van Lamsweerde's obstacle-analysis retrospective derives obstacles from goals and assumptions about the environment. Look for the shortest *reachable* contradiction. NASA's decision-analysis handbook distinguishes mandatory from desirable criteria, assigns a decision authority and scales analysis to consequences. A stylistic preference alone gives no reason to block implementation. These methods come from requirements and systems engineering. [Obstacle analysis](https://discovery.ucl.ac.uk/id/eprint/10204032/1/Obstacle-analysis-retrospective.pdf) · [NASA §6.8](https://www.nasa.gov/reference/6-8-decision-analysis/)
- Desurvire and colleagues compared heuristic inspection with observed play on an early prototype. Inspection surfaced more issues overall, while players exposed game-specific boredom, pacing and terminology problems missed by inspection. It was one design. Fullerton's *Game Design Workshop*, fifth edition, organizes design around experience goals, prototyping, playtesting and revision. The publisher's description and contents were used for the book. [Comparative study, results and conclusion](https://www.eng.auburn.edu/~sealscd/COMP7970/notes/Playtesting/usingheuristics.pdf) · [Book](https://www.routledge.com/Game-Design-Workshop-A-Playcentric-Approach-to-Creating-Innovative-Games-Fifth-Edition/Fullerton/p/book/9781032607009)
- In his GDC talk, Valve's Mike Ambinder compares observation, verbal reports and instrumentation. Death heatmaps locate trouble, while aggregate measures lose context. Steve Bromley describes how a moderator can mistake optional exploration for a missed objective. Ask the player a neutral question after the action. Maddy Thorson's *Celeste* account documents deliberate timing and position allowances: a late jump could be intended. These are practitioner accounts tied to their games and players. The public session listing and slides supplied the talk evidence. [GDC talk](https://gdcvault.com/play/1566/Valve-s-Approach-to-Playtesting) · [Slides, statistical analysis](https://cdn.fastly.steamstatic.com/apps/valve/2009/GDC2009_ValvesApproachToPlaytesting.pdf) · [PlayStation moderation experience](https://www.stevebromley.com/blog/2015/01/06/some-things-ive-learned-about-moderating-playtesting-sessions/) · [Celeste designer's account](https://www.maddymakesgames.com/articles/celeste_and_forgiveness/)
- A CHI PLAY 2024 interview study with 13 indie games professionals reports constraints in recruitment and handling playtest data. Choose a study a decision can actually use. Hämäläinen et al. generated plausible accounts of experiencing games as art with GPT-3. They proposed synthetic responses for ideation and piloting and called for real data to validate findings. Their study examined questionnaire responses. [Indie developers study](https://eprints.whiterose.ac.uk/id/eprint/216480/7/CHI_PLAY_24_Indie_Playtesting_final_.pdf) · [Synthetic player accounts, CHI 2023](https://acris.aalto.fi/ws/portalfiles/portal/106452436/SCI_H_m_l_inen_etal_CHI_2023.pdf)
- Huang et al. found intrinsic self-correction unreliable on reasoning tasks. Gou et al.'s CRITIC reported improvements with external tool feedback on QA, program synthesis and toxicity tasks. For OneStep, retry a disputed judgment when a contract, trace or observation supplies new evidence. Neither paper measured game-review accuracy. [Intrinsic correction](https://arxiv.org/abs/2310.01798) · [Tool-assisted correction](https://arxiv.org/abs/2305.11738)
- Zheng et al. identified position and verbosity biases when LLMs judged assistant answers. Shankar et al.'s EvalGen study with nine expert users found that people refined criteria after grading examples. For a local trial, use owner-adjudicated labels and reserve unseen cases. If the owner changes a rule, record the version and rescore both procedures under it. A second model can suggest counterexamples; agreement alone does not confer authority. [MT-Bench](https://arxiv.org/abs/2306.05685) · [EvalGen paper](https://people.eecs.berkeley.edu/~bjoern/papers/shankar-validators-uist2024.pdf) · [Authors' ACM conference presentation](https://www.youtube.com/watch?v=pkJJNgMYUyM)

**Proposed adoption test.** Compare the current and proposed wording in fresh contexts against the same held-out game requests and governing documents. Mix defects with deliberately valid unconventional designs, settled vs genuinely missing decisions, costly optional improvements and experiential claims. Include a pair where changing one sentence in the contract reverses the correct verdict. Have the game owner label acceptable actions before seeing outputs, and adjudicate findings without procedure labels. Count known defects caught and missed, supported defects among all reported defects, valid designs blocked, needless questions, and experience claims asserted without player evidence. Count equivalent findings once. Measure review plus downstream rework time. Advance to the design skill only if high-consequence misses fall without an unacceptable increase in false blockers or cost, under tolerances agreed before the trial. Current evidence supports the proposal; the earlier follow-up timings (local trial file `skills/vegabond-code-design/tests/repository-change-quality/followup-results.json`) measured implementation verification.

**Pilot decision, 2026-11-26. Retain the current design skill.** Eight fresh AI reviewers assessed the same eight-item fictional game proposal under two contracts, with two matched repetitions per contract. Changing one sentence from spending a seal on the first attempt to spending it on the first valid input reversed which of two proposed mechanisms required repair. Reviewers froze their initial findings before receiving the same producer decision on tied ticks and revising the design. Two separate AI adjudicators each graded a mixed, arm-blind batch against the fixture's prewritten answers. The user authorized testing before adoption; the exercise used stipulated game rules and a scripted producer reply. Protocol and thresholds (local trial file `skills/vegabond-code-design/tests/game-design-judgment/protocol.json`) · Candidate wording (local trial file `skills/vegabond-code-design/tests/game-design-judgment/proposal.txt`)

Both procedures caught 12/12 important defect opportunities per arm (three per review, including recovery/redelivery, the incorrect seal path and an absent accessible lane cue). Each had zero false blockers, unsupported defects, unnecessary product questions, unsupported claims about players or material gaps in the revised handoff. Both procedures followed the changed seal rule, requested the missing tie decision, retained the optional nature of the architecture change and called for player observation in all four runs. The current procedure took 150.6 s for review and 119.4 s for design revision; the candidate took 170.8 s and 129.4 s. Combined AI wall time increased from 270.0 to 300.2 s (+11.2%). The time increase was within the 15% allowance, but the required reduction in important misses did not occur. The existing procedure reached the ceiling on these cases. The trial does not estimate accuracy on open-ended production proposals or human-player outcomes. Keep the examples as reference material.

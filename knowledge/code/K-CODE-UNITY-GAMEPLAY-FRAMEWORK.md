# Verify Unity gameplay boundaries in C# assemblies, assets and Player builds

## Guidance

Start from representative play. Tactics and cards need command validation, resolution order and reproducible state. Action games need input-to-intent, an owner for cost/cooldown and a presentation observer. Network games need authoritative results and reconciliation. Content games need stable definitions plus per-session state. Bulk simulations need measured access patterns before moving to Entities.

Put Unity entry points above the rule owners. Use .asmdef and No Engine References when the project has a meaningful engine-independent unit. Folders and a small public surface may suffice initially. Use a common base type only when initialization, failure and cancellation contracts are shared. Store Inspector inputs in serialized fields. A ScriptableObject can supply shared definitions, while session objects own health and progress. Define writers and reset behavior for deliberately shared mutable assets. Commands with known targets benefit from explicit requests. Event Channels suit genuine notifications.

Track serialized, bundle and dynamic-key dependencies separately. Keep .meta GUIDs with assets and check Prefab overrides after field rename or type/assembly moves. FormerlySerializedAs can assist a field rename, while SerializeReference serves a different polymorphic/shared-reference use case. Load actual prior assets and separate save files. Give every Addressables handle an owner and release path on failure, cancellation and reentry.

## Applicability and exceptions

Subscriptions scoped to activation need deactivation cleanup. Destruction tokens must be observed and do not cover every pool reuse or scene transition. With Domain Reload disabled, consecutive Play sessions can inherit static subscriptions. Editor compilation cannot establish release Player behavior for reflection, generic code and stripping. The cited Unity 6.3 language notes and Addressables 1.21/2.7 materials describe different versions. Verify installed packages and backend.

## Checks

Capture editor/package/platform/backend and entry scene. Inspect .cs, .asmdef, scene, Prefab, ScriptableObject, .meta, settings and bundle changes together. Run rules in Edit Mode, startup and cleanup in Play Mode, and physical pack inclusion in the target Player. Start base, A, B and both, and test B with A's prefab physically absent. Inject the forbidden reference to prove detection. Repeat pool reuse, scene exit during loading, consecutive Play sessions and old asset reload. Measure the files, registrations and effort for the next one or two content changes.

## Evidence

The November 22 review compared Unity documentation, Chop Chop, Boss Room, shipped project accounts and studies. A review covered 36 papers, the code-smell study surveyed 68 and analyzed 100 Unity projects, and UnityBench-Mini3D used 1,178 checks across 77 short tasks. Core ECS is a formal model, and a tower-defense comparison reports its own workload. The A/B Unity pilot is proposed, not an executed port of the C++ examples.

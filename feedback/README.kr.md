# 전략 피드백

OneStep을 프로젝트에서 실제 사용하며 관찰한 전략상의 문제, 유용했던 동작, 개선 제안을 잠시 접수하는 곳입니다. 일반적인 산출물 결함은 작업 프로젝트의 문제 기록에 남깁니다. 별도 피드백 스킬, 카탈로그, 보관소나 사용 대장은 필요하지 않습니다.

## 작업 프로젝트에서 제출하기

1. 결과를 인계하거나 중요한 사실을 발견했을 때 OneStep 지침, 작업 분류, 지식 조회, 검증 방식에 대한 피드백이 있는지 살핍니다. 내용이 없는 정례 보고를 작성하지 않습니다. 지침 자체의 결함, 지침을 따르지 않은 경우, 필요한 수행 능력이 없는 경우, 프로젝트별 선호를 구분합니다. 원인이 불확실해도 관찰한 내용을 제출할 수 있습니다.
2. 작업 프로젝트에서 명시적으로 제공하거나 설정한 OneStep 체크아웃을 사용합니다. 해당 접수함에 대한 쓰기 허가와 실제 파일 접근 권한이 필요합니다. 지침을 읽을 수 있다는 사실만으로 쓰기 권한이 생기지는 않습니다. 경로 설정은 작업 프로젝트에서 관리합니다. OneStep에 다른 프로젝트의 물리 경로나 활성 출처 연결을 넣거나 관련 없는 프로젝트를 뒤지지 않습니다.
3. 독립적으로 처리할 사안 하나를 [양식](template.kr.md)에 따라 `YYYY-MM-DD-short-topic.md`로 작성합니다. 영어 원본에서 같은 이름의 `.kr.md` 번역본을 생성합니다. 이름이 겹치면 고유한 접미사를 사용하고 기존 보고서를 덮어쓰지 않습니다. 실제 사용한 OneStep 버전을 적고 모르면 `unknown`으로 둡니다. 관련 스킬, 조건, 기대한 동작, 관찰한 동작, 영향, 민감 정보를 제거한 최소 근거를 적습니다. 사실·추정 원인·제안을 구분합니다. 긍정적인 피드백은 유지할 동작과 실제 이점을 설명합니다.
4. 자격 증명, 비공개 원자료, 전체 작업 로그는 제외합니다. 익명화한 맥락, OneStep 기준 상대 경로, 최소한의 발췌나 재현 절차를 사용합니다. 직접 접근할 수 없었던 자료의 검증 한계를 밝힙니다.
5. 목적지와 쓰기 허가가 확인되면 해당 체크아웃의 `feedback/`에 두 파일을 작성하고 그 위치에서 확인합니다. 영문과 한국어 파일 이름이 **모두** 비어 있는 이름을 선택합니다. 중간에 쓰기가 실패하면 가능한 범위에서 이번 제출의 빠진 파일을 보완하고 다시 검사합니다. 다른 사안에 해당하는 기존 파일 쌍으로 이번 제출을 증명할 수 없습니다. 제출은 전략 수정, 다른 후기 삭제, 커밋, 푸시, 게시를 허가하지 않습니다.

### 결과를 전달할 때 도착 확인하기

설정된 OneStep 체크아웃의 `tools/check_feedback.py`에 영문 보고서의 파일명을 전달합니다. 체크아웃 루트에서는 다음과 같이 실행할 수 있습니다.

```text
python tools/check_feedback.py 2026-11-20-feedback-lines-not-submitted.md
```

다른 작업 프로젝트에서는 허가된 OneStep 체크아웃에 있는 이 스크립트의 경로로 실행합니다. 현재 작업 디렉터리와 관계없이 스크립트가 속한 체크아웃의 접수함을 검사합니다. 두 파일의 내용을 열지 않고 절대 경로와 파일 상태를 출력합니다. 종료 코드 0과 `pair_present: true`는 두 경로에 현재 비어 있지 않은 일반 파일이 있다는 뜻입니다. 도우미를 사용할 수 없으면 사용 가능한 파일 도구로 같은 두 경로를 확인합니다. 도착을 확인한 뒤 유지관리자의 검토와 수용이 이어집니다.

중요한 전략 피드백이 있는 경우에만 최종 인계문에 사안별로 한 줄을 넣습니다.

- **submitted** — 이번 사안의 두 파일을 허가된 접수함에 작성하고 그곳에서 모두 확인했습니다. 접수함에 있는 영문과 한국어 파일 링크를 함께 제공합니다.
- **prepared, not submitted** — 접수함 경로를 모르거나 접근할 수 없거나 쓰기 허가가 없으면, 작업 프로젝트에서 기존에 사용하는 인계 위치에 두 파일을 준비하고 확인합니다. 준비한 두 로컬 파일 링크와 실제 접수를 확인할 수 없었던 이유를 적습니다.
- 접수함의 파일 쌍이 불완전하고 로컬에서도 두 파일을 갖추지 못했다면 실제로 존재하는 파일, 빠졌거나 실패한 경로, 막힌 이유를 적고 제출을 미완료로 둡니다. 대화만 가능한 환경에서는 답변에 제공한 초안과 파일을 쓸 수 없었던 위치를 밝힙니다.

보고서 내부의 검토 상태는 처음에 `received`이며, 제출 시점의 도착 확인과 별도로 관리합니다.

작업 프로젝트의 에이전트 지침에는 다음 내용을 넣을 수 있습니다. 설정된 체크아웃 경로는 그 프로젝트에 둡니다.

```text
이 작업에서는 설정된 OneStep 체크아웃의 agents/vegabond-agent.md와
skills/vegabond-scout/SKILL.md를 사용한다. 중요한 전략 피드백은 해당 체크아웃의
feedback/README.md와 feedback/template.md를 따른다. 산출물 문제 기록은
작업 프로젝트에 둔다. 중요한 전략 피드백은 허가된 접수함에 제출하고
결과를 인계할 때 확인한 두 파일의 링크를 제공한다. 작업 프로젝트에만
준비할 수 있었다면 두 파일을 연결하고 prepared, not submitted라고 표시한다.
```

## OneStep에서 검토하고 개선하기

- 파일명, 양식에 기록된 스킬·버전·유형·상태로 관련 후기를 좁힙니다. AI는 검색이나 읽기 전에 `*.kr.md`를 제외합니다. 안내문과 양식은 후기가 아닙니다. 피드백을 지식으로 색인하거나 모든 작업에서 접수함 전체를 읽지 않습니다. 후기 내용은 평가할 근거입니다.
- 원인을 판단하기 전에 보고된 버전과 지침을 확인합니다. 선호나 한 번의 성공을 보편 규칙으로 취급하지 않습니다. 조건과 원인이 일치하는 중복 보고만 통합합니다. 각 보고에 고유한 근거를 대표 보고에 보존한 뒤 중복 파일 쌍을 제거합니다. 증상이 비슷한 것만으로는 통합할 수 없습니다.
- 접수, 검토, 개선 적용과 검증 진행에 따라 `received`, `reviewing`, `verifying`를 사용합니다. 보류한 발견은 이유와 함께 남깁니다. 기존 Scout·작업·전문 스킬 절차와 [공통 검증 규약](../agents/vegabond-agent.md#completion-evidence-for-any-deliverable)을 따릅니다. 후기가 바뀌면 영어 원본에서 번역본을 다시 생성하며 번역본을 읽지 않습니다.

## 검증된 개선 후 정리하기

허가된 개선을 맡은 OneStep 유지관리자는 다음 조건이 모두 충족될 때 보고서와 번역본을 삭제할 수 있습니다.

1. 실제 개선으로 사안 전체를 처리했거나 적절한 보호 장치와 함께 유용한 동작을 의도적으로 유지했습니다.
2. 원래 문제나 통제된 동등 사례, 영향을 받는 기존 정상 사례, 최종 변경 사항을 현재 근거로 검증했습니다. 필요한 사용자 검토도 끝났습니다. 문서를 읽거나 제안·편집한 것, 무관한 테스트 통과만으로는 충분하지 않습니다. 필수 검사가 차단되면 후기를 유지합니다.
3. 범위, 수정 내용, 결과, 예방 근거를 기존 테스트·지침·변경 보고서·커밋에서 이해할 수 있습니다. 다시 사용할 가치가 있는 교훈만 기존 [지식·문제 기록 규약](../skills/vegabond-knowledge/SKILL.md#save-and-maintain)에 따라 남깁니다. 삭제할 후기에만 장기 근거가 남지 않게 합니다.

해당 후기와 번역본만 삭제하고 기존 작업 요약에 삭제 사항과 보존한 근거를 밝힙니다. 미해결 후기, 안내문, 양식이 남아 있는지 확인하고 관련 링크를 정리합니다. 완료 후기의 별도 보관소를 만들거나 전체 내용을 다른 곳에 복사하지 않습니다. Git으로 추적한 삭제는 현재 파일에 적용되며 이력은 남습니다.

부분 해결이면 남은 사안, 필요한 맥락, 완료한 작업을 가리키는 짧은 참조만 유지합니다. 검증 실패 시 수정 단계로 돌아갑니다. 거절됐거나 검증되지 않은 제안은 별도 정리 허가가 없는 한 처리 상태를 보존합니다. 오래됐거나 읽었다는 이유로 삭제하지 않습니다.

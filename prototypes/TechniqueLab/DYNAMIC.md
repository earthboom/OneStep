# Dynamic route and crowd experiment — 2026-11-08

This requested experimental extension keeps the original scene, build and historical measurements intact. New `DynamicLab` code and a separate scene/player exercise a shared field while agents move. Canonical knowledge inputs are PATH (field identity, directed costs and topology invalidation) and CROWD (route/local avoidance/rendering separation). A records lookup returned no applicable game incident; an unrelated fiction recovery hit was rejected.

## Design and acceptance

Use a four-neighbor unit grid and equal-radius discs moving continuously along cardinal center-to-center segments. One world owns the graph, reservations and obstacle transactions. Each active mover reserves its current and destination cell. Neighbors choose an available downhill cell or yield, with rotating arbitration order. A right-edge exit strip connects at zero cost to one field sink; arrival removes agents at that strip. The two single-cell wall openings remain the merge bottlenecks. This is conservative cell-reservation local avoidance for a shared goal, not ORCA or unconstrained human crowd motion. ORCA's reciprocal velocity-space constraints are a different algorithm; its guarantees cannot be inherited by this implementation.

A close request immediately excludes the cell from new routes and rebuilds the field. If an agent already reserves that cell, physical closure waits while it completes the segment and leaves. The obstacle becomes solid only when clear. Reopening clears the obstacle and refreshes routes. Agent IDs and continuous positions survive every topology change. Immediate crushing doors, arbitrary obstacle velocities, different radii, diagonals, opposing traffic and production physics integration are outside this experiment.

Required behavior checks: request closure during an occupied traversal, retain positions without reset/teleport, drain the cell, reroute followers through the other door; close both routes, safely wait, reopen and complete; change a crate cell while moving; drain crowded merges at 64 and 256 agents without pair/wall penetration, stale-field consumption, illegal reservation or starvation within declared scenario timeouts (60/120 simulated seconds). Independent continuous segment/geometry checks and native Unity obstacle overlaps must inspect the actual movers. An avoidance-disabled control must demonstrate overlap sensitivity. Use deterministic fixed steps for behavior; accelerated behavior playback is separate from real-time performance.

Performance: 64/256/512 agents, same scene/render settings, avoidance enabled versus disabled, one second warmup and six seconds measured per case, three sequential Windows release Mono processes. Simulation runs at 60 Hz using an accumulator, with bounded catch-up and retained backlog. Capture every measured frame interval, engine CPU/GPU timings when supported, navigation/update component costs and topology-event costs. Target p95 frame interval <=16.67 ms on the observed host; a miss is a reported limit, not a discarded sample. Maintain active counts during the measurement by choosing routes longer than the window; no periodic respawn hides arrival/idle costs. Timing-stat overhead, waits, OS load, asynchronous GPU data and missing counters remain explicit. No adding CPU and GPU times together.

Implementation/verification order: write failing geometry/lifecycle checks; implement owned transactions/reservations; run engine checks; build the dedicated scene; run final PlayMode and three players plus actual live controls; analyze raw distributions; update existing knowledge and regenerate its catalogs/translations. No production integration, dependency installation, commit, push or unrelated file cleanup is authorized by this experiment.

## Progress

Basic lifecycle checks demonstrated 5/8 failures on minimal kernels, then passed 8/8 after implementation. First actual PlayMode passed occupied closure (16/16), full blockage/reopen (32/32), crate changes (32/32), dense merges (64/64 in 31.27 s; 256/256 in 101.47 simulated s) with zero pair/wall/teleport/reservation violations. The avoidance-disabled control detected 8,969 overlapping pair observations. This is pilot evidence, not final acceptance.

The batch Editor does not continuously render Game view: pilot GPU/render timings were zero despite CPU counters. Whole-frame acceptance therefore requires non-batch Windows players with positive render-thread/GPU timing samples; Editor PlayMode is retained for behavior only. This was an intermediate capability finding; final evidence is linked below.

Review corrections reproduced four failed assertions, then passed all 12 in PlayMode: repeated crate movement cycles through valid floor cells, paused controls immediately synchronize native/visual obstacles, and the audit retains terminal movement segments after arrival. The initial reserved-traversal fixture committed closure 38 ticks after its early request. A further geometric occupancy assertion exposed that the request preceded body entry; the final trigger is inside the actual door volume and commits 25 ticks (0.4167 simulated seconds) after request. Both red records remain with the results.

Hidden standalone execution also produced zero render/GPU counters and was rejected. A visible run of the same binary produced genuine rendering and positive GPU samples. Final players therefore use `-Visible`. CPU/render and wall intervals are retained for every measured frame. GPU fields can still be zero in some genuine rendered frames: these are missing GPU timings, not zero cost. An analysis-only assumption requiring 95% GPU coverage was rejected because it conflated optional GPU-tail completeness with measured whole-frame intervals. Final analysis exposes coverage and withholds GPU-tail validation when any values are missing; it does not remove whole-frame samples or loosen the 16.67 ms target. Unity's documented asynchronous timing/resource limitations and this evidence boundary must accompany the results.

## Final engine evidence

[Results and reproduction](DYNAMIC-RESULTS.md) retain final PlayMode, three same-build standalone sessions and actual UI checks. Each passed 12 regressions and six scenario expectations. The 64/256 safe merges completed in 31.27/101.47 simulated seconds. Measured windows retained 149,913 whole-frame intervals; all six count/mode combinations met 16.67 ms p95 across the final three sessions. For 512 reserved agents p95 was 2.87–3.15 ms. Earlier rendered captures showed 24.61–31.24 ms for that case and remain in `Results/Dynamic/pre-body-capture`; no performance optimization or isolated-load comparison established the cause of that difference. Adoption remains conditional on actual hardware/scene/load.

GPU values were missing for 11,887 of 149,913 observations; GPU tail latency remains unvalidated. Raw measurements were losslessly compressed and round-trip hash checked; analysis of the compressed input reproduced the uncompressed summary byte for byte. PATH, CROWD, GUIDE and the reuse convention were updated. Current cumulative limited engine coverage is four sheets; 39 remain unvalidated locally. Catalog, retrieval and document checks complete the handoff separately from these engine checks.
